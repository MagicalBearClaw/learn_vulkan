## What you should already know

**C++.** Classes, references, RAII, `std::vector`, destructors running in reverse
order of construction. The code uses C++23 but stays conservative — no template
metaprogramming, no coroutines. If you can read a constructor that acquires a resource
and a destructor that releases it, you can read all of it.

**A terminal.** Enough to run CMake and a compiler.

**No graphics experience.** Where a chapter needs mathematics it derives what it needs —
chapter 1.12 builds a rotation matrix from a unit circle rather than quoting one, and 1.13
derives the perspective projection from similar triangles. The appendix
[Vectors and Matrices](/appendices/mathematics/) gathers the same material in one place,
from the beginning: vectors, dot and cross products, what the columns of a matrix mean,
and homogeneous coordinates. Read it first or use it as a reference, whichever suits.

School trigonometry — sine, cosine, Pythagoras — is assumed. Nothing beyond it is.

## What you need installed

### A GPU that supports Vulkan 1.3

Any discrete GPU from roughly 2016 onward, and most integrated graphics from 2019
onward. Check with:

```bash
vulkaninfo --summary
```

If that reports an instance version of 1.3 or higher and lists your GPU, you are fine.
If the command is missing, the Vulkan tools are not installed yet — see below.

:::note[If your driver is older than 1.3]
The features this series relies on — dynamic rendering and `synchronization2` — exist
as extensions on 1.2 drivers (`VK_KHR_dynamic_rendering`, `VK_KHR_synchronization2`).
The code would need to request them explicitly and use the `KHR`-suffixed names. Every
sample would still work, but none of the samples here do that, so updating your driver
is by far the easier path.
:::

### Linux

Your distribution supplies the toolchain and the Vulkan runtime pieces. On Arch and
derivatives:

```bash
sudo pacman -S base-devel cmake ninja clang git python \
               vulkan-validation-layers vulkan-tools
```

On Debian and Ubuntu the equivalents are `build-essential cmake ninja-build clang git
python3 vulkan-validationlayers vulkan-tools`. You will also need your GPU vendor's
driver, which is usually already present.

Every *library* the samples link — SDL3, volk, glm, spdlog, the Vulkan headers, VMA,
`stb`, Assimp and Slang — comes from **[vcpkg](https://vcpkg.io/)** instead, so set
`VCPKG_ROOT` to point at your vcpkg checkout and there is nothing else to install.
`code/vcpkg.json` lists them and is the only place a version is chosen: one pinned set
of libraries on every machine, so that what this series says a library does is what it
does for you too.

### Windows

1. **Visual Studio 2022** with the *Desktop development with C++* workload.
2. **The [Vulkan SDK](https://vulkan.lunarg.com/)**, which supplies the validation
   layers, the shader compiler and `vulkaninfo`.
3. **[vcpkg](https://vcpkg.io/)**, with the `VCPKG_ROOT` environment variable pointing
   at it. The rest of the dependencies come from `code/vcpkg.json`.

:::note[Spaces in the path]
Some vcpkg ports build through autotools, which mishandles paths containing spaces.
This project's dependency set reaches none of them — `vcpkg.json` switches off SDL3's
default features, which is where the one such port used to come from — so a checkout
under `C:\Users\Your Name\...` builds fine.
:::

### The shader compiler

SPIR-V is the only shader format Vulkan accepts, and this series writes its shaders in
**Slang**. You do not have to do anything about this one either: it comes from vcpkg
like every other library, and the samples link Slang's compiler and call it when they
start. There is no shader build step, no `slangc` invocation and no `.spv` file
anywhere — editing a shader and re-running the sample is the whole loop.

:::note[Why Slang, and why at startup]
GLSL still works, and `glslangValidator` is still in every SDK. Slang gives us one file
per pipeline instead of one per stage, a shared struct for the interface between stages,
and a real module system for the shader code that Part 2 onward reuses across many
pipelines.

Compiling at startup rather than during the build means the `.slang` file beside the
binary is the shader: edit it, run again, done. A shipping application would compile
ahead of time and cache the result instead — chapter 1.9 weighs both.

Chapter 1.9 goes into the language properly; the appendix
[Slang for GLSL programmers](/appendices/slang-for-glsl-programmers/) is the translation
table.
:::

## Building the samples

```bash
git clone <this repository>
cd learn_vulkan_com

# Linux
cmake --preset linux-debug
cmake --build code/out/build/linux-debug

# Windows
cmake --preset x64-debug
cmake --build code/out/build/x64-debug
```

Then run the smoke test, which exists purely to prove the toolchain works before any
chapter asks you to learn something:

```bash
./code/out/build/linux-debug/bin/0.smoke.clear_colour
```

A window with a slowly cycling colour means the compiler, the loader, your driver, the
validation layers and the swapchain are all working. Press <kbd>Escape</kbd> to close
it.

Every sample in the series accepts the same options:

| Option | Effect |
|---|---|
| `--frames N` | Render N frames, then exit |
| `--screenshot PATH` | Write the last frame as a PNG |
| `--width N`, `--height N` | Initial window size |
| `--no-validation` | Turn the validation layers off |

## Turn on validation and leave it on

Vulkan itself checks nothing. The validation layers are a separate piece of software
that sits between your calls and the driver and tells you, in plain language, exactly
which rule you broke.

They are on by default in these samples. If you see this at start-up:

```
[warning] Validation layers requested but VK_LAYER_KHRONOS_validation is not installed.
```

stop and install them. Developing Vulkan without validation means debugging blank
screens by guesswork.

:::tip[Treat warnings as errors]
Every sample in this series runs with **zero validation messages**. If one of your own
experiments starts producing them, fix it before moving on — a validation message is
nearly always a real bug that happens to work on your machine today.
:::

## Getting the assets

The early chapters need nothing. From the model-loading chapter onward:

```bash
python3 tools/bootstrap.py
```

This downloads openly licensed models and textures into `assets/`, which is not
committed to the repository.

## A note on how to read the code

Each chapter is a single `main.cpp` holding that chapter's subject, written out in full.
What earlier chapters taught is not retyped: it lives in a shared library, `vkcommon`,
and the chapter uses it from there.

So chapter 1.5 writes command buffers and the frame by hand, and takes the window, the
instance, the device and the swapchain — chapters 1.1 to 1.4 — from the scaffold. Its
`main.cpp` is about a third the length it would otherwise be, and all of it is the thing
the chapter is actually about.

**Nothing in that library is hidden from you.** When a chapter's subject moves into
`vkcommon`, that chapter ends by showing the finished file — header and implementation,
in full — and explaining what changed on the way in. Chapter 1.1 ends with the whole of
`vkc::Window`, 1.2 with `VK_CHECK` and `vkc::Instance`, and so on to 1.14 and
`vkc::Camera`. By the end of Part 1 there is no line of `code/common/` that has not
appeared in an article, which is checked by a tool rather than by good intentions:

```bash
python3 tools/coverage.py --part 1      # every line each chapter adds is in its article
python3 tools/attribution.py --strict   # every line of vkcommon is in its owning chapter
python3 tools/terms.py --part 1         # every Vulkan name is explained where it first appears
```

**The rule is enforced by the build, not by good intentions.** Each chapter's
`CMakeLists.txt` names the pieces it may link:

```cmake
add_chapter(1.5.command_buffers
    SOURCES main.cpp
    SCAFFOLD vkc_context vkc_swapchain)
```

Reaching for something a later chapter teaches — `vkc_frame`, here — is a link error, not
a matter of discipline. Chapter 1.1 names nothing at all, which is why it begins with
`SDL_Init`.

You can still diff one chapter against the next to see exactly what it added:

```bash
diff code/src/1.getting_started/the_swapchain/main.cpp \
     code/src/1.getting_started/command_buffers/main.cpp
```
