Vulkan is a specification for talking to a GPU. It covers rasterised graphics, compute,
and increasingly ray tracing, and it is deliberately low-level: it describes the
machine fairly directly and leaves the convenience to you.

That last part is the whole personality of the API, and it is worth understanding
*why* before you write a line of it. Otherwise the first few chapters feel like
arbitrary bureaucracy.

## The problem Vulkan was built to solve

An OpenGL driver is a large, clever program. When you call `glDrawArrays`, the driver
has to work out what the last few hundred state-setting calls added up to, decide
whether the shader needs recompiling for that combination, check that your arguments
make sense, guess when a buffer is safe to overwrite, and insert whatever
synchronisation the hardware needs. Every draw call.

This worked for a long time. It stopped working well when:

- **CPUs went wide.** All that driver work happened on one thread, because the OpenGL
  context is a single global state machine. Eleven idle cores do not help.
- **Games got expensive to validate.** Checking every argument on every call costs
  real time when there are tens of thousands of calls per frame.
- **Guessing got expensive.** The driver has to be conservative about what you *might*
  do next, and conservative means slower.

Vulkan's answer is to stop guessing. You state what you want up front, you say when
things are allowed to happen, and the driver does close to nothing at draw time. The
cost is that all of that becomes your job.

## Six ideas that explain the shape of the API

Everything in the next seven chapters is one of these.

### 1. Nothing is global

There is no context. There are objects: an instance, a device, a queue, a command
buffer. Every function takes the object it operates on as its first argument. Two
threads using two devices do not interact at all.

### 2. You do not call the GPU, you record for it

There is no function that draws a triangle now. You record commands into a
`VkCommandBuffer`, and later submit that buffer to a **queue**. Recording is ordinary
CPU work and can happen on many threads at once. Submission is the moment work crosses
over.

The gap between "recorded" and "executed" is the single biggest adjustment coming from
OpenGL, and it is the reason synchronisation gets a chapter of its own.

### 3. State is compiled, not set

A `VkPipeline` bakes the shaders, blending, depth testing, primitive topology and
vertex layout into one immutable object. Creating one is expensive. Binding one is
nearly free.

This is the trade Vulkan makes everywhere: pay at creation time, so that the frame loop
is cheap.

### 4. Memory is yours

Vulkan will allocate a block of GPU memory when asked. It will not decide which kind
of memory a texture should live in, sub-allocate out of the block, or move things when
you run out. Desktop drivers allow relatively few large allocations, so real programs
allocate big blocks and manage them themselves.

We use the [Vulkan Memory Allocator](https://github.com/GPUOpen-LibrariesAndSDKs/VulkanMemoryAllocator)
for this. It is what most shipping engines use, and hand-rolling one teaches you about
allocators rather than about graphics.

### 5. Images have a layout

The arrangement of pixels in memory that is fast to render into is not the one that is
fast to sample from, nor the one the display hardware wants. Vulkan exposes this as
**image layout**, and images do not change layout on their own. You insert a barrier
saying so.

Forgetting one is the most common beginner error in Vulkan by a wide margin. The
validation layers will tell you, in detail, which is why they are not optional.

### 6. Almost everything is optional

Features, extensions and even API versions are opt-in. A `VkDevice` has exactly the
capabilities you asked for and no others — using a feature you did not enable is
undefined behaviour, not an error. Being explicit is how the driver knows it can stop
being careful.

## So how bad is it really

Honestly: the reputation comes from Vulkan 1.0, and it has improved a great deal.

A 1.0-era tutorial spends chapters on `VkRenderPass` and `VkFramebuffer` objects,
which had to be created up front, kept consistent with the swapchain, and recreated
on every resize. Vulkan 1.3 made **dynamic rendering** core: you describe what you are
rendering into at the point you render into it, and both object types disappear
entirely.

The same is true of synchronisation. The original barrier API had three overlapping
forms with subtly different rules. `synchronization2`, also core in 1.3, replaced them
with one.

This series uses both from the first chapter, which is why the triangle arrives in
chapter 1.7 rather than chapter 5.

## Vulkan compared to what you may know

| | OpenGL | Vulkan |
|---|---|---|
| State | Global, set per call | Compiled into pipeline objects |
| Draw | Executes (eventually) | Recorded, then submitted to a queue |
| Threads | One context, one thread | Record on as many as you like |
| Memory | Driver decides | You allocate and sub-allocate |
| Sync | Driver inserts it | You insert it |
| Errors | `glGetError` | Validation layers, or silence |
| Window | Handled by GLFW/SDL | A `VkSurfaceKHR` and a swapchain you build |

The mathematics — transforms, lighting, projection — is unchanged. That is the part
that transfers wholesale, and it is most of what the later parts of this series are
about.

## Two differences that will bite you

Worth knowing now, because they cause bugs that look like nothing at all:

:::caution[Clip space is not the same]
In Vulkan, **y points down** the screen and **z runs 0 to 1**. In OpenGL, y points up
and z runs -1 to 1. A projection matrix copied from OpenGL material produces an image
that is upside down, or a depth buffer that is wrong in a way that looks almost right.

This project defines `GLM_FORCE_DEPTH_ZERO_TO_ONE` globally to handle the depth half.
The y flip is handled where it comes up, and flagged each time.
:::

:::caution[Nothing checks your arguments]
Pass a garbage value and you get undefined behaviour: a blank screen, a crash inside
the driver, or a result that happens to look correct on your GPU and not on anyone
else's. Turn the validation layers on and leave them on.
:::
