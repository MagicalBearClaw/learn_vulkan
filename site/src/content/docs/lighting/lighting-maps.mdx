Chapter 2.3's materials gave each object one diffuse colour and one specular colour. That
works for a gold cube and fails for nearly everything else, because very few objects are
one material all over. A crate is wood held together by steel, and those two respond to
light in completely different ways — on the same face.

The fix is to stop giving the material *a* colour and give it an image of colours: one
value per texel. This chapter does that for the diffuse and specular terms, and the
lighting arithmetic does not change at all.

## Two maps, two meanings

A **diffuse map** is the surface's colour, texel by texel. It is what you would normally
call "the texture", and it replaces 2.3's `material.diffuse`. It also stands in for
`material.ambient`: a surface's ambient colour is almost always its diffuse colour,
darker, and the light's ambient component already supplies the "darker".

A **specular map** says how much specular light each texel reflects. Bright where the
surface is shiny, black where it is not. It replaces `material.specular`.

Both textures in this chapter are drawn by `tools/make_textures.py` and committed with the
project, like chapter 1.11's test grid. They describe one crate: a brushed-steel frame with
rivets, and five wooden planks. In the specular map the steel is bright with scuffed,
duller patches; the rivets are pure white; the wood is almost black, keeping a faint
varnish sheen; the gaps between planks are zero.

The vertex gains its texture coordinate back, so there is something to look the maps up
with:

And the fragment stage samples both maps and uses them where 2.3 used constants:

```slang title="code/src/2.lighting/lighting_maps/lighting_maps.slang"
float3 surface = diffuse_map.Sample(input.uv).rgb;
float3 shine = specular_map.Sample(input.uv).rgb;

float3 ambient = globals.light.ambient.rgb * surface;
float3 diffuse = globals.light.diffuse.rgb * diffuse_amount * surface;
float3 specular = globals.light.specular.rgb * specular_amount * shine;
```

Both samples happen first, before any arithmetic that could branch. That is chapter 1.11's
rule about derivatives, and it is easy to break the first time a shader grows an `if`.

## Colour is sRGB. Data is not.

Here is the part of this chapter that has nothing to do with Vulkan's API and everything
to do with what numbers mean.

```cpp title="code/src/2.lighting/lighting_maps/main.cpp"
        diffuse_map_ = vkc::load_texture(context(),
                                         vkc::asset_path("textures/lvk_crate_diffuse.png"),
                                         VK_FORMAT_R8G8B8A8_SRGB);
```

```cpp title="code/src/2.lighting/lighting_maps/main.cpp"
        specular_map_ = vkc::load_texture(context(),
                                          vkc::asset_path("textures/lvk_crate_specular.png"),
                                          VK_FORMAT_R8G8B8A8_UNORM);
```

Same loader, same kind of file, different formats. To see why that matters, the curve
behind `_SRGB` is worth writing down.

### What the curve actually is

Human vision is far more sensitive to differences among dark tones than among bright ones.
Storing brightness in a byte *linearly* would therefore waste most of the 256 values on
bright tones nobody can tell apart, and leave visible banding in the shadows. So image
formats do not store linear light. They store a **gamma**-encoded value: light raised to a
fractional power, which spends more codes on the dark end.

Decoding is the inverse, and the exact rule sRGB uses — its **transfer function** — is
piecewise, a short linear segment near black and a power curve above it:

```
   given c = byte / 255,

                    ⎧  c / 12.92                    if c ≤ 0.04045
   linear(c)   =    ⎨
                    ⎩  ((c + 0.055) / 1.055)^2.4    otherwise
```

The threshold sits at byte 10.3, so the linear segment covers only the first ten codes; it
is there because a pure power curve has an infinite slope at zero, which quantises badly.
Everywhere else the exponent 2.4 dominates, and the whole thing approximates `c^2.2`.

Run some bytes through it:

| byte | `c = byte/255` | linear light | as a percentage |
|---|---|---|---|
| 22 | 0.0863 | 0.0080 | 0.8% |
| 64 | 0.2510 | 0.0513 | 5.1% |
| 128 | 0.5020 | 0.2159 | 21.6% |
| 186 | 0.7294 | 0.4910 | 49.1% |
| 255 | 1.0000 | 1.0000 | 100% |

The middle row is the one to remember. **A byte of 128 is not half the light — it is about
22% of it.** The byte that really means half is 186.

### Why that decides the format

The diffuse map is **colour**. It was authored to look right on a display, and displays are
sRGB, so its bytes carry that encoding. `_SRGB` tells the GPU to apply the decode above when
sampling, so the shader receives **linear colour space** values — the only kind it makes
sense to multiply and add. Adding two encoded values would be adding two numbers that are
not proportional to light, and the answer would mean nothing. Chapter 1.11 explained this
for the test grid.

The specular map is **data**. A value of 128 means "reflect half the specular light". It
was never a colour and it was never encoded for a display. Load it as `_SRGB` and the GPU
would run every value through the decode curve anyway: 128 would arrive as 0.216 instead of
0.502, every mid-grey would shrink towards black, and the steel would lose most of its
shine. Nothing errors. The picture is just wrong.

This is not hypothetical, and it is not subtle once you know where to look. Rendering this
chapter's captured frame with the specular map loaded as `_SRGB` changes about 4.5% of the
pixels. The bright highlight along the middle crate's frame breaks up into speckles, because
the scuffed patches — mid-greys in the map — are pushed far darker than the clean steel
around them. And the faint varnish sheen on the planks vanishes entirely: the wood's values
of around 22 out of 255 decode to 0.8%, as the table above shows.

The rule generalises, and later chapters depend on it: **colour textures are `_SRGB`;
everything else is `_UNORM`.** Specular maps, roughness maps, metalness maps, normal maps,
height maps, masks — all data, all `_UNORM`. `vkc::load_texture` defaults to `_SRGB`
because colour is the common case, which makes the `_UNORM` in this chapter a deliberate
line you have to write.

`_UNORM` itself is just "divide the byte by 255", with no curve at all — the numbers arrive
as written.

### One sampler, two textures

A sampler describes **how** to read a texture — filtering, mipmapping, what happens past
the edge — and not **which** texture. Chapter 1.11 kept them as separate objects for
exactly this reason. Any number of textures that want the same filtering can share one,
and a real scene typically needs only a handful of samplers for thousands of textures.

## A set with two kinds of descriptor

The C++ layout mirrors the shader binding for binding: two
`VK_DESCRIPTOR_TYPE_COMBINED_IMAGE_SAMPLER`s at bindings 0 and 1, and a
`VK_DESCRIPTOR_TYPE_UNIFORM_BUFFER` at binding 2. A set has no single type. Each binding
has its own, and the binding numbers and types must agree with the shader — a sampler
declared where a uniform buffer is expected is a validation error at pipeline creation.

```cpp title="code/src/2.lighting/lighting_maps/main.cpp"
        const std::array<VkDescriptorSetLayoutBinding, 3> material_bindings{{
            {
                .binding = 0,
                .descriptorType = VK_DESCRIPTOR_TYPE_COMBINED_IMAGE_SAMPLER,
                .descriptorCount = 1,
                .stageFlags = VK_SHADER_STAGE_FRAGMENT_BIT,
                .pImmutableSamplers = nullptr,
            },
            {
                .binding = 1,
                .descriptorType = VK_DESCRIPTOR_TYPE_COMBINED_IMAGE_SAMPLER,
                .descriptorCount = 1,
                .stageFlags = VK_SHADER_STAGE_FRAGMENT_BIT,
                .pImmutableSamplers = nullptr,
            },
            {
                .binding = 2,
                .descriptorType = VK_DESCRIPTOR_TYPE_UNIFORM_BUFFER,
                .descriptorCount = 1,
                .stageFlags = VK_SHADER_STAGE_FRAGMENT_BIT,
                .pImmutableSamplers = nullptr,
            },
        }};
        const VkDescriptorSetLayoutCreateInfo material_layout_info{
            .sType = VK_STRUCTURE_TYPE_DESCRIPTOR_SET_LAYOUT_CREATE_INFO,
            .pNext = nullptr,
            .flags = 0,
            .bindingCount = static_cast<uint32_t>(material_bindings.size()),
            .pBindings = material_bindings.data(),
        };
        VK_CHECK(vkCreateDescriptorSetLayout(device, &material_layout_info, nullptr,
                                             &material_set_layout_));
```

All three are fragment-stage only. The vertex shader reads none of them — it only passes
the uv along.

## Pools are sized per type

With two descriptor types in play, the pool needs one size entry per type:

```cpp title="code/src/2.lighting/lighting_maps/main.cpp"

            {VK_DESCRIPTOR_TYPE_UNIFORM_BUFFER, vkc::kFramesInFlight + 1},
            {VK_DESCRIPTOR_TYPE_COMBINED_IMAGE_SAMPLER, 2},
        }};
```

```cpp title="code/src/2.lighting/lighting_maps/main.cpp"

            .poolSizeCount = static_cast<uint32_t>(pool_sizes.size()),
            .pPoolSizes = pool_sizes.data(),
```

Each entry counts **descriptors of that type across every set the pool will hold** —
uniform buffers for the two per-frame sets plus the material's, image samplers for the
material's two. `maxSets` is separate, and counts sets: two frame sets plus one material
set. Chapter 2.3 showed what running out looks like; with several types, it is per type, so
you can have room for sets and still run out of one kind of descriptor.

There is one material set rather than 2.3's five, so it is allocated on its own:

```cpp title="code/src/2.lighting/lighting_maps/main.cpp"

```

## Writing three descriptors at once

Filling the set is one `vkUpdateDescriptorSets` call with three writes. Each image write
names the layout the image will be in **when it is sampled** —
`VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL`, where `load_texture` already left both — not
whatever layout it happens to be in while you write the descriptor.

```cpp title="code/src/2.lighting/lighting_maps/main.cpp"
        const VkDescriptorImageInfo diffuse_info{
            .sampler = sampler_.handle(),
            .imageView = diffuse_map_.view(),
            .imageLayout = VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL,
        };
        const VkDescriptorImageInfo specular_info{
            .sampler = sampler_.handle(),
            .imageView = specular_map_.view(),
            .imageLayout = VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL,
        };
        const VkDescriptorBufferInfo params_info{
            .buffer = material_buffer_.handle(),
            .offset = 0,
            .range = sizeof(MaterialParams),
        };
```

Both image infos name the same sampler handle — that is the sharing made concrete.

```cpp title="code/src/2.lighting/lighting_maps/main.cpp"
        const auto image_write = [&](uint32_t binding, const VkDescriptorImageInfo& info) {
            return VkWriteDescriptorSet{
                .sType = VK_STRUCTURE_TYPE_WRITE_DESCRIPTOR_SET,
                .pNext = nullptr,
                .dstSet = material_set_,
                .dstBinding = binding,
                .dstArrayElement = 0,
                .descriptorCount = 1,
                .descriptorType = VK_DESCRIPTOR_TYPE_COMBINED_IMAGE_SAMPLER,
                .pImageInfo = &info,
                .pBufferInfo = nullptr,
                .pTexelBufferView = nullptr,
            };
        };

        const std::array<VkWriteDescriptorSet, 3> material_writes{{
            image_write(0, diffuse_info),
            image_write(1, specular_info),
            {
                .sType = VK_STRUCTURE_TYPE_WRITE_DESCRIPTOR_SET,
                .pNext = nullptr,
                .dstSet = material_set_,
                .dstBinding = 2,
                .dstArrayElement = 0,
                .descriptorCount = 1,
                .descriptorType = VK_DESCRIPTOR_TYPE_UNIFORM_BUFFER,
                .pImageInfo = nullptr,
                .pBufferInfo = &params_info,
                .pTexelBufferView = nullptr,
            },
        }};
        vkUpdateDescriptorSets(device, static_cast<uint32_t>(material_writes.size()),
                               material_writes.data(), 0, nullptr);

        context().name(material_set_, VK_OBJECT_TYPE_DESCRIPTOR_SET, "crate material");
```

The lambda exists because the two image writes differ in exactly two fields. Note that it
captures `info` **by reference** and stores its address — which is fine here only because
`diffuse_info` and `specular_info` outlive the `vkUpdateDescriptorSets` call. Vulkan reads
through those pointers during the call and never after it.

One practical note from building this sample. The first version put the lamp where 2.3 had
it, circling above the scene, and the captured frame had **no specular highlights at all** —
the specular map was working, there was simply nothing for it to show.

A highlight appears where the surface acts as a mirror between the light and your eye.
With the camera and the lamp both above the crates, that mirror point lies above every
front face, off the edge of the geometry. So this sample's lamp sweeps from side to side
low down in front of the crates, where the mirror points land on the steel. If you move the
camera high and find the highlights gone, that is geometry, not a bug.

## What changed since 2.3

- `Vertex` got its texture coordinate back
- the material is two textures and a shininess, bound at set 1 through three bindings of two types
- the pool has a size entry per descriptor type
- one `vkc::Sampler` serves both textures
- one material set, bound once, is shared by three crates
- the lamp sweeps low in front of the scene instead of circling above it

## Words introduced in this chapter

| | |
|---|---|
| **diffuse map** | a texture supplying the surface's colour per texel; replaces a single material colour |
| **specular map** | a texture saying how much specular light each texel reflects; data, not colour |
| **transfer function** | the curve relating a stored value to actual light — sRGB's is a short linear segment plus a 2.4 power |
| **gamma** | the fractional power an image is encoded with, so that byte values are spread to match how eyes see |
| **linear colour space** | values proportional to actual light, which is the only space in which adding and multiplying them is meaningful |

## Exercises

1. Load the specular map as `VK_FORMAT_R8G8B8A8_SRGB` and compare. Then load the *diffuse*
   map as `_UNORM` and describe what happens to the wood. You now have both halves of the
   rule in front of you.
2. Replace `shine` with `float3(1.0)` in the shader — a uniformly shiny crate. The wood
   gleams like the steel, which is the whole case for specular maps in one change.
3. Invert the specular map in the shader (`1.0 - shine`) and look: shiny wood, dull steel.
   Nothing about the geometry changed, only the data.
4. Give the two maps different samplers: nearest filtering for the specular map, linear for
   the diffuse. You will need a second `vkc::Sampler` and a change to one write. Get close to
   a rivet to see the difference.
5. Add a second material — reuse the diffuse map but make a specular map that is uniformly
   bright, a "polished" crate — and draw the middle crate with it. Resize the pool, allocate a
   second set, and rebind set 1 inside the loop only when the material actually changes.
6. Work out, from the table above, which byte value means "reflect a quarter of the specular
   light" in a `_UNORM` map, and which byte would mean the same thing if the map were
   mistakenly `_SRGB`. The gap between those two numbers is the size of the bug.
