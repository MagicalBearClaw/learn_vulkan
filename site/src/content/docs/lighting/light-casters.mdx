Every light so far has been the same kind of light: a point in space, shining equally in
all directions, as strongly at the far end of the scene as right next to it. That is a
useful fiction for learning the shading terms, and it matches almost nothing real.

Real lights differ in two ways that matter to shading: **which direction the light arrives
from** at a given point, and **how much of it arrives**. This chapter handles the three
standard answers — directional, point and spot — and none of them touches the Phong terms
from 2.2. They only change the two inputs those terms take.

## One struct for every kind

All three kinds share one `Light` struct, so that the shader can be written once and 2.6
can put lights of different kinds in a single array:

```slang title="code/src/2.lighting/light_casters/light_casters.slang"
struct Light {
    float4 position;   // xyz: point and spot
    float4 direction;  // xyz, the way the light *travels*: directional and spot
    float4 ambient;
    float4 diffuse;
    float4 specular;

    // Attenuation, for point and spot: intensity = 1 / (c + l*d + q*d^2).
    float constant_term;
    float linear_term;
    float quadratic_term;

    // The spotlight's cone, stored as cosines so the shader can compare them directly
    // against a dot product without calling acos() per fragment.
    float inner_cutoff;
    float outer_cutoff;
};
```

A directional light ignores `position` and the falloff; a point light ignores `direction`
and the cone. Carrying unused fields costs a few bytes and buys one layout.

The C++ side has to match it byte for byte, and this is the sharpest layout case in the
part so far:

```cpp title="code/src/2.lighting/light_casters/main.cpp"
struct Light {
    glm::vec4 position;   // 0
    glm::vec4 direction;  // 16
    glm::vec4 ambient;    // 32
    glm::vec4 diffuse;    // 48
    glm::vec4 specular;   // 64
    float constant_term;  // 80
    float linear_term;    // 84
    float quadratic_term; // 88
    float inner_cutoff;   // 92, a cosine
    float outer_cutoff;   // 96, a cosine
    float padding[3];
};
static_assert(offsetof(Light, constant_term) == 80);
static_assert(offsetof(Light, outer_cutoff) == 96);
static_assert(sizeof(Light) == 112);
```

Five `vec4`s fill offsets 0 to 79. Then five bare floats, and **scalars align to 4, not to
16** — so they pack tightly from 80 in steps of 4, ending at 100. That is the rule worth
carrying: std140 pads vectors, not scalars. The block is 100 bytes of content, and the
`padding[3]` rounds it to 112, because std140 rounds a nested struct up to a multiple of
16 and `Light` is nested inside `Globals`.

```cpp title="code/src/2.lighting/light_casters/main.cpp"
struct Globals {
    glm::mat4 view;           // 0
    glm::mat4 projection;     // 64
    glm::vec4 view_position;  // 128
    Light light;              // 144
};
static_assert(offsetof(Globals, light) == 144);
static_assert(sizeof(Globals) == 256);
```

144 + 112 = 256. The `static_assert`s are what make all of that a fact rather than a hope.

## Directional lights

The sun is 150 million kilometres away. By the time its light reaches a scene, every ray is
effectively parallel: the light arrives from the same direction at every point, and it is
equally strong everywhere.

So a **directional light** has a direction and no position:

```slang title="code/src/2.lighting/light_casters/light_casters.slang"
case kDirectional:
    to_light = normalize(-light.direction.xyz);
    break;
```

The direction stored is the way the light *travels*, which is the convention most engines
use. The lighting terms want the direction *toward* the light, so it is negated. It is also
the same for every fragment — nothing here depends on `input.world_position` — which is
exactly what "infinitely far away" means.

  <figcaption>Directional: every crate is lit the same way, whatever its distance.</figcaption>
</figure>

Look at the near crates and the far ones: the faces pointing up and to the right are lit to
the same brightness regardless of distance. That uniformity is the signature of a
directional light, and it is why outdoor scenes use one for the sun.

## Point lights and attenuation

A bulb is somewhere. Light leaves it in every direction, so the direction toward it differs
at every point in the scene — which 2.2 already handled — and it **weakens with distance**,
which nothing so far has. That weakening is **attenuation**.

### Where the inverse square comes from

A bulb emits some fixed amount of energy per second. That energy spreads outward, and at
distance `d` all of it is crossing the surface of a sphere of radius `d`. A sphere's
surface area is:

```
   area = 4 π d²
```

The same total energy, divided by an area that grows with `d²`, gives energy per unit area
falling as `1/d²`:

```
                    d = 1              d = 2              d = 3

   source  •      ┌──────┐         ┌──────┬──────┐   ┌──────┬──────┬──────┐
                  │ 1/1  │         ├──────┼──────┤   ├──────┼──────┼──────┤
                  └──────┘         │      │      │   │      │      │      │
                                   └──────┴──────┘   ├──────┼──────┼──────┤
                area × 1           area × 4          └──────┴──────┴──────┘
                intensity 1        intensity 1/4     area × 9, intensity 1/9
```

That is the **inverse-square law**, and it is not a graphics convention — it is what
happens to anything radiating from a point into three dimensions.

### Why the sample does not use it

Pure inverse-square looks wrong in a renderer like this one. At `d < 1` it exceeds the
light's own output and blows out to white; at large `d` it dies off far faster than the eye
expects, because a real room is full of bounced light this renderer does not simulate. The
traditional compromise adds two more terms:

```
   intensity = 1 / (constant + linear·d + quadratic·d²)
```

```slang title="code/src/2.lighting/light_casters/light_casters.slang"
float3 offset = light.position.xyz - input.world_position;
float distance = length(offset);
to_light = offset / distance;
intensity = 1.0 / (light.constant_term + light.linear_term * distance +
                   light.quadratic_term * distance * distance);
```

Note that `to_light` is `offset / distance` rather than a second `normalize` call: the
length was needed anyway, so dividing by it normalises for free.

Each term earns its place:

- **constant**, kept at 1.0, stops the denominator dropping below 1. Without it, a surface
  half a unit from the light would receive many times more light than the light emits.
- **linear** controls the gentle falloff at short range.
- **quadratic** takes over at distance and brings the light down toward zero.

The sample uses `1.0`, `0.09` and `0.032`:

| Distance | 1 | 5 | 10 | 16 | 20 |
|---|---|---|---|---|---|
| Intensity | 0.89 | 0.44 | 0.20 | 0.09 | 0.06 |
| Pure `1/d²` | 1.00 | 0.04 | 0.01 | 0.004 | 0.003 |

The second row is why the compromise exists. At 5 units, true inverse-square leaves 4% of
the light and the scene goes black; the three-term version leaves 44%. Values like these
are usually taken from a table of distances rather than derived. The thing to understand is
the shape: a plateau near the light, then a long tail.

## Spotlights

A torch is a point light that only shines inside a cone. It has a position, it attenuates,
and it also has an **axis** and an **angle**.

The test for "inside the cone" is a dot product. The cosine of the angle between the
spotlight's axis and the ray from the light to this fragment is:

```slang title="code/src/2.lighting/light_casters/light_casters.slang"
float theta = dot(-to_light, normalize(light.direction.xyz));
```

Both arguments are unit vectors, so by the appendix's `a · b = |a||b| cos θ` this *is* the
cosine of the angle off the axis — 1.0 dead centre, shrinking as the fragment moves
outward. `-to_light` is used because `to_light` points from the fragment back at the torch,
and we want the ray going the same way the torch points.

A single cutoff gives a pool of light with a razor-sharp edge, which looks like a stage
effect rather than a torch. Two cutoffs give a soft one: full strength inside the **inner
cone**, nothing outside the **outer cone**, and a ramp between:

```slang title="code/src/2.lighting/light_casters/light_casters.slang"
float edge = light.inner_cutoff - light.outer_cutoff;
float cone = saturate((theta - light.outer_cutoff) / edge);
intensity = attenuation * cone;
```

That expression is an inverse lerp: it measures how far `theta` has travelled from the
outer cutoff toward the inner one, as a fraction, and `saturate` clamps it to `[0, 1]`.
With the sample's 12.5° and 17.5° **cone cutoff** angles:

| Angle off axis | 0° | 12.5° | 15° | 17.5° | 20° |
|---|---|---|---|---|---|
| `theta` (cosine) | 1.0000 | 0.9763 | 0.9659 | 0.9537 | 0.9397 |
| `cone` | 1.000 | 1.000 | 0.541 | 0.000 | 0.000 |

The whole soft edge lives in the 0.0226 of cosine between the two cutoffs. That is how
narrow the band is, and why `edge` must never be zero.

:::caution[Cosines run backwards]
The cutoffs are stored as cosines — computed once on the CPU, so the shader never calls
`acos` per fragment. Cosines *decrease* as angles grow, so the **inner** cutoff, the smaller
angle, is the **larger** number: `cos(12.5°) = 0.9763` against `cos(17.5°) = 0.9537`. The
subtraction `inner - outer` is positive for exactly that reason. Swap them and `edge` goes
negative and the cone turns inside out.
:::

The sample's torch is held by the camera: its position and direction are rebuilt from the
camera every frame, so the pool of light follows your gaze. In the screenshot at the top,
the soft edge is visible sweeping across the plank face of the crate to the left of centre.

## Ambient is not attenuated

One line deserves a comment:

```slang title="code/src/2.lighting/light_casters/light_casters.slang"
    return float4(ambient + intensity * (diffuse + specular), 1.0);
```

The intensity multiplies diffuse and specular, **not ambient**. The ambient term stands for
light that has bounced around the whole scene, and that light does not come from the torch's
direction or care how far away the torch is. It is why the crates outside the cone are dim
rather than invisible.

## The shader, assembled

The three cases live in one `switch`, and everything after it is 2.4's Phong code with a
single `intensity` threaded in:

```slang title="code/src/2.lighting/light_casters/light_casters.slang"
static const int kDirectional = 0;
static const int kPoint = 1;
```

```slang title="code/src/2.lighting/light_casters/light_casters.slang"
    Light light = globals.light;

    float3 to_light;
    float intensity = 1.0;
```

Copying `globals.light` into a local is readability, not necessity — it saves writing
`globals.light.` nine times below.

```slang title="code/src/2.lighting/light_casters/light_casters.slang"
    case kPoint: {
```

```slang title="code/src/2.lighting/light_casters/light_casters.slang"
    default: {
```

The spotlight is the `default` case rather than a named one, which keeps the compiler from
warning about an unhandled value: with a specialisation constant the switch has exactly one
reachable arm anyway.

```slang title="code/src/2.lighting/light_casters/light_casters.slang"
        float attenuation = 1.0 / (light.constant_term + light.linear_term * distance +
                                   light.quadratic_term * distance * distance);
```

And the three Phong terms, now reading the light's own components rather than 2.4's:

```slang title="code/src/2.lighting/light_casters/light_casters.slang"
    float3 ambient = light.ambient.rgb * surface;
```

```slang title="code/src/2.lighting/light_casters/light_casters.slang"
    float3 diffuse = light.diffuse.rgb * diffuse_amount * surface;
```

```slang title="code/src/2.lighting/light_casters/light_casters.slang"
    float3 specular = light.specular.rgb * specular_amount * shine;
```

## Choosing the kind: a specialisation constant

Which kind of light the scene uses does not change while the program runs. That makes it a
perfect fit for the mechanism chapter 1.9 introduced and has not used since:

```slang title="code/src/2.lighting/light_casters/light_casters.slang"
[[vk::constant_id(0)]] const int kLightType = 2;

switch (kLightType) {
case kDirectional: ...
case kPoint: ...
default: ...
}
```

The C++ side declares the same three values, and which one is in force:

```cpp title="code/src/2.lighting/light_casters/main.cpp"
enum class LightType : int32_t {
    directional = 0,
    point = 1,
    spot = 2,
};
constexpr LightType kLightType = LightType::spot;

struct ShaderConstants {
    int32_t light_type = static_cast<int32_t>(kLightType);
};
```

`int32_t` rather than plain `int`, because the size has to match what the shader declares
exactly — a specialisation constant is fed raw bytes.

```cpp title="code/src/2.lighting/light_casters/main.cpp"
        const ShaderConstants constants{};
        const std::array<VkSpecializationMapEntry, 1> entries{{
            {
                .constantID = 0,
                .offset = offsetof(ShaderConstants, light_type),
                .size = sizeof(ShaderConstants::light_type),
            },
        }};
```

The map entry says: constant id 0 is found at this offset in the blob, and is this many
bytes long. The blob itself is the `ShaderConstants` struct reinterpreted as bytes:

```cpp title="code/src/2.lighting/light_casters/main.cpp"
        object_pipeline_ =
            vkc::PipelineBuilder(device)
                .shaders(shader, "vertexMain", "fragmentMain")
                .vertex_input(std::span(&binding, 1), attributes)
                .fragment_specialisation(
                    entries, std::span(reinterpret_cast<const std::byte*>(&constants),
                                       sizeof(constants)))
                .cull(VK_CULL_MODE_BACK_BIT, VK_FRONT_FACE_COUNTER_CLOCKWISE)
                .depth(depth_format_, /*test=*/true, /*write=*/true, VK_COMPARE_OP_LESS)
                .colour_attachment(swapchain().format())
                .layout(pipeline_layout_)
                .build();
```

This is the first time a sample has not used the shared `build` lambda for both pipelines,
because only the object pipeline is specialised. The lamp pipeline still goes through it.

The value is fixed when the pipeline is created, so the `switch` compiles to a SPIR-V
`OpSwitch` on a constant — and a driver is free to fold that away and keep only the case
that will run. A uniform would work too, and would leave a genuine branch in every fragment
of every frame for a value that never changes.

The specialisation is attached only to the lit pipeline. The lamp pipeline is built from the
same module and needs none: its fragment entry point never reads `kLightType`.

## Building the light each frame

```cpp title="code/src/2.lighting/light_casters/main.cpp"
    [[nodiscard]] Light make_light() const {
        Light light{
            .position = {},
            .direction = {},
            .ambient = kLightAmbient,
            .diffuse = kLightDiffuse,
            .specular = kLightSpecular,
            .constant_term = kConstant,
            .linear_term = kLinear,
            .quadratic_term = kQuadratic,
            .inner_cutoff = std::cos(glm::radians(kInnerCutoffDegrees)),
            .outer_cutoff = std::cos(glm::radians(kOuterCutoffDegrees)),
            .padding = {},
        };
```

The two cosines are computed here, once per frame, rather than per fragment in the shader.
The fields a given kind does not use are left at zero and never read.

```cpp title="code/src/2.lighting/light_casters/main.cpp"
        case LightType::directional:
            light.direction = glm::vec4(glm::normalize(kSunDirection), 0.0F);
            break;
        case LightType::point:
            light.position = glm::vec4(kPointLightPosition, 1.0F);
            break;
        case LightType::spot:
            light.position = glm::vec4(camera_.position, 1.0F);
            light.direction = glm::vec4(camera_.front(), 0.0F);
            break;
        }
        return light;
    }
```

Note the `w` components: `1.0F` for a position, `0.0F` for a direction. That is 1.12's
homogeneous rule showing up in data rather than in a matrix multiply — and for the
spotlight, `camera_.front()` is the `vkc::Camera` accessor chapter 1.14 built.

```cpp title="code/src/2.lighting/light_casters/main.cpp"
    void update_globals(size_t slot, VkExtent2D extent) {
```

```cpp title="code/src/2.lighting/light_casters/main.cpp"
            .light = make_light(),
```

`update_globals` no longer takes a light position: the light builds itself. So the call in
`on_render` loses its third argument, which 2.4 needed:

## What changed since 2.4

- `Light` gained `direction`, three attenuation terms and two cone cutoffs (112 bytes)
- the light's kind is a specialisation constant on the lit pipeline
- three crates became ten, standing still, at 1.14's positions
- the spotlight is rebuilt from the camera each frame; the lamp is drawn only for a point light

## Running it

```bash
./code/out/build/linux-debug/bin/2.5.light_casters
```

Sweep the torch across the scene and watch the soft edge move over the crates; walk toward a
crate and see it brighten as the attenuation falls away. To see the other two kinds, change
`kLightType` in `main.cpp` to `LightType::point` or `LightType::directional` and rebuild.

## Words introduced in this chapter

| | |
|---|---|
| **directional light** | a light infinitely far away: one direction everywhere, no position, no falloff |
| **point light** | a light at a position, radiating in every direction and weakening with distance |
| **spotlight** | a point light restricted to a cone, with an axis, an angle and a soft edge |
| **attenuation** | the fall in intensity with distance; here `1/(c + l·d + q·d²)` |
| **inverse-square law** | energy from a point spread over a sphere of area `4πd²`, so intensity falls as `1/d²` |
| **cone cutoff** | the spotlight's half-angle, stored as a cosine so a dot product can be compared against it directly |
| **inner / outer cone** | the two cutoffs between which intensity ramps from full to nothing, giving a soft edge |

## Exercises

1. Make the cone's edge hard. Replace the `saturate(...)` line with
   `float cone = step(light.outer_cutoff, theta);` — since shaders are compiled when the sample
   starts, you can edit the copy in `bin/shaders/2.5.light_casters/` and just run again. The pool of light keeps its size and its falloff with distance, but its edge becomes a sharp line — clearest across the planks of the crate to the left of centre, where the soft gradient collapses to a single hard boundary. That is the difference one `saturate` makes.
2. Widen the torch to 25° inner and 35° outer, then narrow it to 5° and 7°. Notice that the
   narrow beam reaches just as far: the cone limits *where* light goes, attenuation limits *how
   far*.
3. Set the quadratic term to `0.0` and the linear term to `0.0` for the point light. The light
   no longer weakens at all, and the scene looks like it is lit by something much larger than a
   bulb. Then try quadratic `0.2`, and find the distance at which the light effectively ends.
4. Scale the ambient term by `intensity` too, and look at the crates outside the cone. Decide
   whether that is more realistic or less — and what it would take to do ambient properly
   (Part 6 answers that).
5. Replace the specialisation constant with a field in `Globals` and switch the light type at
   run time with a key press. It works. Now think about what the shader is doing on every
   fragment that it was not doing before.
6. Use true inverse-square: constant `0`, linear `0`, quadratic `1`. Stand a unit from a crate
   and then back away. The near face blows out to white and the far crates vanish — both
   halves of why the three-term compromise exists, in one change.
