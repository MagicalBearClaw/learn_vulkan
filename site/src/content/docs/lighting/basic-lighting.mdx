Chapter 2.1 ended on a cube that was the right colour and the wrong shape. Every face came
out identical, because nothing in the shader knew which way a face points or where the
light is.

This chapter supplies both, and the scene above is the result — rendered from exactly the
same camera, at exactly the same frame, as 2.1's screenshot. Nothing moved. The only
difference is the arithmetic in the fragment shader.

## The model

Real light bounces around a scene indefinitely, and computing that exactly is out of
reach for anything interactive. The **Phong reflection model** is an approximation that
splits the light reaching the eye from a point into three terms, each cheap on its own and
each standing in for a different physical effect:

| Term | Stands in for | Depends on |
|---|---|---|
| **Ambient** | Light that has bounced so many times it arrives from everywhere | nothing |
| **Diffuse** | Light scattered equally in all directions by a matte surface | the light's direction |
| **Specular** | Light reflected mirror-fashion into a highlight | the light's direction *and* the eye's |

Add the three together and multiply by the object's colour — the same multiply as 2.1,
which was right all along. What 2.1 was missing was *how much* light reaches each point.

Phong is not physically based, and Part 6 replaces it. It is still worth learning
properly, because the vocabulary — normals, light vectors, view vectors, `N · L` — carries
straight across, and because most of the reasoning about *why* each term looks the way it
does survives the upgrade.

## Normals

Everything here needs to know which way a surface faces. That is its **normal**: a unit
vector perpendicular to the surface, pointing outward.

A normal is a property of a vertex, like a position, so the vertex gains an attribute:

```cpp title="code/src/2.lighting/basic_lighting/main.cpp"
struct Vertex {
    glm::vec3 position;
    glm::vec3 normal;
};
```

This finally explains why the cube has been 24 vertices since chapter 1.13 rather than 8.
A corner of a cube belongs to three faces pointing three different ways. It needs three
normals, a vertex is the whole bundle of attributes, so it needs three vertices. A mesh
with hard edges always duplicates its vertices along them.

Each face's four corners now carry the direction that face points:

```cpp title="code/src/2.lighting/basic_lighting/main.cpp"
constexpr float kH = 0.5F;
constexpr std::array<Vertex, 24> kVertices{{
    // front (+z)
    {{-kH, -kH, kH}, {0, 0, 1}}, {{kH, -kH, kH}, {0, 0, 1}},
    {{kH, kH, kH}, {0, 0, 1}},   {{-kH, kH, kH}, {0, 0, 1}},
    // back (-z)
    {{kH, -kH, -kH}, {0, 0, -1}}, {{-kH, -kH, -kH}, {0, 0, -1}},
    {{-kH, kH, -kH}, {0, 0, -1}}, {{kH, kH, -kH}, {0, 0, -1}},
    // left (-x)
    {{-kH, -kH, -kH}, {-1, 0, 0}}, {{-kH, -kH, kH}, {-1, 0, 0}},
    {{-kH, kH, kH}, {-1, 0, 0}},   {{-kH, kH, -kH}, {-1, 0, 0}},
    // right (+x)
    {{kH, -kH, kH}, {1, 0, 0}},  {{kH, -kH, -kH}, {1, 0, 0}},
    {{kH, kH, -kH}, {1, 0, 0}},  {{kH, kH, kH}, {1, 0, 0}},
    // top (+y)
    {{-kH, kH, kH}, {0, 1, 0}},  {{kH, kH, kH}, {0, 1, 0}},
    {{kH, kH, -kH}, {0, 1, 0}},  {{-kH, kH, -kH}, {0, 1, 0}},
    // bottom (-y)
    {{-kH, -kH, -kH}, {0, -1, 0}}, {{kH, -kH, -kH}, {0, -1, 0}},
    {{kH, -kH, kH}, {0, -1, 0}},   {{-kH, -kH, kH}, {0, -1, 0}},
}};
```

The normals are exact axis directions because a cube's faces are axis-aligned in model
space. The indices are unchanged from 2.1 and 1.13, and so is the winding.

On the Vulkan side this is one more `VkVertexInputAttributeDescription` at location 1, and
one more field in the shader's input struct. Nothing new.

## Everything in one space

Before any lighting arithmetic: every vector in a dot product has to be in the same
coordinate space, or the answer means nothing.

A coordinate space is just a choice of origin and axes, and 1.13 already built three of
them. **World space** is the shared space the whole scene lives in, after the model matrix
and before the view matrix. **View space** is what the view matrix produces: the same
scene expressed with the camera at the origin.

This sample does its lighting in world space. The light's position is in world space
already, the camera's position is in world space already, so the vertex stage hands the
fragment stage a world-space position and a world-space normal:

```slang title="code/src/2.lighting/basic_lighting/lighting.slang"
struct VSInput {
    [[vk::location(0)]] float3 position;
    [[vk::location(1)]] float3 normal;
};

struct VSOutput {
    float4 position : SV_Position;
    [[vk::location(0)]] float3 world_position;
    [[vk::location(1)]] float3 normal;
};
```

View space is an equally valid choice — the camera sits at the origin there, which makes
the eye vector trivial. What is not valid is mixing them, and a world-space light position
against a view-space normal is one of the most common lighting bugs there is.

The per-frame block gains the two positions the model needs:

```slang title="code/src/2.lighting/basic_lighting/lighting.slang"
struct Globals {
    float4x4 view;
    float4x4 projection;
    float4 light_colour;
    float4 light_position;  // xyz; w unused
    float4 view_position;   // xyz; w unused
};
[[vk::binding(0, 0)]] ConstantBuffer<Globals> globals;
```

Both are `float4` rather than `float3`. A `float3` would work — std140 aligns it to 16
bytes and the next member would land in the same place — but only by a rule you have to
remember, and the unused `w` costs nothing.

## The normal matrix

The position is transformed by the model matrix. The normal is **not**. This is the one
piece of real mathematics in the chapter, and it is worth deriving rather than quoting.

### Why the model matrix is wrong

Picture a surface tilted at 45° and stretch the object to twice its width. The surface
flattens out — so its normal has to tilt *toward* vertical. Apply the stretch to the
normal itself and it tilts the other way, becoming less vertical as the surface becomes
more so:

```
   before:  surface at 45°          after a 2x stretch along x:

      n                                  n_correct
       ↖  ╱                                 ↑   ____
        ╲╱                                  │ ╱        the surface flattened,
        ╱                                   │╱         so its normal stands up

                                       n_wrong = M·n
                                            ↗  leans further over instead
```

Positions and normals respond **oppositely** to a stretch, so whatever matrix transforms
normals, it is not `M`.

### Deriving the right one

The property that defines a normal is perpendicularity: `n` is perpendicular to every
tangent `t` lying in the surface. Written as a dot product, which is the appendix's
`a · b = |a||b|cos θ` at θ = 90°:

```
   n · t = 0        for every tangent t in the surface
```

After the transform, the tangent is a difference of two transformed positions, so it
genuinely does transform by `M`: the new tangent is `M·t`. Call the unknown normal matrix
`G`. We need the transformed normal to stay perpendicular to the transformed tangent:

```
   (G·n) · (M·t) = 0        for every tangent t
```

Write a dot product as a row times a column — `a · b = aᵀb` — and the left side becomes:

```
   (G·n)ᵀ (M·t)  =  nᵀ Gᵀ M t
```

We know `nᵀt = 0` and want `nᵀGᵀMt = 0` for *every* tangent `t`. The way to guarantee
that is for `GᵀM` to be the identity, which leaves `nᵀt` unchanged:

```
   Gᵀ M = I        →        Gᵀ = M⁻¹        →        G = (M⁻¹)ᵀ
```

The **inverse transpose** of the model matrix's upper 3×3. That is the whole derivation,
and it explains the shape of the answer: the inverse undoes what the stretch did, and the
transpose puts the result back in the right orientation to multiply a normal.

Only the upper 3×3 is used, because a normal is a direction and has no business being
translated — the `w = 0` rule from 1.12 saying the same thing a different way.

:::note[Checked, not assumed]
Take a surface with two tangents, transform everything by `M`, and measure
`(G·n) · (M·t)` — which should be zero if the derivation is right:

| `M` | with `G = (M⁻¹)ᵀ` | with the naive `M·n` |
|---|---|---|
| non-uniform scale | 5.6 × 10⁻¹⁷ | 1.125 |
| pure rotation | 4.8 × 10⁻¹⁶ | 0.000 |
| rotate × scale | 1.1 × 10⁻¹⁶ | 0.626 |
| scale × rotate | 6.2 × 10⁻¹⁵ | 3.226 |

The inverse transpose is perpendicular to machine precision in every case. The naive
version is perpendicular only for the pure rotation — which is the next point.
:::

### When it does not matter

For a **pure rotation**, the inverse transpose *is* the rotation. Rotation matrices are
orthonormal, which by the appendix's `R⁻¹ = Rᵀ` gives `(R⁻¹)ᵀ = (Rᵀ)ᵀ = R`. Inverting and
transposing cancel exactly, and the check above confirms it.

For a **uniform scale** by `s`, the inverse transpose is `(1/s)·I` — a different length
but the same direction, and normals get renormalised anyway.

So the normal matrix only differs from the model matrix when there is a **non-uniform**
scale, and less often even then than you might expect; exercise 3 shows exactly when.

### Computing it

This sample computes it on the CPU:

```cpp title="code/src/2.lighting/basic_lighting/main.cpp"
[[nodiscard]] std::array<glm::vec4, 3> normal_matrix_of(const glm::mat4& model) {
    const glm::mat3 m = glm::inverseTranspose(glm::mat3(model));
    return {glm::vec4(m[0], 0.0F), glm::vec4(m[1], 0.0F), glm::vec4(m[2], 0.0F)};
}
```

`glm::mat3(model)` takes the upper 3×3 by dropping the fourth row and column.
`m[0]`, `m[1]`, `m[2]` are its three columns — glm indexes column first, as 1.12
established — and each is widened to a `vec4`. Why three `vec4`s rather than a `glm::mat3`
is the trap below.

It is computed once per object rather than once per vertex, which would be the right call
anyway. But there is a second reason, worth knowing if you are coming from GLSL:

:::caution[Slang has no `inverse()`]
GLSL has a built-in `inverse()`, and a lot of tutorial code computes the normal matrix in
the vertex shader with it. Slang does not — try it and you get
`error[E30015]: undefined identifier 'inverse'`. Code ported from GLSL that inverts
matrices in a shader has to move that work to the CPU, which is where it belonged.
:::

The vertex stage therefore just applies it:

```slang title="code/src/2.lighting/basic_lighting/lighting.slang"
[shader("vertex")]
VSOutput vertexMain(VSInput input) {
    VSOutput output;

    float4 world = mul(push.model, float4(input.position, 1.0));
    output.world_position = world.xyz;
    output.position = mul(globals.projection, mul(globals.view, world));

    output.normal = mul(push.normal_matrix, input.normal);
    return output;
}
```

The normal is renormalised in the fragment shader, not here. Interpolating between unit
vectors produces vectors shorter than unit length — the interpolated value lands on the
straight line between two points on the unit sphere, which passes inside it — and every
term below assumes unit vectors.

## Ambient

```slang title="code/src/2.lighting/basic_lighting/lighting.slang"
    float3 normal = normalize(input.normal);
    float3 to_light = normalize(globals.light_position.xyz - input.world_position);

    const float kAmbientStrength = 0.1;
    float3 ambient = kAmbientStrength * globals.light_colour.rgb;
```

A constant. It is a crude stand-in for indirect light, and its job is modest: stop the
faces turned away from the lamp going pure black, which no real surface does. In the
screenshot it is what you are seeing on the left-hand face.

`to_light` is the unit vector **from the fragment toward the light** — subtract the
fragment's position from the light's, then normalise. Getting the subtraction the wrong
way round points it at the floor and is a classic silent bug.

## Diffuse

```slang title="code/src/2.lighting/basic_lighting/lighting.slang"
    float diffuse_amount = max(dot(normal, to_light), 0.0);
    float3 diffuse = diffuse_amount * globals.light_colour.rgb;
```

This is **Lambert's cosine law**, and it is the term doing almost all the work in the
screenshot.

A beam of light of fixed width lands on a patch of surface. Facing the beam squarely, the
patch catches all of it. Tilted by θ, the same beam spreads over a larger patch:

```
   beam of width w, surface facing it:      beam of width w, surface tilted by θ:

     │ │ │ │  light                           │ │ │ │
     ▼ ▼ ▼ ▼                                  ▼ ▼ ▼ ▼
   ──────────  area = w                     ╱──────────╱  area = w / cos θ
      n ↑                                  ╱  n ↗     ╱
                                          ╱          ╱

   energy per unit area = 1               energy per unit area = cos θ
```

The same energy spread over `w / cos θ` of surface gives `cos θ` as much per unit area.
And for two unit vectors, the appendix's `a · b = |a||b| cos θ` collapses to
`a · b = cos θ` — the cosine we want *is* the dot product, with no trigonometry called at
all.

The `max` matters. A negative dot product means θ exceeds 90°, so the surface faces away
from the light, and the right amount of light for that is zero, not negative. Leave it out
and faces turned away from the lamp subtract the ambient term and go blacker than black —
which, after clamping, is just black, and a silent loss of the ambient floor.

## Specular

```slang title="code/src/2.lighting/basic_lighting/lighting.slang"
    const float kSpecularStrength = 0.5;
    const float kShininess = 32.0;
    float3 to_eye = normalize(globals.view_position.xyz - input.world_position);
    float3 reflected = reflect(-to_light, normal);
    float specular_amount = pow(max(dot(to_eye, reflected), 0.0), kShininess);
    float3 specular = kSpecularStrength * specular_amount * globals.light_colour.rgb;
```

The highlight. Reflect the incoming light about the normal as if the surface were a
mirror, then ask how closely that **reflection vector** points at the eye. Dead on, the
highlight is at full strength; the further off, the dimmer.

The reflection itself is worth seeing written out. For a unit normal `n`, an incoming
direction `d` splits into a part along the normal and a part in the surface, and reflecting
flips only the first:

```
   reflect(d, n)  =  d - 2 (d · n) n
```

`(d · n) n` is the component of `d` along the normal; subtracting it once removes that
component, subtracting it twice sends it out the other side. Slang's `reflect` is exactly
this.

`reflect` wants the direction the light is *travelling*, which is from the light toward
the surface — the opposite of `to_light`, hence the negation. Forget it and the highlight
turns up on the wrong side of the object: in this scene, the face turned *away* from the
lamp starts to glow.

The exponent is the surface's **shininess**. A dot product falls off gently; raised to the
32nd power it falls off steeply, and the highlight tightens into a small bright spot:

```
   cos θ           at θ = 0    0.5    1.0    (radians)
   cos θ           1.000     0.878  0.540
   (cos θ)^2       1.000     0.771  0.292
   (cos θ)^32      1.000     0.017  0.0000019
```

Higher is glossier. 2.3 makes this a property of the material rather than a constant.

This is the only term that depends on where the camera is, which is why `view_position`
joined the per-frame block. It is also the physical difference between matte and shiny:
a matte surface looks the same from every angle because it has no specular, and a shiny
one does not.

## The three together

```slang title="code/src/2.lighting/basic_lighting/lighting.slang"
    float3 result = (ambient + diffuse + specular) * push.object_colour.rgb;
    return float4(result, 1.0);
```

The three terms add up to the light arriving at the eye from this point, and the object's
colour multiplies it exactly as in 2.1. The multiply was right; what was missing was how
much light actually reaches each fragment.

The lamp's fragment stage is untouched from 2.1 — it still draws at the light's own
colour, and it still ignores the whole model.

## The layout trap: a 3×3 matrix is 48 bytes

Here is this chapter's Vulkan lesson, and it is a sharp one.

The push constants now hold the model matrix, the normal matrix and the object colour:

```slang title="code/src/2.lighting/basic_lighting/lighting.slang"
struct PushConstants {
    float4x4 model;
    float3x3 normal_matrix;
    float4 object_colour;
};
[[vk::push_constant]] PushConstants push;
```

The natural C++ counterpart would use `glm::mat3`. **Do not.** Look at what the compiler
actually lays out, with the `slangc` trick from chapter 1.9:

```
OpMemberDecorate %PushConstants_std430 0 Offset 0
OpMemberDecorate %PushConstants_std430 1 Offset 64
OpMemberDecorate %PushConstants_std430 1 MatrixStride 16
OpMemberDecorate %PushConstants_std430 2 Offset 112
```

`MatrixStride 16` is the **matrix stride**: the distance in bytes from the start of one
column to the start of the next. Each column of a 3×3 matrix is a three-component vector,
and the layout rules align three-component vectors to 16 bytes — so the matrix takes
3 × 16 = 48 bytes, and `object_colour` starts at 112. A `glm::mat3` packs its columns into
12 bytes each, 36 in all:

```
   the shader's float3x3, stride 16:     glm::mat3, stride 12:

   0    col 0   xyz _                    0    col 0   xyz
   16   col 1   xyz _                    12   col 1   xyz
   32   col 2   xyz _                    24   col 2   xyz
   48   ends                             36   ends
```

Send a `glm::mat3` and the second column arrives 4 bytes early, the third 8 bytes early.
Try it: the lighting changes visibly, and nothing — not the compiler, not the driver, not
the validation layers — says a word. It is exactly the `std140` trap from chapter 1.10,
wearing a matrix.

So the C++ side spells out the padding:

```cpp title="code/src/2.lighting/basic_lighting/main.cpp"
struct PushConstants {
    glm::mat4 model;                           // offset 0
    std::array<glm::vec4, 3> normal_matrix;    // offset 64, one column each
    glm::vec4 object_colour;                   // offset 112
};
static_assert(offsetof(PushConstants, normal_matrix) == 64);
static_assert(offsetof(PushConstants, object_colour) == 112);
static_assert(sizeof(PushConstants) == 128);
```

Three `glm::vec4`s are 16 bytes each by construction, which is exactly the stride the
shader expects — the padding is no longer something to remember, it is the type.

The `static_assert`s are the habit 1.10 recommended, and here they earn their keep twice
over. They pin the layout, and the last one records that this struct is now **exactly**
128 bytes — the push constant size every Vulkan device guarantees. There is no room left.
The next thing per-object data needs has to go somewhere else, and that is where chapter
2.3 begins.

:::tip[When in doubt, ask the SPIR-V]
The offsets above came from disassembling the compiled shader, not from memorising layout
rules. That is the reliable way to settle a layout question: the compiler's answer is the
one the GPU will use.
:::

## The sample

Everything else is 2.1's file with the new data threaded through it. Two includes appear:

```cpp title="code/src/2.lighting/basic_lighting/main.cpp"
#include <glm/gtc/matrix_inverse.hpp>
#include <cmath>
```

`matrix_inverse.hpp` is where `glm::inverseTranspose` lives; `<cmath>` is for the `std::sin`
and `std::cos` of the lamp's orbit.

The per-frame block gains its two positions on the C++ side, matching the shader field for
field:

```cpp title="code/src/2.lighting/basic_lighting/main.cpp"
struct Globals {
    glm::mat4 view;            // offset 0
    glm::mat4 projection;      // offset 64
    glm::vec4 light_colour;    // offset 128
    glm::vec4 light_position;  // offset 144
    glm::vec4 view_position;   // offset 160
};
static_assert(sizeof(Globals) == 176);
```

Every offset is a multiple of 16 without any padding being inserted, because each member
is either a `mat4` (64 bytes) or a `vec4` (16). 176 bytes in total.

The class, and the one changed call in the frame:

```cpp title="code/src/2.lighting/basic_lighting/main.cpp"

```

## What changed since 2.1

- `Vertex` gained a `normal`, and the cube's 24 vertices each carry one
- `Globals` gained `light_position` and `view_position` (176 bytes)
- `PushConstants` gained `normal_matrix`, reaching the 128-byte limit
- the lit fragment entry point computes ambient, diffuse and specular
- the lamp, the pipelines, the descriptor set and the camera are unchanged

## Words introduced in this chapter

| | |
|---|---|
| **Phong reflection model** | the three-term approximation — ambient plus diffuse plus specular — that this chapter implements |
| **normal** | a unit vector perpendicular to a surface, pointing outward; what tells a fragment which way it faces |
| **ambient** | a constant floor standing in for light that has bounced too many times to trace |
| **diffuse** | light scattered equally in all directions by a matte surface; depends on the light's direction only |
| **specular** | the mirror-like highlight; the only term that depends on where the eye is |
| **Lambert's cosine law** | a tilted surface catches a beam over a larger area, so brightness falls with `cos θ` — which for unit vectors is the dot product |
| **normal matrix** | the matrix that transforms normals correctly, `(M⁻¹)ᵀ` of the model matrix's upper 3×3 |
| **inverse transpose** | inverting then transposing; for an orthonormal matrix the two cancel and it changes nothing |
| **reflection vector** | `d - 2(d · n)n`, the incoming direction mirrored about the normal |
| **shininess** | the specular exponent; higher values tighten the highlight and read as glossier |
| **world space** | the shared space the scene lives in after the model matrix; where this sample does its lighting |
| **view space** | the same scene with the camera at the origin; an equally valid choice, but never mix the two |
| **matrix stride** | the byte distance between one column of a shader matrix and the next — 16 for a `float3x3`, not 12 |

## Exercises

1. Set `kAmbientStrength` to `0.0`, then to `0.5`. At zero, the faces turned away from the
   lamp go pure black — darker than the background behind them, which no real object
   does. At a half, the scene looks washed out and flat again — too much ambient is 2.1
   creeping back.
2. Change `kShininess` to `4` and to `256`. Then set `kSpecularStrength` to `0` and fly
   around: the cube's appearance stops depending on where you are.
3. See when the normal matrix matters. Replace `push.normal_matrix` in the vertex shader
   with `(float3x3)push.model` — the model matrix itself.

   First, scale the lit cube *before* rotating it:
   `glm::rotate(...) * glm::scale(glm::mat4(1.0F), glm::vec3(1.8F, 0.6F, 1.0F))`. The
   picture is **identical** to the correct version, to the pixel. On a box, every normal
   lies along a scaled axis, and scaling a vector along its own axis only changes its
   length, which normalisation removes.

   Now scale *after* rotating:
   `glm::scale(glm::mat4(1.0F), glm::vec3(1.8F, 0.6F, 1.0F)) * glm::rotate(...)`. Now the
   stretch is not along the box's own axes, the normals genuinely tilt the wrong way, and
   the shading changes: the front face comes out brighter and its gradient runs the wrong
   way. Put the normal matrix back and compare. It is a subtle difference on a box — on a
   sphere or a character it is glaring.
4. Do the layout trap on purpose. Change `normal_matrix_of` to `memcpy` a `glm::mat3`
   straight into the array. Run it and confirm the validation layers stay silent, then
   delete the `static_assert`s and note that nothing would have caught this but your eye.
5. Move the lighting into view space. Transform the normal by the view matrix as well,
   bring the light position into view space on the CPU, and replace `view_position` with
   the origin. The picture should not change at all — which is how you know you did it
   right.
6. Drop the `normalize` on `input.normal` in the fragment shader and look closely at the
   middle of a large lit face. The interpolated normals are shorter than unit length
   there, so the diffuse term comes out slightly too dark — a gradient that should not
   exist on a flat face.
