Every chapter since 1.7 changed the picture by changing what a shader computed. This one
does not. Its fragment shaders are the shortest in the series so far — one lit surface,
one flat colour — and the orange ring around each crate is not drawn by either of them.

What changes the picture here is the state the fragments meet *after* the fragment shader
has finished: the depth test, and the stencil test sitting next to it in the same struct.

Part 4 is about that tail end of the pipeline — the fixed-function stages that every
chapter so far has configured once, in 1.13, and never questioned. This chapter takes the
depth test apart, works out how much precision it actually has (the answer is "a great
deal near your face and almost none at the far plane", and the derivation says by exactly
how much), and then adds the stencil test, which no chapter has touched at all.

## What this chapter builds

Two crates on a tiled floor. A painted slab lying in *exactly* the floor's plane, which is
the setup for depth bias. An orange outline around each crate, which is the stencil test's
job and is not geometry anybody modelled.

Two keys make the failure modes visible rather than described: <kbd>1</kbd> turns the
outlines off, <kbd>2</kbd> turns the slab's depth bias off.

## The two blocks of data, unchanged from Part 2

`Globals` is 2.2's with the light list collapsed to one sun, and the shininess riding in
the ambient vector's unused `w` rather than costing another 16 bytes:

```cpp title="code/src/4.advanced_vulkan/depth_and_stencil/main.cpp"
struct Globals {
    glm::mat4 view;           // 0
    glm::mat4 projection;     // 64
    glm::vec4 view_position;  // 128
    glm::vec4 sun_direction;  // 144
    glm::vec4 sun_colour;     // 160
    glm::vec4 ambient;        // 176, w is the specular exponent
};
static_assert(offsetof(Globals, ambient) == 176);
static_assert(sizeof(Globals) == 192);
```

The offsets in the comments and the `static_assert`s below them are 1.10's std140 discipline:
the shader's idea of this struct and the C++ one have to agree byte for byte, and only one
of the two can be checked by a compiler. Check that one.

The push block is 2.6's, still exactly the 128 bytes Vulkan guarantees every implementation
provides:

```cpp title="code/src/4.advanced_vulkan/depth_and_stencil/main.cpp"
// 2.6's push block, unchanged and still exactly the 128 bytes Vulkan guarantees.
struct PushConstants {
    glm::mat4 model;                         // 0
    std::array<glm::vec4, 3> normal_matrix;  // 64
    glm::vec4 colour;                        // 112
};
static_assert(offsetof(PushConstants, colour) == 112);
static_assert(sizeof(PushConstants) == 128);

[[nodiscard]] std::array<glm::vec4, 3> normal_matrix_of(const glm::mat4& model) {
    const glm::mat3 m = glm::inverseTranspose(glm::mat3(model));
    return {glm::vec4(m[0], 0.0F), glm::vec4(m[1], 0.0F), glm::vec4(m[2], 0.0F)};
}
```

`normal_matrix` is three `vec4` rather than a `glm::mat3` for 2.2's reason: a `float3x3` in
a shader has a 16-byte column stride, so its three columns occupy 48 bytes, not 36, and
padding each one to a `vec4` is what makes the C++ side match. `colour` is new in this
chapter — the outline and the slab are flat colours, and putting the colour in the push
block means neither needs a descriptor.

## The shader, which has nothing to do with the chapter

This is worth stating plainly because it inverts everything Part 2 taught:

```slang title="code/src/4.advanced_vulkan/depth_and_stencil/depth_and_stencil.slang"

//
// This chapter's subject is not in here. Every visible effect it demonstrates -- what
// survives the depth test, which fragments the stencil test lets through, how far a
// polygon is pushed before it is compared -- is decided by pipeline state on the CPU
// side, after the fragment shader has already run.
//
// That is worth saying out loud, because it is the opposite of how the lighting
// chapters worked. There, changing the picture meant changing the shader. Here the
// shader is a constant and the picture changes anyway.

struct VSInput {
    [[vk::location(0)]] float3 position;
    [[vk::location(1)]] float3 normal;
    [[vk::location(2)]] float2 uv;
};

struct VSOutput {
    float4 position : SV_Position;
    [[vk::location(0)]] float3 world_position;
    [[vk::location(1)]] float3 normal;
    [[vk::location(2)]] float2 uv;
};
```

The two interface blocks, then the two descriptor sets — set 0 per frame, set 1 per
material, which is 2.3's split:

```slang title="code/src/4.advanced_vulkan/depth_and_stencil/depth_and_stencil.slang"
// Set 0, per frame. One sun and an ambient term: this chapter has no lighting to teach,
// and a scene needs just enough shading for the shapes to read.
struct Globals {
    float4x4 view;
    float4x4 projection;
    float4 view_position;
    float4 sun_direction;
    float4 sun_colour;
    float4 ambient;  // rgb ambient, w shininess
};
[[vk::binding(0, 0)]] ConstantBuffer<Globals> globals;

// Set 1, per material. One texture, because one is all that changes between the crate
// and the floor.
[[vk::binding(0, 1)]] Sampler2D base_colour_map;

struct PushConstants {
    float4x4 model;
    float3x3 normal_matrix;
    float4 colour;
};
[[vk::push_constant]] PushConstants push;

static const float kSpecularStrength = 0.2;
```

The vertex stage is 2.2's, and the only thing in the file that runs for every pipeline in
the chapter:

```slang title="code/src/4.advanced_vulkan/depth_and_stencil/depth_and_stencil.slang"
[shader("vertex")]
VSOutput vertexMain(VSInput input) {
    VSOutput output;
    float4 world = mul(push.model, float4(input.position, 1.0));
    output.world_position = world.xyz;
    output.position = mul(globals.projection, mul(globals.view, world));
    output.normal = mul(push.normal_matrix, input.normal);
    output.uv = input.uv;
    return output;
}
```

`mul(M, v)` and never `M * v`: Slang's `*` is component-wise, and the transform you want
is the matrix product. The projection is applied last because with column vectors the
matrix nearest the vector acts first, which 3.3 derived for node hierarchies and which is
the same rule here.

Then the lit surface — floor and crates:

```slang title="code/src/4.advanced_vulkan/depth_and_stencil/depth_and_stencil.slang"
// The textured, lit surfaces: the floor and the two crates. `push.colour` tints it,
// and is white everywhere in this chapter.
[shader("fragment")]
float4 fragmentMain(VSOutput input) : SV_Target {
    float3 albedo = base_colour_map.Sample(input.uv).rgb * push.colour.rgb;

    float3 normal = normalize(input.normal);
    float3 to_eye = normalize(globals.view_position.xyz - input.world_position);
    float3 to_sun = normalize(-globals.sun_direction.xyz);

    float diffuse_amount = max(dot(normal, to_sun), 0.0);
    float3 diffuse = globals.sun_colour.rgb * diffuse_amount * albedo;

    float3 reflected = reflect(-to_sun, normal);
    float specular_amount = pow(max(dot(to_eye, reflected), 0.0), globals.ambient.w);
    float3 specular = globals.sun_colour.rgb * specular_amount * kSpecularStrength;

    return float4(globals.ambient.rgb * albedo + diffuse + specular, 1.0);
}
```

Phong, exactly as 2.2 derived it: `max(dot(n, l), 0)` is Lambert's cosine law, and the
`pow(..., shininess)` term is the specular lobe. Nothing here is new, and nothing here is
what the chapter is about.

And the one that is almost empty:

```slang title="code/src/4.advanced_vulkan/depth_and_stencil/depth_and_stencil.slang"
// The decal and the outline. Both are flat colour, and neither is lit: a decal painted
// on the floor takes the floor's light, and an outline is not a surface at all.
//
```

## How much precision does the depth buffer actually have?

1.13 named *hyperbolic depth* and moved on, because nothing in Part 1 or Part 2 ever had two
surfaces close enough to care. This chapter has two surfaces in the *same plane*, so this is
where the distribution has to be worked out rather than named.

Start from the projection matrix 1.13 built. With `GLM_FORCE_DEPTH_ZERO_TO_ONE` set
project-wide, `glm::perspective` produces a right-handed matrix whose third column and
fourth row are:

```
   z_clip  =  ( f / (n − f) ) · z_eye  −  f·n / (f − n)
   w_clip  =  − z_eye
```

The camera looks down −z, so a point in front of it has negative `z_eye`. Write `d = −z_eye`
for the distance in front of the camera, which is a positive number, and both lines simplify:

```
   z_clip  =  f·(d − n) / (f − n)
   w_clip  =  d
```

The perspective divide — which is where the word *hyperbolic* comes from, because the divide
is by `d` — gives the window-space depth that actually reaches the depth test:

```
              f       (       n )
   z_w  =  ─────── · ( 1  −  ─── )
            f − n     (       d )
```

Sanity-check the two ends. At `d = n` the bracket is zero, so `z_w = 0`. At `d = f` the
bracket is `1 − n/f`, and `(f/(f−n))·(1 − n/f) = (f − n)/(f − n) = 1`. The near plane maps
to 0 and the far plane to 1, which is Vulkan's convention and the reason for the
`GLM_FORCE_DEPTH_ZERO_TO_ONE` define.

**Now the part that matters.** Differentiate with respect to `d`:

```
   d z_w         f        n
   ─────  =  ───────  ·  ───
    d d       f − n      d²
```

The rate at which stored depth changes with real distance falls off as `1/d²`. Invert it to
get the question a z-fighting bug actually asks — *how far apart do two surfaces have to be
before the depth buffer can tell them apart?*

```
                     (f − n) · d²
   Δd  =  Δz_w  ·  ───────────────
                        f · n
```

With this chapter's near and far — `glm::perspective(radians(45), aspect, 0.1F, 100.0F)` —
the constant `(f − n)/(f·n)` is `99.9/10 = 9.99` per square metre, and `Δd` grows with the
*square* of the distance. Taking `Δz_w = 2⁻²⁴`, which is what both of the formats this
chapter can choose from resolve near the far plane:

| distance `d` | `z_w` | smallest distinguishable `Δd` |
|---|---|---|
| 0.5 m | 0.800801 | 0.15 µm |
| 1 m | 0.900901 | 0.60 µm |
| 5 m | 0.980981 | 14.9 µm |
| 10 m | 0.990991 | 59.5 µm |
| 50 m | 0.998999 | **1.49 mm** |

A factor of 50 in distance costs a factor of 2 500 in precision, and that 2 500 is exactly
`50²`. The same fact said the other way round is more alarming:

- `z_w` reaches **0.5** at `d = 0.1998 m`. Half of every value the depth buffer can hold is
  spent on the first ten centimetres of the frustum.
- It reaches **0.9** at `d = 0.99 m` and **0.99** at `d = 9.1 m`.
- Everything from 9 metres to 100 metres shares the last 1% of the range.

So z-fighting at distance is not bad luck. It is the near plane's fault, and the single most
effective fix for it is to push `n` out: the `(f − n)/(f·n)` factor is dominated by `n`, and
moving the near plane from 0.1 to 1.0 takes it from 9.99 to 0.99, dividing every entry in that
table by 10.1.

:::note[Why a float depth buffer does not rescue this]
This machine picks `VK_FORMAT_D32_SFLOAT_S8_UINT`, so depth is a 32-bit float rather than a
24-bit fixed-point value, and it is tempting to assume that buys precision. It does not,
where you need it.

A `float` has its finest spacing near zero, and the hyperbolic mapping puts `z_w` near zero
at the *near* plane — where `Δd` was already 0.15 µm. Near the far plane `z_w` sits just
under 1.0, where a 32-bit float's step is `2⁻²⁴ = 5.96 × 10⁻⁸` — which is, to three
significant figures, exactly what a 24-bit `UNORM` gives (`1/(2²⁴−1)`). Every extra exponent
bit has been spent at the end that did not need them.

That is the whole argument for **reversed-Z**: swap the near and far mappings so the far
plane lands at 0, clear the buffer to 0 and compare with `VK_COMPARE_OP_GREATER`. The
distribution is unchanged, but now the float's fine end lines up with the distances that
were starving. At `d = 50 m` the step becomes `1.16 × 10⁻¹⁰`, and `Δd` falls from 1.49 mm to
**2.9 µm** — a 512-fold improvement.

It takes three changes, not two, and it is easy to stop at two. Changing only the compare op
and the clear value leaves the projection sending the far plane to 1, and on this scene that
alone changes **14.81%** of the frame. Swapping the near and far arguments of
`glm::perspective` as well — which algebraically turns `z_w` into `1 − z_w` — and flipping the
sign of the depth bias brings it back: the frame then differs in 0.72% of pixels, every one
of them an isolated pixel on the floor's grid lines where interpolation lands a hair
differently, and the slab covers exactly the same 112 194 pixels. Exercise 2 asks you to
make it.
:::

## The struct that has been there all along

`VkPipelineDepthStencilStateCreateInfo` has been in `PipelineBuilder` since 1.13, filled
in and never discussed:

```cpp title="code/common/scaffold/src/pipeline.cpp"
const VkPipelineDepthStencilStateCreateInfo depth_stencil{
    .depthTestEnable = depth_test_ ? VK_TRUE : VK_FALSE,
    .depthWriteEnable = depth_write_ ? VK_TRUE : VK_FALSE,
    .depthCompareOp = depth_compare_,
    .depthBoundsTestEnable = VK_FALSE,
    .stencilTestEnable = stencil_test_ ? VK_TRUE : VK_FALSE,
    .front = stencil_front_,
    .back = stencil_back_,
    .minDepthBounds = 0.0F,
    .maxDepthBounds = 1.0F,
};
```

Three of those fields are worth separating, because they are routinely confused:

- **`depthTestEnable`** decides whether the fragment's depth is *compared* at all. Off
  means every fragment survives, whatever is in front of it.
- **`depthWriteEnable`** decides whether a surviving fragment's depth is *stored*. Off
  means the surface is visible but invisible to everything drawn after it — which is
  exactly what a transparent surface wants, and what 4.2 will need.
- **`depthCompareOp`** decides what "closer" means. `LESS` with a buffer cleared to 1.0 is
  the arrangement this series has used throughout, and it is a convention, not a law.

The outline pipeline in this chapter turns the first two off together. An outline is a
decoration in screen space, not a thing in the world: it should not be buried by the floor
it overlaps, and nothing drawn later should be occluded by it.

## Two surfaces in one plane

The slab in the picture is a quad lying at exactly the floor's y. Both surfaces produce a
depth value at every pixel they share, the two values are the same number computed along
different paths, and `LESS` has to pick one.

The textbook answer is that they z-fight — a shimmering speckle of one surface and the
other. **That is not what happened here, and it is worth saying so.** With the slab as a
smaller quad with its own vertices, it simply won, everywhere, on this GPU, with no help
at all. Turning depth bias on and off changes 333 pixels out of 921600 — 0.04%, and all of
them on the slab's own edges.

That is luck, not a guarantee, and the way to see what the depth test really does with a
tie is to remove the luck: give the slab the floor's exact vertices, so the two depth
values are computed by the same arithmetic from the same inputs and come out bit for bit
identical.

<figure>
  <img src="/learn_vulkan/img/4.1/coplanar-unbiased.png" alt="The grid floor with no slab visible at all" />
  <figcaption>Identical coplanar geometry, no depth bias. The slab is drawn, and every one of its fragments is rejected.</figcaption>
</figure>

With `VK_COMPARE_OP_LESS`, equal is not less. The slab loses every pixel and disappears
completely — not a speckle, not a fight, an absence. Switch the bias on and it is the
floor that vanishes instead:

<figure>
  <img src="/learn_vulkan/img/4.1/coplanar-biased.png" alt="The same view with the painted slab covering the entire floor" />
  <figcaption>The same geometry with `depthBiasConstantFactor = -2.0`. 74.38% of the frame changes.</figcaption>
</figure>

Depth bias is the fixed-function answer to coplanar geometry, and it lives in the
rasterisation state rather than the depth-stencil state:

```cpp title="code/common/scaffold/src/pipeline.cpp"
.depthBiasEnable = depth_bias_ ? VK_TRUE : VK_FALSE,
.depthBiasConstantFactor = depth_bias_constant_,
.depthBiasClamp = 0.0F,
.depthBiasSlopeFactor = depth_bias_slope_,
```

The constant factor is not a distance. It is a multiple of *r*, and the spec's definition of
*r* is worth reading closely because it explains why the bias has to be expressed this way:

- for a **fixed-point** depth format, *r* is one constant for the whole buffer, of the order
  of one step of the format — about `2⁻²⁴` for a 24-bit one, with the exact value left to the
  implementation;
- for a **floating-point** depth format, there is no single answer, so *r* is computed per
  primitive as `2^(e − n)`, where *e* is the largest exponent among the primitive's own depth
  values and *n* the number of mantissa bits.

That second clause is the previous section's arithmetic turned into a hardware rule. A
`float` depth buffer has no one "smallest difference", so the implementation picks the one
that is right for *this triangle at this distance* — which is precisely what a bias measured
in world units could never do. The same `-2.0` works at 1 metre and at 50, because *r* is not
the same size in the two places.

The slope factor is scaled by *m*, how fast depth changes across the polygon: the length of
its depth gradient, `√((∂z/∂x)² + (∂z/∂y)²)`, which the spec lets an implementation
approximate by `max(|∂z/∂x|, |∂z/∂y|)`. A floor seen at a glancing angle covers an
enormous depth range in very few pixels, and a constant offset that is ample head-on is
nothing at all out near the horizon. The total offset is
`depthBiasConstantFactor · r + depthBiasSlopeFactor · m`, and a decal on a ground plane
generally needs both terms.

:::note[Why the number is negative]
`LESS` means smaller wins, and Vulkan's depth range runs 0 at the near plane to 1 at the
far one. A negative bias moves a fragment toward the viewer, which is the direction that
wins the comparison. Under a reversed-Z setup — `GREATER` with the buffer cleared to 0 —
the sign flips with it.
:::

## The stencil test needs a format that has one

Everything so far was depth. The stencil test needs something the previous eleven chapters
never asked for: somewhere to put the stencil.

vkcommon's chooser, written in 1.13, asks for the most precise depth format first:

```cpp title="code/common/scaffold/src/image.cpp"
constexpr std::array candidates{
    VK_FORMAT_D32_SFLOAT,
    VK_FORMAT_D32_SFLOAT_S8_UINT,
    VK_FORMAT_D24_UNORM_S8_UINT,
};
```

`VK_FORMAT_D32_SFLOAT` has no stencil aspect at all, and it is the one that wins on any
sane desktop GPU. So this chapter writes its own chooser that considers only the two
combined formats:

```cpp title="code/src/4.advanced_vulkan/depth_and_stencil/main.cpp"
[[nodiscard]] VkFormat choose_depth_stencil_format(VkPhysicalDevice physical_device) {
    // The two combined formats, most precise first. Vulkan guarantees that *at least
    // one* of these is supported as a depth-stencil attachment on every implementation,
    // but not which one -- D24_UNORM_S8_UINT is absent on some desktop GPUs and
    // D32_SFLOAT_S8_UINT on some mobile ones -- so both have to be asked for.
    constexpr std::array candidates{
        VK_FORMAT_D32_SFLOAT_S8_UINT,
        VK_FORMAT_D24_UNORM_S8_UINT,
    };

    for (const VkFormat format : candidates) {
        VkFormatProperties properties{};
        vkGetPhysicalDeviceFormatProperties(physical_device, format, &properties);
        if ((properties.optimalTilingFeatures &
             VK_FORMAT_FEATURE_DEPTH_STENCIL_ATTACHMENT_BIT) != 0) {
            return format;
        }
    }
    throw std::runtime_error("No supported depth-stencil attachment format was found.");
}
```

`vkGetPhysicalDeviceFormatProperties` is 1.11's call, asked a different question:
`optimalTilingFeatures` is a bitmask of what an image in `VK_IMAGE_TILING_OPTIMAL` can be
used for, and `VK_FORMAT_FEATURE_DEPTH_STENCIL_ATTACHMENT_BIT` is the bit that says "you may
attach this". Vulkan guarantees at least one of the two combined formats has it, but not
which, so both have to be asked for — on this machine (an RTX 4080) it is
`D32_SFLOAT_S8_UINT`.

The image itself differs from 1.13's depth buffer in exactly one field:

```cpp title="code/src/4.advanced_vulkan/depth_and_stencil/main.cpp"
[[nodiscard]] vkc::Image create_depth_stencil_buffer(vkc::Context& context,
                                                     VkFormat format,
                                                     VkExtent2D extent) {
    context.wait_idle();

    vkc::Image image(context,
                     vkc::ImageDesc{
                         .format = format,
                         .extent = extent,
                         .usage = VK_IMAGE_USAGE_DEPTH_STENCIL_ATTACHMENT_BIT,
                         .mip_levels = 1,
                         // The difference from 1.13's depth buffer, and the only one.
                         // The aspect mask has to name both, because it is used for the
                         // view and for every barrier, and a view that covers only the
                         // depth half cannot be used as a stencil attachment.
                         .aspect = VK_IMAGE_ASPECT_DEPTH_BIT |
                                   VK_IMAGE_ASPECT_STENCIL_BIT,
                     });

    vkc::immediate_submit(context, [&](VkCommandBuffer cmd) {
        // DEPTH_STENCIL_ATTACHMENT_OPTIMAL, not DEPTH_ATTACHMENT_OPTIMAL: the layout
        // has to cover both aspects for the same reason the view does.
        image.transition(cmd, VK_IMAGE_LAYOUT_UNDEFINED,
                         VK_IMAGE_LAYOUT_DEPTH_STENCIL_ATTACHMENT_OPTIMAL);
    });

    context.name(image.handle(), VK_OBJECT_TYPE_IMAGE, "depth-stencil buffer");
    return image;
}
```

`context.wait_idle()` first, because this is also called from `on_resize`, and destroying an
image the GPU might still be reading from is the one thing a resize path must not do.

Keeping 1.13's chooser and asking for a stencil anyway is instructive, because the
validation layers catch it four separate times — four different VUIDs — before a single pixel
is drawn:

```
vkCreateImageView(): pCreateInfo Using format (VK_FORMAT_D32_SFLOAT) with aspect flags
(VK_IMAGE_ASPECT_DEPTH_BIT|VK_IMAGE_ASPECT_STENCIL_BIT) but depth-only image formats can
have only the VK_IMAGE_ASPECT_DEPTH_BIT set.

vkCmdPipelineBarrier2(): pDependencyInfo->pImageMemoryBarriers[0].image Using format
(VK_FORMAT_D32_SFLOAT) with aspect flags (VK_IMAGE_ASPECT_DEPTH_BIT|VK_IMAGE_ASPECT_STENCIL_BIT)
but depth-only image formats can have only the VK_IMAGE_ASPECT_DEPTH_BIT set.

vkCreateGraphicsPipelines(): pCreateInfos[0].pNext<VkPipelineRenderingCreateInfo>
.stencilAttachmentFormat (VK_FORMAT_D32_SFLOAT) does not have a stencil aspect
(need to use a stencil format).

vkCmdBeginRendering(): pRenderingInfo->pStencilAttachment->imageView was created with a
format (VK_FORMAT_D32_SFLOAT) that does not have a stencil aspect.
```

The **image aspect** is the part that is easy to forget, because it is not one decision but
three that must agree: the view's `subresourceRange`, every barrier's `subresourceRange`,
and the layout. An aspect names *which half of the image you mean* — a combined format is a
single allocation carrying two logically separate buffers, and almost every Vulkan call that
touches an image wants to be told which of them it is talking about. A depth-stencil image
uses `VK_IMAGE_ASPECT_DEPTH_BIT | VK_IMAGE_ASPECT_STENCIL_BIT` and
`VK_IMAGE_LAYOUT_DEPTH_STENCIL_ATTACHMENT_OPTIMAL`, not the depth-only versions 1.13 used.

## Three attachments, two of them the same view

Dynamic rendering describes depth and stencil separately, so `VkRenderingInfo` grows a
third attachment. vkcommon's `begin_rendering()` attaches colour and depth; this chapter
writes its own with the third:

```cpp title="code/src/4.advanced_vulkan/depth_and_stencil/main.cpp"
void begin_rendering(VkCommandBuffer cmd, VkImageView colour_view,
                     VkImageView depth_stencil_view, VkExtent2D extent,
                     const VkClearColorValue& clear_colour) {
    const VkRenderingAttachmentInfo colour_attachment{
        .sType = VK_STRUCTURE_TYPE_RENDERING_ATTACHMENT_INFO,
        .pNext = nullptr,
        .imageView = colour_view,
        .imageLayout = VK_IMAGE_LAYOUT_COLOR_ATTACHMENT_OPTIMAL,
        .resolveMode = VK_RESOLVE_MODE_NONE,
        .resolveImageView = VK_NULL_HANDLE,
        .resolveImageLayout = VK_IMAGE_LAYOUT_UNDEFINED,
        .loadOp = VK_ATTACHMENT_LOAD_OP_CLEAR,
        .storeOp = VK_ATTACHMENT_STORE_OP_STORE,
        .clearValue = VkClearValue{.color = clear_colour},
    };
```

`VkClearColorValue` is the union that carries a clear colour in whichever of three types the
attachment's format wants — `float32[4]`, `int32[4]` or `uint32[4]`. The swapchain's format is
a normalised one, so the float member is the right arm, and `{{0.05F, 0.06F, 0.09F, 1.0F}}`
at the call site is two sets of braces because the outer pair initialises the union and the
inner pair the array inside it.

Then the depth and stencil attachments, which name the same view:

```cpp title="code/src/4.advanced_vulkan/depth_and_stencil/main.cpp"
    const VkClearValue clear_depth_stencil{.depthStencil = {.depth = 1.0F, .stencil = 0}};

    const VkRenderingAttachmentInfo depth_attachment{
        .sType = VK_STRUCTURE_TYPE_RENDERING_ATTACHMENT_INFO,
        .pNext = nullptr,
        .imageView = depth_stencil_view,
        .imageLayout = VK_IMAGE_LAYOUT_DEPTH_STENCIL_ATTACHMENT_OPTIMAL,
        .resolveMode = VK_RESOLVE_MODE_NONE,
        .resolveImageView = VK_NULL_HANDLE,
        .resolveImageLayout = VK_IMAGE_LAYOUT_UNDEFINED,
        .loadOp = VK_ATTACHMENT_LOAD_OP_CLEAR,
        .storeOp = VK_ATTACHMENT_STORE_OP_DONT_CARE,
        .clearValue = clear_depth_stencil,
    };

    const VkRenderingAttachmentInfo stencil_attachment{
        .sType = VK_STRUCTURE_TYPE_RENDERING_ATTACHMENT_INFO,
        .pNext = nullptr,
        .imageView = depth_stencil_view,
        .imageLayout = VK_IMAGE_LAYOUT_DEPTH_STENCIL_ATTACHMENT_OPTIMAL,
        .resolveMode = VK_RESOLVE_MODE_NONE,
        .resolveImageView = VK_NULL_HANDLE,
        .resolveImageLayout = VK_IMAGE_LAYOUT_UNDEFINED,
        // Clearing to 0 is what makes "did anything write here?" a meaningful question
        // later in the frame. Without it the outline pass would test against whatever
        // the previous frame left behind.
        .loadOp = VK_ATTACHMENT_LOAD_OP_CLEAR,
        .storeOp = VK_ATTACHMENT_STORE_OP_DONT_CARE,
        .clearValue = clear_depth_stencil,
    };

    const VkRenderingInfo rendering{
        .sType = VK_STRUCTURE_TYPE_RENDERING_INFO,
        .pNext = nullptr,
        .flags = 0,
        .renderArea = {{0, 0}, extent},
        .layerCount = 1,
        .viewMask = 0,
        .colorAttachmentCount = 1,
        .pColorAttachments = &colour_attachment,
        .pDepthAttachment = &depth_attachment,
        .pStencilAttachment = &stencil_attachment,
    };
    vkCmdBeginRendering(cmd, &rendering);
}
```

`depth_attachment` and `stencil_attachment` name **the same `VkImageView`**. That is not a
duplicate and not a mistake: a combined format is one image carrying two aspects, and they
are listed separately because they are cleared, loaded and stored separately. Here both
clear on load — depth to 1.0, stencil to 0 — and both are `DONT_CARE` on store, because
nothing outlives the frame.

`VkClearValue` is itself a union of a colour and a `depthStencil` pair, which is why one
`clear_depth_stencil` can serve both attachments even though each will use only its own half.

Clearing the stencil is load-bearing. The outline pass asks "did a crate write here?", and
that question only means anything if the buffer started the frame saying no.

## The stencil test is one integer comparison

Everything the stencil test does is this, per fragment, before the depth test runs:

```
   pass  =  ( reference & compareMask )  compareOp  ( stencil & compareMask )
```

Five fields, one comparison, and the whole of the rest of the stencil state is about what to
*write* afterwards. Two things in that line trip people up.

**The order of the operands.** The reference value is on the **left**. `VK_COMPARE_OP_LESS`
with `reference = 1` asks whether `1 < stencil`, not whether `stencil < 1`, and the two mean
opposite things.

That is easy to state and easy to get backwards, so it is worth measuring rather than
asserting. This chapter's outline pass uses `NOT_EQUAL` against a buffer that holds only 0
and 1; swapping in each of three other compare ops and counting the pixels that change gives:

| `compareOp`, `reference = 1` | reads as | outline pixels drawn |
|---|---|---|
| `VK_COMPARE_OP_NOT_EQUAL` | `1 ≠ stencil` | 3 394 |
| `VK_COMPARE_OP_GREATER` | `1 > stencil` | 3 394 — *byte-identical* |
| `VK_COMPARE_OP_LESS` | `1 < stencil` | **0** |
| `VK_COMPARE_OP_EQUAL` | `1 = stencil` | 24 289 |

With only 0 and 1 in the buffer, `1 > stencil` and `1 ≠ stencil` select exactly the same
fragments, and the two frames come out identical to the byte. `1 < stencil` can never be
true, so the outline vanishes entirely. Had the operands been the other way round, `LESS`
would have been the one that worked and `GREATER` the one that drew nothing — so the
experiment settles the question rather than illustrating it.

**The masks are not the same field.** `compareMask` is `AND`ed into *both* sides of the
comparison above, so it selects which bits take part in the test. `writeMask` controls which
bits a later write may change and has no effect on the comparison at all. A stencil buffer
holding several independent flags in different bits is the reason both exist.

Three more fields say what to do afterwards, and they cover the three possible fates of a
fragment:

| field | when it applies |
|---|---|
| `failOp` | the stencil test failed |
| `depthFailOp` | the stencil test passed, the depth test failed |
| `passOp` | both passed |

Each is a `VkStencilOp`, and the ones this chapter uses are `VK_STENCIL_OP_KEEP` (leave the
stored value alone) and `VK_STENCIL_OP_REPLACE` (store `reference`, masked by `writeMask`).
The others in the enum — `ZERO`, `INCREMENT_AND_CLAMP`, `DECREMENT_AND_CLAMP`, `INVERT`,
`INCREMENT_AND_WRAP`, `DECREMENT_AND_WRAP` — are what turn the stencil buffer into a counter
rather than a flag, which is how shadow volumes and concave-polygon fills work.

Seen that way, the two passes in this chapter are a set operation. The crates stamp a set —
"pixels where a crate is visible". The outline draws an enlarged crate restricted to the
complement of that set, which is the rim and nothing else.

## Stamping a silhouette

The crates are drawn with the only state that differs from the floor's:

```cpp title="code/src/4.advanced_vulkan/depth_and_stencil/main.cpp"
const VkStencilOpState write_one{
    .failOp = VK_STENCIL_OP_KEEP,
    .passOp = VK_STENCIL_OP_REPLACE,
    // A fragment that passes the stencil test and fails the depth test is behind
    // something. KEEP is what stops a crate hidden by a wall from stamping a
    // silhouette that would then be outlined through the wall.
    .depthFailOp = VK_STENCIL_OP_KEEP,
    .compareOp = VK_COMPARE_OP_ALWAYS,
    .compareMask = 0xFF,
    .writeMask = 0xFF,
    .reference = 1,
};
```

`compareOp = ALWAYS` means this pass never rejects anything — it is writing, not reading.
`passOp = REPLACE` stores `reference` wherever the fragment also survived the depth test,
so what accumulates is the crates' *visible* silhouette, occlusions included.

`depthFailOp = KEEP` is the field that earns its place. A fragment that passes the stencil
test and fails the depth test is behind something else, and keeping the stencil unchanged
there is what stops a crate hidden behind a wall from stamping a silhouette that would then
be outlined straight through the wall.

## Drawing only where nothing was

The outline is the same cube, 6% larger, with the test inverted:

```cpp title="code/src/4.advanced_vulkan/depth_and_stencil/main.cpp"
const VkStencilOpState keep_where_unstamped{
    .failOp = VK_STENCIL_OP_KEEP,
    .passOp = VK_STENCIL_OP_KEEP,
    .depthFailOp = VK_STENCIL_OP_KEEP,
    .compareOp = VK_COMPARE_OP_NOT_EQUAL,
    .compareMask = 0xFF,
    .writeMask = 0x00,
    .reference = 1,
};
```

`NOT_EQUAL 1` keeps only fragments landing where no crate was drawn, which of a
slightly-enlarged crate is precisely the rim protruding past the real one. `writeMask = 0`
because this pass reads the stencil and must leave it intact for the next crate. All three
ops are `KEEP` for the same reason: a pass that writes nothing needs no write behaviour.

## The frame, and why the order is the chapter

```cpp title="code/src/4.advanced_vulkan/depth_and_stencil/main.cpp"

                push(frame.cmd, model_of(crate, kOutlineScale), kOutlineColour);
                vkCmdDrawIndexed(frame.cmd, static_cast<uint32_t>(kCubeIndices.size()), 1,
                                 0, 0, 0);
            }
        }

        vkCmdEndRendering(frame.cmd);
    }
```

The draw order matters more than any of the state does. Every crate stamps its silhouette
before any outline is drawn. Interleave the two — crate, outline, crate, outline — and the
first crate's halo spills across the second crate, which has not yet written the stencil that
would have masked it. All the writes, then all the reads.

## The helpers

Three small ones, all of them shapes Part 2 established:

```cpp title="code/src/4.advanced_vulkan/depth_and_stencil/main.cpp"
    [[nodiscard]] static glm::mat4 model_of(const CratePlacement& crate, float scale) {
        return glm::scale(
            glm::rotate(glm::translate(glm::mat4(1.0F), crate.position), crate.angle,
                        glm::vec3(0.0F, 1.0F, 0.0F)),
            glm::vec3(scale));
    }

    void push(VkCommandBuffer cmd, const glm::mat4& model, const glm::vec4& colour) {
        const PushConstants constants{
            .model = model,
            .normal_matrix = normal_matrix_of(model),
            .colour = colour,
        };
        vkCmdPushConstants(cmd, pipeline_layout_,
                           VK_SHADER_STAGE_VERTEX_BIT | VK_SHADER_STAGE_FRAGMENT_BIT, 0,
                           sizeof(constants), &constants);
    }
```

`model_of` reads inside out — translate, then rotate, then scale — and composes as
`T · R · S`, which is 1.12's ordering: the scale is nearest the vertex so it happens first,
in the object's own frame, and the translation is outermost so it is not scaled. The outline
pass calls the same function with `kOutlineScale`, which is why the enlarged crate grows
about its own centre rather than sliding away from the origin.


Then the frame plumbing, all of it Part 1's:

```cpp title="code/src/4.advanced_vulkan/depth_and_stencil/main.cpp"
    static void set_viewport(const vkc::FrameInfo& frame) {
        const VkViewport viewport{
            .x = 0.0F,
            .y = 0.0F,
            .width = static_cast<float>(frame.extent.width),
            .height = static_cast<float>(frame.extent.height),
            .minDepth = 0.0F,
            .maxDepth = 1.0F,
        };
        vkCmdSetViewport(frame.cmd, 0, 1, &viewport);

        const VkRect2D scissor{.offset = {0, 0}, .extent = frame.extent};
        vkCmdSetScissor(frame.cmd, 0, 1, &scissor);
    }
```

`minDepth` and `maxDepth` are the third place the depth range appears, after the clear value
and the compare op. They rescale `z_w` into the range the buffer actually stores, and
`0.0` to `1.0` is the identity.

Vulkan allows `minDepth > maxDepth`, and swapping them does reverse the direction of the depth
range — but it is *not* reversed-Z. The viewport computes `1 − z_w` from a `z_w` that has
already been rounded near 1.0, where a float's step is `2⁻²⁴`, so the subtraction produces a
small number with none of the fine resolution a small float could have carried. The precision
has to be built in by the projection matrix, before any rounding near 1 happens.

```cpp title="code/src/4.advanced_vulkan/depth_and_stencil/main.cpp"
    [[nodiscard]] static glm::mat4 build_projection(VkExtent2D extent) {
        const float aspect =
            static_cast<float>(extent.width) / static_cast<float>(extent.height);
        glm::mat4 projection =
            glm::perspective(glm::radians(45.0F), aspect, 0.1F, 100.0F);
        projection[1][1] *= -1.0F;  // Vulkan's clip-space y points down.
        return projection;
    }
```

Those are the `0.1F` and `100.0F` the precision table was computed from. The `[1][1] *= -1`
is 1.13's y-flip, and 4.2 works out what it does to the winding of every triangle in the
scene.

```cpp title="code/src/4.advanced_vulkan/depth_and_stencil/main.cpp"
    void create_uniform_buffers() {
        for (vkc::Buffer& buffer : uniform_buffers_) {
            buffer = vkc::Buffer(context().allocator(), sizeof(Globals),

                                     VMA_ALLOCATION_CREATE_MAPPED_BIT);
        }
    }

    void update_globals(size_t slot, VkExtent2D extent) {
        const Globals globals{
```

One buffer per frame in flight, persistently mapped — 1.10's arrangement, so that writing
this frame's globals cannot disturb the frame the GPU is still reading.

### Declaring the attachment is not enabling the test

Every pipeline shares an opening, and one line in it is worth stopping on:

```cpp title="code/src/4.advanced_vulkan/depth_and_stencil/main.cpp"
        // The return type is spelled out because the setters return a reference to the
        // builder, and `auto` would deduce a reference to a temporary that has already
        // died. Naming the type makes each call hand back a fresh copy to configure.
        const auto base = [&]() -> vkc::PipelineBuilder {
            return vkc::PipelineBuilder(device)
                .shaders(shader)
                .vertex_input(std::span(&binding, 1), attributes)
                .colour_attachment(swapchain().format())
                .stencil_attachment(depth_stencil_format_)
                .layout(pipeline_layout_);
        };
```

`base` is a lambda returning a fresh builder rather than a builder stored in a variable,
because `PipelineBuilder`'s setters return `PipelineBuilder&` — a reference to the object
they were called on. Writing `const auto base = PipelineBuilder(device).shaders(shader)`
would deduce `PipelineBuilder&` bound to a temporary that dies at the end of that
statement. Spelling the return type out forces a copy on every call, which is exactly what
five differently-configured pipelines need.

`stencil_attachment()` is the line that surprises. **Every** pipeline here declares the
stencil format, including the three that never test the stencil.

Without a render pass object, a pipeline carries its own description of the attachments it
expects, and that description has to match the rendering instance it is used inside.
Dropping `stencil_attachment()` and running gives:

```
vkCmdDrawIndexed(): VkRenderingInfo::pStencilAttachment->imageView format
(VK_FORMAT_D32_SFLOAT_S8_UINT) must match the corresponding format in
VkPipelineRenderingCreateInfo::stencilAttachmentFormat (VK_FORMAT_UNDEFINED).
```

Note where it lands: at the **draw**, not at pipeline creation. Nothing is wrong with
either object on its own; they are only incompatible once used together, which is the
characteristic shape of a dynamic-rendering mistake and worth recognising.

### The five

The floor: ordinary opaque geometry, and the one pipeline in the chapter with no surprises
in it at all.

```cpp title="code/src/4.advanced_vulkan/depth_and_stencil/main.cpp"
        // The floor. Ordinary opaque geometry: test against what is already there, write
        // what survives, and leave the stencil alone.
        floor_pipeline_ = base()
                              .cull(VK_CULL_MODE_NONE, VK_FRONT_FACE_COUNTER_CLOCKWISE)
                              .depth(depth_stencil_format_, /*test=*/true, /*write=*/true,
                                     VK_COMPARE_OP_LESS)
                              .build();
```

`VK_CULL_MODE_NONE` because a floor is a single quad with no back side to hide, and a camera
that dips below it should still see something. 4.2 makes that choice properly.

The crates, with the stencil write:

```cpp title="code/src/4.advanced_vulkan/depth_and_stencil/main.cpp"

            base()
                .cull(VK_CULL_MODE_BACK_BIT, VK_FRONT_FACE_COUNTER_CLOCKWISE)

                       VK_COMPARE_OP_LESS)
                .stencil_test(write_one, write_one)
                .build();
```

`stencil_test` takes two states, front and back, and passing the same struct twice says
"treat both the same". They are separate because a two-sided stencil effect — shadow volumes,
again — increments on front faces and decrements on back ones.

The slab, built twice so the <kbd>2</kbd> key has something to switch between:


## What changed since 3.4

- a depth-stencil format, chosen from the two combined candidates rather than 1.13's list
- an image whose aspect mask, view and layout all name depth *and* stencil
- a third attachment in `VkRenderingInfo`, pointing at the same view as the second
- five pipelines that differ only in depth and stencil state, sharing two fragment shaders
- the first calls to 1.7's `depth_bias`, `stencil_attachment` and `stencil_test`
- Part 4 opens with 26 chapters in the build

## Words introduced in this chapter

| | |
|---|---|
| **depth test** | comparing a fragment's depth against what is already stored, and discarding it if it loses |
| **depth write** | whether a surviving fragment's depth is *stored* — a separate decision from testing it |
| **depth compare op** | what "closer" means; `LESS` against a buffer cleared to 1.0 is a convention, not a law |
| **depth precision** | how far apart two surfaces must be before the buffer can distinguish them: `Δd = Δz·(f−n)d²/(f·n)`, so it worsens with the square of distance |
| **coplanar geometry** | two surfaces in the same plane, whose depth values are equal or differ by one bit |
| **depth bias** | a per-pipeline offset applied to depth before the test, which resolves coplanarity without moving a vertex |
| **minimum resolvable difference** | the spec's *r*: one constant for a fixed-point format, and recomputed per primitive as `2^(e − n)` for a float one |
| **slope-scaled bias** | the second bias term, multiplied by the polygon's depth slope *m*, because a glancing polygon covers more depth per pixel |
| **combined depth-stencil format** | one image carrying two buffers; `D32_SFLOAT_S8_UINT` or `D24_UNORM_S8_UINT`, at least one of which always exists |
| **image aspect** | which half of such an image a view, barrier or layout is talking about |
| **stencil buffer** | a small integer per pixel that the pipeline can test and write, with no meaning of its own |
| **stencil test** | `(reference & compareMask) compareOp (stencil & compareMask)` — reference on the left |
| **stencil operation** | what to write afterwards, chosen by which of three fates the fragment met: `failOp`, `depthFailOp`, `passOp` |
| **compare mask / write mask** | which bits take part in the comparison, and which bits a write may change — two different fields |
| **reference value** | the constant the stencil is compared against, and the value `REPLACE` stores |
