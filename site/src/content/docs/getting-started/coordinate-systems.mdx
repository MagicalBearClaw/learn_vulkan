Everything so far has been flat. This chapter adds the third dimension, and with it the two pieces
that make 3D work: a **projection matrix**, which decides how a point in space lands on the screen,
and a **depth buffer**, which decides which surface you actually see.

It also contains the two most reliable ways to get Vulkan wrong, both of which produce a picture
that is confidently, silently incorrect.

## A cube is twenty-four vertices

```cpp title="code/src/1.getting_started/coordinate_systems/main.cpp"
    // bottom (-y)
    {{-kH, -kH, -kH}, {0.0F, 1.0F}},
    {{kH, -kH, -kH}, {1.0F, 1.0F}},
    {{kH, -kH, kH}, {1.0F, 0.0F}},
    {{-kH, -kH, kH}, {0.0F, 0.0F}},
}};
```

Twenty-four vertices, not eight. The eight corners each need **three different texture
coordinates** — one per face they belong to — and a vertex is the whole bundle of attributes, not
just a position:

```
   one corner of the cube belongs to three faces
        │
        ├── on the front face  it is uv (0,0)
        ├── on the top face    it is uv (0,1)
        └── on the right face  it is uv (1,0)

   three different vertices that happen to share a position
```

The same will be true of normals in chapter 2.2, which is why a cube with hard edges always has 24
vertices in practice.

Model space here is right-handed: +x right, +y up, +z toward the viewer. Each face is listed
bottom-left, bottom-right, top-right, top-left **as seen from outside**, which makes every face
wind counter-clockwise from outside — and that matters when culling is switched on.

```cpp title="code/src/1.getting_started/coordinate_systems/main.cpp"
constexpr std::array<uint16_t, 36> kIndices{
    0,  1,  2,  2,  3,  0,   // front
    4,  5,  6,  6,  7,  4,   // back
    8,  9,  10, 10, 11, 8,   // left
    12, 13, 14, 14, 15, 12,  // right
    16, 17, 18, 18, 19, 16,  // top
    20, 21, 22, 22, 23, 20,  // bottom
};
```

Six faces, two triangles each, the same `0-1-2 2-3-0` pattern the quad used, shifted by four each
time.

simply win, which is the point of having three rather than one.

## The chain of spaces

A vertex passes through four coordinate systems on its way to a pixel, and each step is one matrix.

| Space | Origin | What it is |
|---|---|---|
| **Model** | the object's own centre | what is in the vertex buffer |
| **World** | the scene's origin | after the model matrix places the object |
| **View** | the camera | after the view matrix, camera at the origin looking down −z |
| **Clip** | — | after the projection, ready for the divide by `w` |

```slang title="code/src/1.getting_started/coordinate_systems/cube.slang"
struct VSInput {
    [[vk::location(0)]] float3 position;
    [[vk::location(1)]] float2 uv;
};

struct VSOutput {
    float4 position : SV_Position;
    [[vk::location(0)]] float2 uv;
};
```

```slang title="code/src/1.getting_started/coordinate_systems/cube.slang"
struct Globals {
    float4x4 view;
    float4x4 projection;
};
[[vk::binding(0, 0)]] ConstantBuffer<Globals> globals;

struct PushConstants {
    float4x4 model;
};
[[vk::push_constant]] PushConstants push;

[[vk::binding(1, 0)]] Sampler2D tex;
```

```slang title="code/src/1.getting_started/coordinate_systems/cube.slang"
[shader("vertex")]
VSOutput vertexMain(VSInput input) {
    VSOutput output;
```

```slang title="code/src/1.getting_started/coordinate_systems/cube.slang"
    float4 world = mul(push.model, float4(input.position, 1.0));
    float4 view_space = mul(globals.view, world);
    output.position = mul(globals.projection, view_space);
```

```slang title="code/src/1.getting_started/coordinate_systems/cube.slang"
    output.uv = input.uv;
    return output;
}

[shader("fragment")]
float4 fragmentMain(VSOutput input) : SV_Target {
    return tex.Sample(input.uv);
}
```

Nested `mul()` calls would be the literal translation of GLSL's `projection * view * model *
position`, but three named steps read better and compile to the same thing — and the names are the
coordinate spaces this chapter is about.

After that the hardware divides all four components by `w` to get **normalised device
coordinates**, and maps those onto the viewport. That divide is the whole of perspective:

```
   a vertex 2 units away    →  w = 2   →  x/2, y/2   lands near the centre
   a vertex 8 units away    →  w = 8   →  x/8, y/8   lands four times closer to the centre
```

The projection matrix is what puts the distance into `w`.

:::tip[Three multiplies per vertex, or one]
Multiplying the three matrices on the CPU once per object and pushing the result saves the GPU two
matrix multiplies per vertex. Worth doing when a model has 100 000 vertices.

They are kept separate here because the separation is the lesson, and because the lighting chapters
need world-space and view-space positions as well as the final one.
:::

```cpp title="code/src/1.getting_started/coordinate_systems/main.cpp"
struct Globals {
    glm::mat4 view;
    glm::mat4 projection;
};
static_assert(sizeof(Globals) == 128);
```

Two matrices, 128 bytes, and **no padding needed** — a `mat4` is four 16-byte columns, so std140
and C++ agree exactly. This is the struct chapter 1.10's alignment section was preparing you to
check.

## The projection

```cpp title="code/src/1.getting_started/coordinate_systems/main.cpp"
    [[nodiscard]] static glm::mat4 build_projection(VkExtent2D extent) {
        const float aspect = static_cast<float>(extent.width) /
                             static_cast<float>(extent.height);

        glm::mat4 projection = glm::perspective(glm::radians(45.0F), aspect, 0.1F, 100.0F);
```

Four arguments: **vertical field of view**, **aspect ratio**, **near plane**, **far plane**. The
aspect ratio is what replaces the hand-rolled `aspect_fix` from chapter 1.12 — that was an
orthographic projection all along, and this is the real thing.

### Where that matrix comes from

`glm::perspective` is four lines of arithmetic, and leaving it a black box makes the next two
sections impossible to follow. It is worth deriving, because every term in it answers a question
you can ask in plain English.

The camera sits at the origin of view space looking down **−z**, so a point in front of it has a
negative `z`; call its distance `d = -z`. Perspective is the observation that a thing twice as far
away covers half the angle — so the question "where on screen does this land?" is answered by
similar triangles:

```
              top edge of the view
            ┌ · · · · · · · · · · ·
            │        ╱│
   camera   │     ╱   │ y            a point at height y,
      ●─────┼──╱──────●              distance d from the camera
            │╱        │
            └ · · · · · · · · · · ·
             ←    d    →

   the top edge, at distance d, is at height   d · tan(fov/2)
   so the point's height as a fraction of it:  y / (d · tan(fov/2))
```

That fraction is what has to come out as −1…1 across the screen, so writing `t = tan(fov/2)`:

```
   ndc.y = y / (d · t)
   ndc.x = x / (d · t · aspect)      horizontal half-angle is `aspect` times the vertical
```

Both divide by `d`. That is the one thing a matrix *cannot* do — a matrix multiply has no division
in it — and it is the reason the hardware's divide-by-`w` exists at all. So the matrix's job is to
put `d` into `w` and let the fixed-function divide finish the job. Since `d = -z`, that is a single
`-1` in the bottom row:

```
        x       y       z          w
   ┌                                        ┐
   │  1/(a·t)   0       0          0        │   →  clip.x = x/(a·t)
   │  0         1/t     0          0        │   →  clip.y = y/t
   │  0         0       f/(n-f)    f·n/(n-f)│   →  clip.z = the depth mapping, below
   │  0         0      -1          0        │   →  clip.w = -z = d
   └                                        ┘

        a = aspect,  t = tan(fov/2),  n = near,  f = far
```

Divide the first two rows by that `w` and you get the two similar-triangle formulas back exactly.
**The entire content of perspective is that `-1`.**

The third row is a separate problem with a separate answer: `z` has to come out as 0 at the near
plane and 1 at the far plane, and it has to survive the same divide by `d`. Two conditions, two
unknowns, and the `f/(n-f)` and `f·n/(n-f)` above are their solution. Check it:

```
   at z = -n :   clip.z = -n·f/(n-f) + f·n/(n-f) = 0,      clip.w = n   →  0/n = 0   ✓
   at z = -f :   clip.z = -f·f/(n-f) + f·n/(n-f) = f,      clip.w = f   →  f/f = 1   ✓
```

### Why the near plane matters so much

Working that division through for any distance `d` gives the depth actually stored:

```
   depth(d) = f/(f-n) · (1 - n/d)
```

The `n/d` is the whole story: depth is **hyperbolic** in distance, not linear. Doubling the
distance does not halve the remaining precision, it does something far more lopsided. Setting
`depth = 0.5` and solving for `d` says where the first half of the buffer's range is spent:

```
   half the range is used up by   d = 2·f·n / (f + n)

   near = 0.1,  far = 100   →   d = 0.1998     half the precision covers 0.1 → 0.2
   near = 0.01, far = 100   →   d = 0.02       half of it covers 0.01 → 0.02
```

Moving the near plane *in* by a factor of ten costs an order of magnitude of precision everywhere
else, and the far plane barely matters by comparison — it appears only in the `f/(f-n)` scale.
When surfaces flicker against each other at a distance, pushing the near plane out is the first
thing to try, ahead of anything cleverer.

### Trap one: y points down

```cpp title="code/src/1.getting_started/coordinate_systems/main.cpp"
        projection[1][1] *= -1.0F;

        return projection;
    }
```

**Vulkan's clip-space y axis points down. OpenGL's points up.**

glm produces an OpenGL projection, because glm was written for OpenGL. Negating the matrix entry
that scales y turns one into the other.

That entry is the `1/t` in the matrix above, and `projection[1][1]` is how you reach it: a
`glm::mat4` is stored column by column, so the first index is the **column** and the second the
row. Column 1, row 1 is the y scale. (Chapter 1.12's section on getting a matrix to the shader is
where that indexing convention was introduced; it is the one piece of glm that regularly reads as
a typo.)

Leave the negation out and everything renders upside down — and because a rotating cube looks
plausible either way, it is entirely possible not to notice until a letter of text appears.

There is a second way to do it: give the viewport a **negative height**, with `y` set to the bottom
of the image:

```cpp
const VkViewport viewport{
    .y = static_cast<float>(extent.height),
    .height = -static_cast<float>(extent.height),
};
```

This is legal in core Vulkan (it came from `VK_KHR_maintenance1`, folded in at 1.1). Either works.
Pick one and be consistent, because doing both gets you back where you started.

### Trap two: z runs 0 to 1

**Vulkan's clip-space z runs 0 to 1. OpenGL's runs −1 to 1.**

```
   OpenGL projection output:  near → -1     far → +1
   Vulkan clips at:           0 ................ 1
                              └── everything from -1 to 0 is thrown away
```

So the entire near half of the frustum disappears, and the far half has half its precision. The
result is a scene with chunks missing and depth fighting in whatever survives.

This is handled once, project-wide:

```cmake title="code/common/base/CMakeLists.txt"
GLM_FORCE_DEPTH_ZERO_TO_ONE   # Vulkan clip space is z in [0,1], not [-1,1]
```

It must be defined for **every** translation unit that includes glm, which is why it is `PUBLIC` on
`vkbase` rather than set per chapter — half a program with it and half without is a genuinely
horrible bug to find.

:::note[0 to 1 is also just better]
Even setting compatibility aside, 0…1 is the right range. Depth values are stored with the
precision of a float, and floats are dense near zero. OpenGL's −1…1 range wastes roughly half the
representable values on a symmetric range nobody needed.

This is also why **reversed-z** — mapping near to 1 and far to 0, with a `GREATER` depth test —
gives so much better precision with a floating-point depth buffer. Chapter 4.1 works through it.
:::

```cpp title="code/src/1.getting_started/coordinate_systems/main.cpp"
    void update_globals(size_t slot, VkExtent2D extent) {
        const Globals globals{
            .view = glm::translate(glm::mat4(1.0F), glm::vec3(0.0F, 0.0F, -3.5F)),
            .projection = build_projection(extent),
        };

        std::memcpy(uniform_buffers_[slot].mapped(), &globals, sizeof(globals));
    }
```

A fixed camera, three and a half units back. **Moving the world away from the camera and moving the
camera away from the world are the same matrix**, which is why a translation of −3.5 serves as a
view matrix. Chapter 1.14 makes this interactive and explains why a view matrix is the camera's
transform *inverted*.

Rebuilding the projection every frame from the current extent is what makes resizing work for free.

## The depth buffer

Three cubes overlap on screen. Without a depth buffer, whichever is drawn last wins, everywhere it
covers — which is wrong roughly half the time.

```
   for each fragment:
       if (its depth < the depth already stored here)   ← VK_COMPARE_OP_LESS
           keep it, write the new depth
       else
           discard it
```

The comparison, the test and the write are fixed-function hardware, and they are close to free.

```cpp title="code/src/1.getting_started/coordinate_systems/main.cpp"
    [[nodiscard]] VkFormat choose_depth_format() {
        constexpr std::array candidates{
            VK_FORMAT_D32_SFLOAT,
            VK_FORMAT_D32_SFLOAT_S8_UINT,
            VK_FORMAT_D24_UNORM_S8_UINT,
        };

        for (const VkFormat format : candidates) {
            VkFormatProperties properties{};
            vkGetPhysicalDeviceFormatProperties(context().physical_device(), format,
                                                &properties);
            if ((properties.optimalTilingFeatures &
                 VK_FORMAT_FEATURE_DEPTH_STENCIL_ATTACHMENT_BIT) != 0) {
                spdlog::info("Depth format: {}",
                             format == VK_FORMAT_D32_SFLOAT ? "D32_SFLOAT" : "other");
                return format;
            }
        }
        throw std::runtime_error("No supported depth attachment format was found.");
    }
```

Depth formats are not all mandatory, so the first supported one wins. `D32_SFLOAT` is what to want:
full float precision and no stencil bits to pay for. `D24_UNORM_S8_UINT` is the traditional
alternative. `D16_UNORM` is mandatory everywhere and is genuinely too coarse for a scene of any
depth — it is where a lot of z-fighting comes from, and it is deliberately not in the list.

This is the same "ask, do not assume" pattern as chapter 1.11's linear-blit check.

```cpp title="code/src/1.getting_started/coordinate_systems/main.cpp"
    void create_depth_buffer(VkExtent2D extent) {
        context().wait_idle();

        depth_ = vkc::Image(context(), vkc::ImageDesc{
                                           .format = depth_format_,
                                           .extent = extent,
                                           .usage =
                                               VK_IMAGE_USAGE_DEPTH_STENCIL_ATTACHMENT_BIT,
                                           .mip_levels = 1,
                                           .aspect = VK_IMAGE_ASPECT_DEPTH_BIT,
                                       });
```

It is an image, with three things different from a texture: a **depth format**,
**`DEPTH_STENCIL_ATTACHMENT` usage** instead of `SAMPLED`, and a **`DEPTH` aspect** instead of
`COLOR`. The aspect is the one that gets forgotten, and it must match everywhere — in the view, in
every barrier, in every copy.

`wait_idle()` first, because this also runs on resize, and the old depth image may still be in use
by a frame in flight. Assigning over `depth_` destroys the old one.

```cpp title="code/src/1.getting_started/coordinate_systems/main.cpp"
        vkc::immediate_submit(context(), [&](VkCommandBuffer cmd) {
            depth_.transition(cmd, VK_IMAGE_LAYOUT_UNDEFINED,
                              VK_IMAGE_LAYOUT_DEPTH_ATTACHMENT_OPTIMAL);
        });

        context().name(depth_.handle(), VK_OBJECT_TYPE_IMAGE, "depth buffer");
    }
```

A new image is in `UNDEFINED`. Moving it to the attachment layout once here means the rendering
scope never has to, and since `loadOp` is `CLEAR` the previous contents are discarded every frame
anyway.

### Attaching it

```cpp title="code/src/1.getting_started/coordinate_systems/main.cpp"
        const VkClearValue colour_clear{.color = {{0.02F, 0.02F, 0.04F, 1.0F}}};
```

```cpp title="code/src/1.getting_started/coordinate_systems/main.cpp"
        const VkClearValue depth_clear{.depthStencil = {1.0F, 0}};

        const VkRenderingAttachmentInfo depth_attachment{
            .sType = VK_STRUCTURE_TYPE_RENDERING_ATTACHMENT_INFO,
            .pNext = nullptr,
            .imageView = depth_.view(),
            .imageLayout = VK_IMAGE_LAYOUT_DEPTH_ATTACHMENT_OPTIMAL,
            .resolveMode = VK_RESOLVE_MODE_NONE,
            .resolveImageView = VK_NULL_HANDLE,
            .resolveImageLayout = VK_IMAGE_LAYOUT_UNDEFINED,
            .loadOp = VK_ATTACHMENT_LOAD_OP_CLEAR,
            .storeOp = VK_ATTACHMENT_STORE_OP_DONT_CARE,
            .clearValue = depth_clear,
        };
```

```cpp title="code/src/1.getting_started/coordinate_systems/main.cpp"
            .pDepthAttachment = &depth_attachment,
```

Cleared to **1.0**, the far plane, because the test keeps the *smaller* value and everything must
start out further away than "infinitely far". `.depthStencil` is the other arm of the
`VkClearValue` union that `.color` came from.

`storeOp` is `DONT_CARE`, and that is a real optimisation rather than tidiness. Nothing reads the
depth buffer after the frame ends, so the driver can skip writing it back to memory. On a
tile-based GPU — every phone, and Apple silicon — the depth buffer can then live entirely in tile
memory and never touch RAM at all.

Compare that with `VkRenderPass`, where expressing the same thing meant a `storeOp` on an
attachment description, a subpass dependency, and a framebuffer object built to match.

### Turning the test on

```cpp title="code/src/1.getting_started/coordinate_systems/main.cpp"
                .depth(depth_format_, /*test=*/true, /*write=*/true, VK_COMPARE_OP_LESS)
```

Test and write are separate switches, and the combination matters:

| test | write | for |
|---|---|---|
| on | on | opaque geometry — the default |
| on | off | transparent geometry: hidden by things in front, but does not hide what is behind |
| off | off | UI drawn over everything |

`VK_COMPARE_OP_LESS` keeps the nearer fragment. With a reversed-z depth buffer this becomes
`GREATER`, and with an equal-depth pre-pass it becomes `EQUAL`.

The pipeline is also told the depth *format*, for the same reason it is told the colour format:
there is no render pass to describe the attachments, so `VkPipelineRenderingCreateInfo` carries it.

## Back-face culling

```cpp title="code/src/1.getting_started/coordinate_systems/main.cpp"
                .cull(VK_CULL_MODE_BACK_BIT, VK_FRONT_FACE_COUNTER_CLOCKWISE)
```

Half the triangles of a closed object face away from the camera and are entirely hidden by the half
that do not. Culling throws them out before rasterisation, for free.

Which winding counts as "front" is the fiddly part, and the reasoning is not obvious:

```
   the cube is wound counter-clockwise seen from outside
        │
        ├── the y flip in the projection is a MIRROR    → reverses winding
        └── glm::perspective is right-handed and
            negates z on the way to clip space          → reverses winding again

   two reflections compose to a rotation → the winding on screen is unchanged
```

:::tip[Do not reason about this — look]
The failure is subtle. A cube with the wrong winding still renders as a cube-shaped thing; it is
the *inside* you are seeing, and it reads as an open box with a concave corner rather than a solid
one.

Set `cullMode` to `VK_CULL_MODE_NONE` and it always looks right, which makes culling a good thing
to turn off when geometry is behaving strangely and a bad thing to leave off.
:::

## What moves into `vkcommon`

The two depth functions join `image.cpp`, beside the `vkc::Image` chapter 1.11 wrote.
Chapter 1.14 calls both.

```cpp title="code/common/scaffold/src/image.cpp"
VkFormat choose_depth_format(VkPhysicalDevice physical_device) {
    // Most precise first. A format is only usable as a depth attachment if the GPU says
    // so, and asking is cheaper than assuming: D24_UNORM_S8_UINT is absent on some
    // desktop GPUs and D32_SFLOAT_S8_UINT on some mobile ones.
    constexpr std::array candidates{
        VK_FORMAT_D32_SFLOAT,
        VK_FORMAT_D32_SFLOAT_S8_UINT,
        VK_FORMAT_D24_UNORM_S8_UINT,
    };

    for (const VkFormat format : candidates) {
        VkFormatProperties properties{};
        vkGetPhysicalDeviceFormatProperties(physical_device, format, &properties);
        if ((properties.optimalTilingFeatures &
             VK_FORMAT_FEATURE_DEPTH_STENCIL_ATTACHMENT_BIT) != 0) {
            return format;
        }
    }
    throw std::runtime_error("No supported depth attachment format was found.");
}
```

Your function with the logging removed, and taking the physical device as a parameter
rather than reaching for `context()`. The comment records *why* all three candidates are
needed rather than just the first: `D24_UNORM_S8_UINT` is missing on some desktop GPUs and
`D32_SFLOAT_S8_UINT` on some mobile ones, so a list of one would fail somewhere real.

```cpp title="code/common/scaffold/src/image.cpp"
Image create_depth_buffer(Context& context, VkFormat format, VkExtent2D extent) {
    // The GPU must have finished with the old depth buffer before it is replaced. A
    // resize already waits for idle, and at start-up there is nothing in flight, so this
    // costs nothing in either case.
    context.wait_idle();

    Image depth(context, ImageDesc{
                             .format = format,
                             .extent = extent,
                             .usage = VK_IMAGE_USAGE_DEPTH_STENCIL_ATTACHMENT_BIT,
                             .mip_levels = 1,
                             // The aspect is the easy one to forget, and it has to match
                             // in the view and in every barrier.
                             .aspect = VK_IMAGE_ASPECT_DEPTH_BIT,
                         });

    // A new image is in UNDEFINED. Moving it to the attachment layout once here means no
    // frame ever has to, and loadOp CLEAR discards the contents anyway.
    immediate_submit(context, [&](VkCommandBuffer cmd) {
        depth.transition(cmd, VK_IMAGE_LAYOUT_UNDEFINED,
                         VK_IMAGE_LAYOUT_DEPTH_ATTACHMENT_OPTIMAL);
    });

    context.name(depth.handle(), VK_OBJECT_TYPE_IMAGE, "depth buffer");
    return depth;
}
```

Your `create_depth_buffer`, unchanged apart from **returning** the image rather than
assigning to a member. That difference is what makes the next chapter's resize handler a
single line:

```cpp
depth_ = vkc::create_depth_buffer(context(), depth_format_, extent);
```

Assigning over `depth_` invokes `Image`'s move-assignment operator, which — as chapter 1.11
noted — destroys the old image first. Without that, every resize would leak a full-screen
depth buffer.

The `wait_idle()` at the top is still here and still necessary for the same reason: on a
resize the old depth image may be in use by a frame in flight.

## Words introduced in this chapter

| | |
|---|---|
| **model / view / projection** | the three matrices taking a vertex from its own space to clip space |
| **field of view** | the vertical angle the camera sees; `tan(fov/2)` is the scale it becomes |
| **normalised device coordinates** | what clip space becomes after the divide by `w` |
| **perspective divide** | dividing by `w`, which is what makes distant things small |
| **hyperbolic depth** | stored depth goes as `1 − n/d`, so precision piles up near the camera |
| **near / far plane** | the range the projection maps into the depth buffer |
| **depth buffer** | a per-pixel record of the nearest surface so far |
| **z-fighting** | flickering where two surfaces are too close for the depth buffer to separate |
| **back-face culling** | discarding triangles whose winding shows they face away |
| **reversed-z** | mapping near to 1 and far to 0 for far better float precision |

## Exercises

1. Delete `projection[1][1] *= -1.0F`. The scene turns upside down. Now instead give the viewport a
   negative height and check you get the original image back.
2. Set `storeOp` on the depth attachment to `VK_ATTACHMENT_STORE_OP_STORE`. Nothing changes on
   screen, which is the point: you have just asked the GPU to write several megabytes per frame that
   nobody reads.
3. Set the near plane to `0.0001F`. Look for flickering where the cubes intersect, then read the
   note about reversed-z again.
4. Set the depth compare op to `VK_COMPARE_OP_GREATER`. You are now seeing the *back* of every cube.
5. Turn culling off with `VK_CULL_MODE_NONE` and set the front face to `CLOCKWISE`. Nothing changes,
   because nothing is being culled. Now turn culling back on and watch the cubes turn inside out.
6. Remove the depth attachment entirely and pass `false` for the depth test. The cubes still draw,
   in the order the loop submits them, and it is immediately obvious why sorting by hand is not a
   plan.
7. Add `VK_FORMAT_D16_UNORM` to the front of the `candidates` array. It is mandatory, so it wins,
   and the cubes begin to fight where they intersect.
