`vkCmdDraw`.

## Vulkan takes SPIR-V, not source

Vulkan does not accept shader source. It accepts **SPIR-V**, a binary intermediate
representation, so something has to do the translation.

That is already a real improvement over the OpenGL model, where you handed the driver a
string of GLSL and every vendor's front end understood it slightly differently. SPIR-V
moves parsing out of the driver: there is one compiler, one dialect, and the driver
receives something much closer to machine code.

*When* the translation happens is a separate question, and you have a choice. Shipping
engines do it offline and load the binary. This series does it **when the program
starts**: the samples link Slang's compiler as a library and hand it the `.slang` file
sitting beside the binary. The file next to the executable *is* the shader — edit it,
run again, and the change is there, with no build step in between. The cost is a
library to link and a few milliseconds at startup; chapter 1.9 weighs that properly.

Several languages compile to SPIR-V. This series uses **Slang** — an open-source
shading language stewarded by Khronos, shipped in the Vulkan SDK, with a syntax
descended from HLSL. Two of its properties matter immediately:

- **One file holds every stage of a pipeline**, and compiles to one SPIR-V module with
  one entry point per stage. The vertex-to-fragment interface is a struct that both
  stages share rather than two lists of declarations you keep in step by hand.
- **It is an ordinary modern language**, with generics, modules, interfaces and real
  type checking, which starts to matter around the lighting chapters where the same
  shading code gets reused across a dozen pipelines.

If you know GLSL, nothing here will be unfamiliar for long: the types are spelled
`float3` instead of `vec3`, `mix` is `lerp`, and the layout qualifiers become
attributes. Appendix *Slang for GLSL programmers* is the full table.

Declaring it takes one line:

```cmake title="code/src/1.getting_started/hello_triangle/CMakeLists.txt"
add_chapter(1.7.hello_triangle
    SOURCES main.cpp
    SHADERS triangle.slang
    NO_SCAFFOLD
)
```

One shader file, not two. The build does not compile it — it copies it to
`bin/shaders/1.7.hello_triangle/`, where the running program will find it. There is no
`.spv` file anywhere in this project.

:::note[Where Slang comes from]
CMake looks for an installed Slang and, not finding one, downloads the official release
build and uses that. Nothing to install by hand on either platform. The Vulkan SDK ships
Slang too, and is picked up if you have it.
:::

## The vertex shader

```slang title="code/src/1.getting_started/hello_triangle/triangle.slang"
struct VSOutput {
    float4 position : SV_Position;
    [[vk::location(0)]] float3 colour;
};

static const float2 kPositions[3] = {
    float2( 0.0, -0.5),   // top
    float2( 0.5,  0.5),   // bottom right
    float2(-0.5,  0.5),   // bottom left
};

static const float3 kColours[3] = {
    float3(1.0, 0.0, 0.0),
    float3(0.0, 1.0, 0.0),
    float3(0.0, 0.0, 1.0),
};

[shader("vertex")]
VSOutput vertexMain(uint vertex_index: SV_VulkanVertexID) {
    VSOutput output;
    output.position = float4(kPositions[vertex_index], 0.0, 1.0);
    output.colour = kColours[vertex_index];
    return output;
}
```

`[shader("vertex")]` is what makes a function an entry point and says which stage it
belongs to. The name `vertexMain` is this project's convention, not a rule — Vulkan
takes the entry point by name, and we will pass that name in shortly.

`SV_Position` is a **system-value semantic**: it marks the one output every vertex
shader must write, the clip-space position. GLSL spells this `gl_Position` and makes it
a global; Slang makes it a field of the output struct, which is why the struct is the
return type. Everything else is an ordinary varying, and `[[vk::location(n)]]` is the
slot it travels in.

The vertices are in the shader. There is no vertex buffer in this chapter, deliberately:
buffers, GPU memory and staging uploads are chapter 1.8's subject, and meeting them
here would mean learning two large things at once.

`SV_VulkanVertexID` counts 0, 1, 2 across the three vertices we asked for, so it can
index a constant array directly.

:::caution[`SV_VertexID` is not the same thing]
Slang inherits `SV_VertexID` from HLSL, where the index is relative to the draw. It
compiles to `VertexIndex - BaseVertex`, which pulls in SPIR-V's `DrawParameters`
capability — so the validation layers will reject the module unless you enabled
`shaderDrawParameters` on the device.

`SV_VulkanVertexID` is Vulkan's `VertexIndex` builtin with nothing subtracted and
nothing to enable. The two agree whenever `firstVertex` is 0, which is why the mistake
can survive a long time before it bites. `SV_InstanceID` and `SV_VulkanInstanceID` are
the same story.
:::

:::caution[Vulkan's y axis points down]
In clip space, x and y run -1 to 1 with **y pointing down** the screen, and z runs
**0 to 1**. OpenGL has y pointing up and z running -1 to 1.

So `-0.5` in y is the *top* of the screen here. A shader or projection matrix copied
from OpenGL material renders upside down, and a depth buffer set up for OpenGL's range
produces results that look almost right, which is worse.

This project sets `GLM_FORCE_DEPTH_ZERO_TO_ONE` globally to deal with the depth half.
The y flip is handled where it arises, and flagged each time.
:::

## The fragment shader

```slang title="code/src/1.getting_started/hello_triangle/triangle.slang"
[shader("fragment")]
float4 fragmentMain(VSOutput input) : SV_Target {
    return float4(input.colour, 1.0);
}
```

Same file, a few lines further down. One invocation per pixel the triangle covers.

It takes the **same `VSOutput` struct** the vertex shader returned. That is the part
worth pausing on: the interface between the two stages is one declaration, so the two
ends cannot drift apart. In GLSL this is a list of `out` declarations in one file and a
matching list of `in` declarations in another, and keeping the `location` numbers and
types in step is your problem. Chapter 1.9 looks at what the validation layers do and
do not catch when they disagree.

`SV_Target` is the semantic for a colour attachment output — `SV_Target0` through
`SV_TargetN` once there is more than one attachment to address.

`input.colour` is not the value any single vertex wrote. The hardware **interpolates**
the three vertex outputs across the triangle, weighted by how close the pixel is to
each corner, which is why the result is a smooth gradient rather than three flat
regions. That interpolation is free, it is done by fixed-function hardware, and it is
the basis of nearly everything in the lighting chapters — normals, texture coordinates
and world positions all reach the fragment shader the same way.

## Compiling the shader

`load_shader` is longer than anything else in this chapter that is not the pipeline, and
almost all of it is Slang's compiler API rather than Vulkan. The shape is four steps:

```cpp title="code/src/1.getting_started/hello_triangle/main.cpp"
// 1. The compiler itself, and its standard library.
Slang::ComPtr<slang::IGlobalSession> global;
slang::createGlobalSession(global.writeRef());

// 2. What to generate, and where to look for source.
slang::TargetDesc target{};
target.format = SLANG_SPIRV;
target.profile = global->findProfile("spirv_1_6");
// ... session_desc.searchPaths points at bin/shaders/1.7.hello_triangle/

// 3. Load the file and collect its entry points.
slang::IModule* module = session->loadModule("triangle", diagnostics.writeRef());

// 4. Compose, link, and ask for the bytes.
composed->link(linked.writeRef(), diagnostics.writeRef());
linked->getTargetCode(0, spirv.writeRef(), diagnostics.writeRef());
```

The global session is the expensive object — it loads the standard module and sets up
the compiler — and it is meant to be created once and shared. There is one shader here
so it hardly matters; from 1.8, `vkcommon` caches it.

Step 3 is where the "one file, both stages" property becomes concrete.
`getDefinedEntryPointCount()` reports how many `[shader("...")]` functions the file has,
and composing those with the module before linking is what produces a single SPIR-V
binary containing all of them.

Every call takes a `diagnostics` blob rather than returning an error string, and if you
skip checking them you get a null module and no idea why. Break the shader on purpose
and you get Slang's own diagnostics, with the line and a caret:

```
error[E30027]: member not found
  --> quad.slang:67:12
   |
67 | output.flat_colour = input.colour;
   |        ^^^^^^^^^^^ 'flat_colour' is not a member of 'VSOutput'.
```

:::caution[The matrix layout default is wrong for glm]
`SessionDesc::defaultMatrixLayoutMode` defaults to row-major, and a `glm::mat4` is
sixteen floats stored **column** by column. Leave the default and every transform comes
out transposed — it still draws, nothing errors, it is simply wrong.

Setting `SLANG_MATRIX_LAYOUT_COLUMN_MAJOR` fixes it, and confusingly makes Slang emit a
`RowMajor` decoration in the SPIR-V. That is not a contradiction: Slang pairs that
decoration with `OpVectorTimesMatrix`, and the two conventions cancel. `slangc`'s command
line defaults to column-major; the API does not. This does not matter until chapter
1.12, which is exactly when it will cost you an afternoon if you have not read this.
:::

## Shader modules

```cpp title="code/src/1.getting_started/hello_triangle/main.cpp"
const VkShaderModuleCreateInfo info{
    .codeSize = spirv->getBufferSize(),
    .pCode = static_cast<const uint32_t*>(spirv->getBufferPointer()),
};
```

After all that, the Vulkan part is six lines. A shader module is just the SPIR-V blob
handed to the driver. It is *not* compiled to machine code here — that happens at
pipeline creation, when the driver finally knows the rest of the state the shader will
run under.

Note `codeSize` is in **bytes** while `pCode` is a `const uint32_t*`. SPIR-V is a stream
of 32-bit words and must be 4-byte aligned; Slang's blob already is, and that is worth
checking if you ever change where the bytes come from.

There is **one** module here, not two, because `triangle.slang` compiles to one binary.
Both pipeline stages point at it and pick their entry point by name:

```cpp title="code/src/1.getting_started/hello_triangle/main.cpp"
const VkShaderModule shader = load_shader("triangle.slang");

const VkPipelineShaderStageCreateInfo stages[2]{
    {
        .stage = VK_SHADER_STAGE_VERTEX_BIT,
        .module = shader,
        .pName = "vertexMain",
    },
    {
        .stage = VK_SHADER_STAGE_FRAGMENT_BIT,
        .module = shader,
        .pName = "fragmentMain",
    },
};
```

A SPIR-V module can hold as many entry points as you like — that has always been true
of the format, and `pName` has always been how you select one. It is just that glslang
never emitted more than one, and always called it `main`, so the field looked like
boilerplate. With Slang it does real work.

The build passes `-fvk-use-entrypoint-name` to keep the SPIR-V entry points named after
the Slang functions. Without it, a module with a single entry point gets renamed to
`main`, and the names stop matching what `pName` asks for.

## The pipeline

Here is the idea that defines Vulkan's approach to state.

In OpenGL you set state one call at a time — bind a shader, enable blending, set a depth
function — and the driver works out what that combination means at draw time, every
draw. Vulkan makes you declare the whole configuration up front and compiles it into an
immutable `VkPipeline`.

That is why pipeline creation is a large function and why it is a one-off cost:
expensive at creation, nearly free to bind.

The pieces, briefly:

| Struct | Decides |
|---|---|
| `pStages` | Which shaders, and their entry points |
| `pVertexInputState` | Vertex buffer layout — empty here |
| `pInputAssemblyState` | How vertices form primitives |
| `pViewportState` | How many viewports and scissors |
| `pRasterizationState` | Fill mode, culling, winding order |
| `pMultisampleState` | Anti-aliasing sample count |
| `pColorBlendState` | How output combines with what is there |
| `pDynamicState` | Which state is *not* baked in |

A few fields deserve comment.

```cpp title="code/src/1.getting_started/hello_triangle/main.cpp"
.cullMode = VK_CULL_MODE_NONE,
.frontFace = VK_FRONT_FACE_COUNTER_CLOCKWISE,
```

No culling yet. Face culling gets its own chapter; turning it on now would silently
discard the triangle if its winding happened to be the other way, and "nothing is drawn
and nothing is wrong" is a poor place to start debugging.

```cpp title="code/src/1.getting_started/hello_triangle/main.cpp"
.colorWriteMask = VK_COLOR_COMPONENT_R_BIT | VK_COLOR_COMPONENT_G_BIT |
                  VK_COLOR_COMPONENT_B_BIT | VK_COLOR_COMPONENT_A_BIT,
```

Even with blending disabled, the write mask still has to list the channels to write.
Leave it at zero — which is what value-initialising the struct gives you — and you get a
black screen with no error at all.

## Dynamic state

```cpp title="code/src/1.getting_started/hello_triangle/main.cpp"
const VkDynamicState dynamic_states[2]{
    VK_DYNAMIC_STATE_VIEWPORT,
    VK_DYNAMIC_STATE_SCISSOR,
};
```

Almost everything is baked in, which would mean rebuilding the pipeline every time the
window resized. Declaring the viewport and scissor dynamic means supplying them per
frame instead:

```cpp title="code/src/1.getting_started/hello_triangle/main.cpp"
vkCmdSetViewport(frame.cmd, 0, 1, &viewport);
vkCmdSetScissor(frame.cmd, 0, 1, &scissor);
```

The counts in `pViewportState` still matter even though the pointers are null: the
pipeline needs to know there is one of each.

The viewport's `minDepth` and `maxDepth` of 0 to 1 are Vulkan's depth range again.

## The pipeline layout

```cpp title="code/src/1.getting_started/hello_triangle/main.cpp"
const VkPipelineLayoutCreateInfo layout_info{
    .setLayoutCount = 0,
    .pushConstantRangeCount = 0,
};
```

The layout declares what external data the shaders can see — descriptor sets and push
constants. This shader reads nothing at all, so the layout is empty. It still has to
exist, and it comes into its own in chapter 1.10.

## No render pass

```cpp title="code/src/1.getting_started/hello_triangle/main.cpp"
const VkPipelineRenderingCreateInfo rendering_info{
    .colorAttachmentCount = 1,
    .pColorAttachmentFormats = &format_,
    .depthAttachmentFormat = VK_FORMAT_UNDEFINED,
};

const VkGraphicsPipelineCreateInfo pipeline_info{
    .pNext = &rendering_info,
    // ...
    .renderPass = VK_NULL_HANDLE,
};
```

With dynamic rendering there is no `VkRenderPass` for the pipeline to be compatible
with, so it is told the attachment formats directly.

:::caution[These must match]
The formats here must match the `VkRenderingInfo` used at draw time. A mismatch means
nothing is drawn, and validation's complaint about render pass compatibility is not
obvious the first time you read it.
:::

Once the pipeline exists, the shader module has been consumed and can be destroyed
immediately.

## The draw

```cpp title="code/src/1.getting_started/hello_triangle/main.cpp"
vkCmdBindPipeline(frame.cmd, VK_PIPELINE_BIND_POINT_GRAPHICS, pipeline_);
vkCmdSetViewport(frame.cmd, 0, 1, &viewport);
vkCmdSetScissor(frame.cmd, 0, 1, &scissor);
vkCmdDraw(frame.cmd, 3, 1, 0, 0);
```

Three vertices, one instance, starting at vertex 0 and instance 0. The vertex shader
runs three times, the triangle is rasterised, and the fragment shader runs once per
covered pixel.

After six chapters of setup, that is the draw call.

## Running it

```bash
./code/out/build/linux-debug/bin/1.7.hello_triangle
```

A triangle with a red apex, green bottom-right and blue bottom-left, blending smoothly
between them. Resize the window — the triangle scales with it, because the viewport is
dynamic and no pipeline rebuild is needed.

## What you have built

Worth taking stock. The program now:

- opens a window and handles its events
- creates an instance with validation layers and a debug messenger
- selects a GPU and creates a device with the features it needs
- builds a swapchain and rebuilds it when the window changes
- records command buffers, transitions image layouts, and renders
- keeps the CPU and GPU working simultaneously with correct synchronisation
- compiles shaders, builds a pipeline, and draws

That is the foundation. Everything from here — textures, lighting, shadows, PBR — is
built on exactly this.

:::note[From the next chapter, `vkcommon`]
Chapters 1.1 to 1.7 each built all of this by hand. From 1.8 onward the samples use a
shared library, `vkcommon`, which contains precisely the code you have just read:
`Window`, `Context`, `Swapchain` and `FrameContext`.

Nothing new is hidden in it. Each chapter states exactly which helper replaced the code
it taught, and you can read any of it at `code/common/scaffold/`.
:::

## Exercises

1. Change the vertex positions so the triangle is upside down. Convince yourself which
   way y points.
2. Make all three vertices the same colour and watch the gradient disappear — the
   interpolation is still happening, between three identical values.
3. Set `cullMode` to `VK_CULL_MODE_BACK_BIT`. The triangle vanishes or does not,
   depending on its winding. Then reverse the vertex order and watch it flip.
4. Add a second `vkCmdDraw` after the first. Nothing changes, because it draws the same
   three vertices in the same place. Making the second one useful is what push
   constants are for, in 1.10.
5. Set `polygonMode` to `VK_POLYGON_MODE_LINE` for a wireframe. Note this needs the
   `fillModeNonSolid` feature enabled at device creation — validation will tell you so
   if you forget, which is a good demonstration of why features are opt-in.
6. Rename `fragmentMain` in the shader to something else, rebuild, and read the error.
   Then fix it by changing `pName` rather than the shader. Two different places to say
   the same name is the cost of one module holding both stages, and it is worth feeling
   once.
