Chapter 1.2 built a `VkInstance`, which is a connection to *the Vulkan implementation on
this machine*. It is not a connection to a GPU. This chapter finds a GPU, asks it what it
can do, and opens a connection to it.

That connection is the object every remaining chapter in the series hangs off, so it is
worth going slowly here.

## What a GPU actually is

Worth being concrete, because the rest of the chapter only makes sense if this part is
solid.

A GPU is a **separate computer inside your computer**. It has its own processors, its own
memory, and its own idea of what it is doing. On a desktop with a discrete graphics card
it is physically a separate board, connected over a bus called PCIe:

```
   ┌───────────────────────┐        ┌───────────────────────┐
   │        CPU            │        │        GPU            │
   │   a few fast cores    │        │  thousands of small   │
   │                       │        │  cores in lockstep    │
   │   ┌───────────────┐   │  PCIe  │   ┌───────────────┐   │
   │   │  system RAM   │◀──┼────────┼──▶│  video RAM    │   │
   │   │   32 GB       │   │ ~30x   │   │   16 GB       │   │
   │   └───────────────┘   │ slower │   └───────────────┘   │
   └───────────────────────┘        └───────────────────────┘
```

Three consequences follow, and they explain most of Vulkan's shape.

**You cannot call a function on it.** Your CPU program cannot jump into GPU code the way it
calls an ordinary function. It has to write a *description of work to be done* somewhere
both can see, and tell the GPU that it is there. That is why chapter 1.5 is about command
buffers: a command buffer is that description.

**It runs in parallel with you, not in step.** When you hand it work, it starts when it
starts and finishes when it finishes. Your program carries on immediately. Everything in
chapter 1.6 exists because of this one fact.

**Its memory is not your memory.** A pointer in your program means nothing to it. Getting
data across is a deliberate copy over that slow bus, which is chapter 1.8.

A modern GPU also runs **thousands of threads at once**, not a few dozen like a CPU, and
they run in lockstep groups. That is why shading a million pixels is cheap, and why a
branch that differs between neighbouring pixels is expensive — both come up later.

## Handles, and which ones you own

Chapter 1.2 introduced the **handle**: an opaque token identifying an object that lives
inside the driver. This chapter adds the half that determines whether you must clean it up.

```
  CREATED    vkCreateDevice, vkCreateBuffer      → yours; you must vkDestroy* it
  RETRIEVED  vkEnumeratePhysicalDevices,         → the driver's; there is no destroy
             vkGetDeviceQueue                       function and you must not invent one
```

This chapter meets both kinds, and the destructor below is conspicuously shorter than the
list of things created, for exactly that reason.

## The three ideas

| | |
|---|---|
| **`VkPhysicalDevice`** | A GPU that exists in the machine. You do not create it; you enumerate it and ask it questions. |
| **Queue family** | A group of queues that can do the same kinds of work. Commands are never "executed" — they are submitted to a queue. |
| **`VkDevice`** | Your connection to one physical device, with exactly the features you asked for switched on and nothing else. |

## What we need from a device

```cpp title="code/src/1.getting_started/devices_and_queues/main.cpp"
namespace {

constexpr std::array kRequiredDeviceExtensions = {
    VK_KHR_SWAPCHAIN_EXTENSION_NAME,
};
```

Chapter 1.2 asked for *instance* extensions, which extend the API before a device exists.
These are **device** extensions, which extend what a particular GPU can do. Separate lists,
separate enumeration functions, and confusing the two produces
`VK_ERROR_EXTENSION_NOT_PRESENT` from whichever create call you fed it to.

We need exactly one. `VK_KHR_swapchain` is what lets a device present images to a window, and
it will always be an extension rather than core, because not every Vulkan device has a screen
attached — a compute node in a rack runs the same API with no display at all.

That the list is one line long is a direct consequence of the Vulkan 1.3 baseline. Dynamic
rendering and `synchronization2` were folded into the core specification in 1.3, so unlike a
1.0-era tutorial there is no `VK_KHR_dynamic_rendering`, no `VK_KHR_synchronization2` and no
`VK_KHR_buffer_device_address` to ask for here.

## The surface comes first

```cpp title="code/src/1.getting_started/devices_and_queues/main.cpp"
    void create_surface() {
        if (!SDL_Vulkan_CreateSurface(window_.handle(), instance_.handle(), nullptr,
                                      &surface_)) {
            throw std::runtime_error(
                std::format("SDL_Vulkan_CreateSurface failed: {}", SDL_GetError()));
        }
    }
```

A **surface** (`VkSurfaceKHR`) is Vulkan's handle for "a thing you can draw into that the
window system owns". It is the bridge between two worlds that otherwise know nothing about
each other: Vulkan has no concept of a window, and your window system has no concept of a
GPU.

Creating one is platform-specific — on Wayland it wraps a `wl_surface`, on Windows an `HWND`
— which is why SDL does it, having created the window in the first place.

The surface belongs to the **instance**, not to a device, and it has to exist before we pick
a GPU. That ordering is not arbitrary:

```
   instance ──▶ surface ──▶ "can this GPU present to that surface?" ──▶ pick a GPU
```

You cannot ask the question without both halves. In a laptop with a discrete GPU and
integrated graphics it is entirely possible for one of them to be unable to present to a
given window — the display may physically be wired to the other one. Vulkan makes you check
rather than assume.

## Asking what exists

```cpp title="code/src/1.getting_started/devices_and_queues/main.cpp"
const char* device_type_name(VkPhysicalDeviceType type) {
    switch (type) {
        case VK_PHYSICAL_DEVICE_TYPE_DISCRETE_GPU: return "discrete GPU";
        case VK_PHYSICAL_DEVICE_TYPE_INTEGRATED_GPU: return "integrated GPU";
        case VK_PHYSICAL_DEVICE_TYPE_VIRTUAL_GPU: return "virtual GPU";
        case VK_PHYSICAL_DEVICE_TYPE_CPU: return "CPU";
        default: return "other";
    }
}
```

Purely for the log, but the list teaches something. A **discrete** GPU is a separate card
with its own memory. An **integrated** GPU shares the CPU's memory and sits on the same chip
— slower, far more power-efficient, and the only option on most laptops. A **CPU** device is
a software implementation such as lavapipe that pretends to be a GPU: genuinely useful for
testing on a machine with no driver, far too slow for this series. A **virtual** GPU is a
paravirtualised device inside a virtual machine.

```cpp title="code/src/1.getting_started/devices_and_queues/main.cpp"
bool device_supports_extensions(VkPhysicalDevice gpu) {
    uint32_t count = 0;
    VK_CHECK(vkEnumerateDeviceExtensionProperties(gpu, nullptr, &count, nullptr));
    std::vector<VkExtensionProperties> available(count);
    VK_CHECK(vkEnumerateDeviceExtensionProperties(gpu, nullptr, &count, available.data()));

    return std::ranges::all_of(kRequiredDeviceExtensions, [&](const char* required) {
        return std::ranges::any_of(available, [required](const VkExtensionProperties& e) {
            return std::strcmp(required, e.extensionName) == 0;
        });
    });
}
```

Chapter 1.2's count-then-fill idiom, against a *device* this time.

`std::strcmp` rather than `==` here, because both sides are `const char*` and comparing
those with `==` compares **addresses** — asking "are these two pointers the same pointer",
which they never are. Chapter 1.2's helpers took a `std::string_view` parameter and could
use `==` honestly; this one iterates an array of `const char*` and has to be explicit.

## Queues: the part with no OpenGL equivalent

This is the idea most worth slowing down for.

A **queue** is a channel into the GPU. You do not call the GPU; you post work to a queue, and
the GPU takes work off it and runs it when it gets to it. Posting is called **submitting**,
and what you submit is a command buffer — a recorded list of things to do, which chapter 1.5
builds.

```
   CPU                                        GPU
   record ──▶ [command buffer]
                     │
                     │ vkQueueSubmit2()  ← returns immediately
                     ▼
              ┌─────────────┐
              │    queue    │ ──────────────▶ executes, eventually
              └─────────────┘
```

Two properties drive everything later. **Work on a queue runs asynchronously**: the submit
call returns before anything has happened. And **there is no "current" queue** — OpenGL had
one implicit context that every call acted on; Vulkan has handles, and you say which queue
every time.

A **queue family** is a group of queues that can do the same kinds of work. A GPU advertises
its families, each declaring which categories it supports:

| Capability | What it covers |
|---|---|
| `GRAPHICS` | drawing — vertex and fragment shaders, rasterisation |
| `COMPUTE` | general-purpose GPU programs |
| `TRANSFER` | copying memory and images |
| `SPARSE_BINDING` | binding memory to resources piecewise; rare, ignore for now |

Real hardware typically offers a general family that does everything, a compute-only family,
and a transfer-only family backed by a dedicated copy engine. Using the specialised ones is a
genuine optimisation — a texture upload on the transfer queue does not compete with drawing.

It also has a real cost. A resource written by one family and read by another needs an
explicit **queue family ownership transfer**: extra bookkeeping in a barrier, which chapter
1.5 introduces. Getting one wrong produces corruption that appears on some hardware and not
others.

So this series uses **one queue that does everything**.

```cpp title="code/src/1.getting_started/devices_and_queues/main.cpp"
std::optional<uint32_t> find_universal_queue_family(VkPhysicalDevice gpu,
                                                    VkSurfaceKHR surface) {
    uint32_t count = 0;
    vkGetPhysicalDeviceQueueFamilyProperties(gpu, &count, nullptr);
    std::vector<VkQueueFamilyProperties> families(count);
    vkGetPhysicalDeviceQueueFamilyProperties(gpu, &count, families.data());

    for (uint32_t i = 0; i < count; ++i) {
        constexpr VkQueueFlags wanted = VK_QUEUE_GRAPHICS_BIT | VK_QUEUE_COMPUTE_BIT;
        if ((families[i].queueFlags & wanted) != wanted) {
            continue;
        }
        VkBool32 can_present = VK_FALSE;
        VK_CHECK(vkGetPhysicalDeviceSurfaceSupportKHR(gpu, i, surface, &can_present));
        if (can_present == VK_TRUE) {
            return i;
        }
    }
    return std::nullopt;
}
```

Three details in that loop.

**`queueFlags` is a bitmask.** Each capability is one bit, and the test is
`(flags & wanted) != wanted`, *not* `flags & wanted`, because we need **both** bits:

```
  wanted        = GRAPHICS | COMPUTE   = 0b0011
  a family with   TRANSFER | COMPUTE   = 0b0110

  flags & wanted            = 0b0010   → non-zero, so `if (flags & wanted)` passes. Wrong.
  (flags & wanted) != wanted           → 0b0010 != 0b0011, correctly rejected.
```

**Presentation is a separate question.** A family that can draw does not necessarily have any
route to get pixels onto *this particular surface*, so `vkGetPhysicalDeviceSurfaceSupportKHR`
asks about the pair. It answers in a `VkBool32` rather than a C++ `bool` because the API is C
and needs a type of known size.

**Not every query returns a `VkResult`.** `vkGetPhysicalDeviceQueueFamilyProperties` returns
`void` — it cannot fail, so it does not pretend it might, which is why those two lines are not
wrapped in `VK_CHECK`.

:::note[`VK_QUEUE_TRANSFER_BIT` is implied]
Any family with graphics or compute support can do transfers, whether or not it advertises the
bit. Only transfer-*only* families are required to set it, so testing for it explicitly would
reject families that support it perfectly well.
:::

```cpp title="code/src/1.getting_started/devices_and_queues/main.cpp"
int score_device(const VkPhysicalDeviceProperties& props) {
    switch (props.deviceType) {
        case VK_PHYSICAL_DEVICE_TYPE_DISCRETE_GPU: return 3;
        case VK_PHYSICAL_DEVICE_TYPE_INTEGRATED_GPU: return 2;
```

Deliberately crude. A real application would weigh memory size, driver version and the user's

## Enumerating and choosing

```cpp title="code/src/1.getting_started/devices_and_queues/main.cpp"
    void select_physical_device() {
        uint32_t count = 0;
        VK_CHECK(vkEnumeratePhysicalDevices(instance_.handle(), &count, nullptr));
        if (count == 0) {
            throw std::runtime_error(
                "No Vulkan-capable GPU found. Check your graphics driver.");
        }
        std::vector<VkPhysicalDevice> devices(count);
        VK_CHECK(vkEnumeratePhysicalDevices(instance_.handle(), &count, devices.data()));

        spdlog::info("Found {} physical device(s):", count);

        int best_score = -1;
        std::string rejections;
```

The zero case is handled separately because "no GPU at all" and "no *suitable* GPU" deserve
different messages.

```cpp title="code/src/1.getting_started/devices_and_queues/main.cpp"
        for (VkPhysicalDevice candidate : devices) {
            VkPhysicalDeviceProperties props{};
            vkGetPhysicalDeviceProperties(candidate, &props);
            spdlog::info("  {} ({})", props.deviceName, device_type_name(props.deviceType));

            if (props.apiVersion < VK_API_VERSION_1_3) {
                rejections += std::format("\n  {}: reports Vulkan {}.{}, needs 1.3",
                                          props.deviceName,
                                          VK_API_VERSION_MAJOR(props.apiVersion),
                                          VK_API_VERSION_MINOR(props.apiVersion));
                continue;
            }
            if (!device_supports_extensions(candidate)) {
                rejections +=
                    std::format("\n  {}: no VK_KHR_swapchain", props.deviceName);
                continue;
            }
            const std::optional<uint32_t> family =
                find_universal_queue_family(candidate, surface_);
            if (!family.has_value()) {
                rejections += std::format(
                    "\n  {}: no queue family with graphics + compute + present",
                    props.deviceName);
                continue;
            }
```

`VkPhysicalDeviceProperties` is a large struct of facts: name, vendor, type, the API version
the driver implements, and a `limits` sub-struct holding several dozen numbers — maximum
texture size, maximum push constant bytes, maximum bound descriptor sets. Later chapters read
individual limits out of it.

Collecting the rejections rather than discarding them is worth the six extra lines. "No
suitable GPU found" is a maddening error to receive; "your GPU reports Vulkan 1.2, needs 1.3"
is one you can act on.

:::note[Three different version numbers]
A common confusion, and all three appear in this series:

```
  vkEnumerateInstanceVersion()   the LOADER's version   (1.2 printed this)
  props.apiVersion               the DRIVER's version   (checked here)
  VkApplicationInfo::apiVersion  what you PROMISED      (1.2 set this to 1.3)
```

The loader's is usually highest and constrains nothing. The driver's is the one that can stop
you.
:::

```cpp title="code/src/1.getting_started/devices_and_queues/main.cpp"
            const int score = score_device(props);
            if (score > best_score) {
                best_score = score;
                gpu_ = candidate;
                gpu_properties_ = props;
                queue_family_ = *family;
            }
        }

        if (gpu_ == VK_NULL_HANDLE) {
            throw std::runtime_error(

        }

```

`*family` dereferences the `optional` to get the number out, which is only legal because
`has_value()` was checked above. The queue family index is stored alongside the device,
because it was found by querying *that* device and means nothing for any other one.

## The logical device

A `VkDevice` is often called a **logical device**, and the distinction is worth stating:

```
  PHYSICAL   the hardware. Exists whether or not your program runs.
             You ask it questions. Shared by every program on the machine.

  LOGICAL    your program's connection to it, configured as you asked.
             Created and destroyed. Owns everything you make.
             Two programs on one GPU have two separate logical devices.
```

Everything from here on — buffers, images, pipelines, shaders — is created from the logical
device and dies with it.

```cpp title="code/src/1.getting_started/devices_and_queues/main.cpp"
    void create_device() {
        const float priority = 1.0F;
        const VkDeviceQueueCreateInfo queue_info{
            .sType = VK_STRUCTURE_TYPE_DEVICE_QUEUE_CREATE_INFO,
            .pNext = nullptr,
            .flags = 0,
            .queueFamilyIndex = queue_family_,
            .queueCount = 1,
            .pQueuePriorities = &priority,
        };
```

**Queues are not created individually.** `VkDeviceQueueCreateInfo` does not create a
queue — it is a request attached to device creation, saying "when you make the device,
give me this many queues from this family". You ask a family for a number of them and
they arrive as part of the device. `pQueuePriorities` is an array with one entry per requested queue, each
between `0.0` and `1.0`; it matters only when you request several, and even then it is a hint
the driver may ignore.

`priority` is a named local rather than a literal because the struct stores a *pointer* to it,
read later when `vkCreateDevice` runs. A temporary would be destroyed before then. Chapter 1.2
met this with `messenger_info`, and it recurs throughout Vulkan.

### Features, and the `pNext` chain

```cpp title="code/src/1.getting_started/devices_and_queues/main.cpp"
        VkPhysicalDeviceVulkan13Features features13{};
        features13.sType = VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_VULKAN_1_3_FEATURES;
        features13.synchronization2 = VK_TRUE;   // the barrier form used from 1.5
        features13.dynamicRendering = VK_TRUE;   // no render passes, ever

        VkPhysicalDeviceVulkan12Features features12{};
        features12.sType = VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_VULKAN_1_2_FEATURES;
        features12.pNext = &features13;
        features12.bufferDeviceAddress = VK_TRUE;
        features12.descriptorIndexing = VK_TRUE;

        VkPhysicalDeviceFeatures2 features2{};
        features2.sType = VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_FEATURES_2;
        features2.pNext = &features12;
        features2.features.samplerAnisotropy = VK_TRUE;
```

`VkPhysicalDeviceVulkan13Features` and `VkPhysicalDeviceVulkan12Features` are what that
growth looks like in practice. Rather than one ever-expanding feature struct, each Vulkan
version gets its own, holding the features that version added — so the 1.2 struct carries
`bufferDeviceAddress` and `descriptorIndexing`, and the 1.3 struct carries
`synchronization2` and `dynamicRendering`.

Chapter 1.2 explained *why* `pNext` exists — a frozen C API cannot grow its structs, so new
functionality arrives as new structs chained on. Here it does real work, and the chain is
built backwards:

```
  &features2 ──pNext──▶ features12 ──pNext──▶ features13 ──pNext──▶ nullptr
   (1.0 features)        (1.2 features)        (1.3 features)

  passed as VkDeviceCreateInfo::pNext — the driver walks the list,
  reads each sType, and applies the ones it recognises
```

**A feature is an optional capability** that the device may or may not support, and that you
must switch on even when it does. Using one you did not enable is *undefined behaviour* rather
than an error — it may work on your machine and corrupt memory on someone else's.

The structs are value-initialised with `{}` so every field starts `VK_FALSE`, and only the
wanted ones are switched on. That is not tidiness: asking for everything can cost performance
merely by enabling it, and some drivers refuse device creation over a feature the hardware
cannot provide.

They are assigned member by member rather than with designated initialisers, which is the one
place this series breaks its own habit. These structs have dozens of fields each, and writing
them all out would take half a page to say "false" sixty times.

The five enabled here are what the series is built on. Each names something not yet explained,
so briefly:

- **`dynamicRendering`** — lets you describe what you are drawing into at the moment you draw,
  rather than building a `VkRenderPass` and a `VkFramebuffer` up front. Those are the two
  objects a 1.0-era tutorial spends chapters on; we never create either. Chapter 1.5 uses this.
- **`synchronization2`** — the modern form of *barriers*, the instructions that tell the GPU
  "finish this before starting that". Chapter 1.5 writes the first one.
- **`bufferDeviceAddress`** — lets a shader hold a raw 64-bit pointer into GPU memory instead
  of reaching data through a binding. Part 4 is where it pays off.
- **`descriptorIndexing`** — a *descriptor* is the small object that tells a shader where a
  buffer or texture lives (chapter 1.10). This lets a shader index into a large array of them,
  which is what "bindless" means. Part 3 uses it.
- **`samplerAnisotropy`** — a *sampler* is the object describing how a texture is read
  (chapter 1.11); this improves quality on surfaces seen at a steep angle.

`samplerAnisotropy` lives in `features2.features` rather than in a version struct because it is
a Vulkan 1.0 feature, and the 1.0 features all live in one `VkPhysicalDeviceFeatures` struct
nested inside `VkPhysicalDeviceFeatures2`.

:::caution[Asking is not checking]
Setting a feature to `VK_TRUE` *requests* it. If the device does not support it,
`vkCreateDevice` fails. A robust application calls `vkGetPhysicalDeviceFeatures2` first and
adapts; this series asks for a small set any Vulkan 1.3 device provides, and lets the failure be
loud. Exercise 2 makes it fail on purpose.
:::

Vulkan 1.0.13; the instance layer from 1.2 covers the device too.

## Loading device functions — the trap

```cpp title="code/src/1.getting_started/devices_and_queues/main.cpp"
        VK_CHECK(vkCreateDevice(gpu_, &create_info, nullptr, &device_));

        volkLoadDevice(device_);

        vkGetDeviceQueue(device_, queue_family_, 0, &queue_);
    }
```

This is volk's third and last tier, and the order of these three lines is not stylistic.
`vkGetDeviceQueue` is a device-level function, and every device-level function pointer is null
until `volkLoadDevice` runs. Call it first and you jump to address zero — a segfault with an
empty stack trace, on a line that looks perfectly correct.

There is a second reason to prefer it over the alternative `volkLoadInstance`. When several
drivers are installed the loader inserts a **dispatch table** — an extra indirection on every
call — to pick the right one. `volkLoadDevice` fetches the functions from the device itself,
skipping that indirection for the rest of the program's life.

`vkGetDeviceQueue` does not create anything: the queue already exists, having come with the
device, and this retrieves a handle to queue `0` of the chosen family. Another retrieved
handle, another thing with no destroy function.

## Memory allocation

```cpp title="code/src/1.getting_started/devices_and_queues/main.cpp"
    void create_allocator() {
        VmaVulkanFunctions functions{};
        functions.vkGetInstanceProcAddr = vkGetInstanceProcAddr;
        functions.vkGetDeviceProcAddr = vkGetDeviceProcAddr;
```

Vulkan's memory API will allocate a block of GPU memory when asked. It will not decide which
*kind* of memory a texture belongs in, cut that block into pieces for individual resources, or
reorganise when you run out.

And there is a hard limit waiting: `maxMemoryAllocationCount` is commonly **4096**. One
allocation per resource runs out on a scene of any size, so a real program allocates a few large
blocks and hands out slices of them — which means writing an allocator, complete with alignment
and free lists, before drawing anything.

The [Vulkan Memory Allocator](https://github.com/GPUOpen-LibrariesAndSDKs/VulkanMemoryAllocator)
does all of that and is what most shipping engines use. Chapter 1.8 is where it starts being
used; it is created here because it needs the device.

Those two function pointers are the one piece of wiring the combination requires. VMA would
normally call `vkAllocateMemory` and friends as ordinary global symbols, and `VK_NO_PROTOTYPES`
means there are none.

`vkGetInstanceProcAddr` and `vkGetDeviceProcAddr` are the two functions that make the whole
loader work: given a name, each returns a pointer to the function with that name, at the
instance and device level respectively. They are how volk filled its tables in the first
place. Handing VMA just these two lets it look up everything else it needs by itself.

```cpp title="code/src/1.getting_started/devices_and_queues/main.cpp"
        const VmaAllocatorCreateInfo info{
            .flags = VMA_ALLOCATOR_CREATE_BUFFER_DEVICE_ADDRESS_BIT,
            .physicalDevice = gpu_,
            .device = device_,
            .preferredLargeHeapBlockSize = 0,
            .pAllocationCallbacks = nullptr,
            .pDeviceMemoryCallbacks = nullptr,
            .pHeapSizeLimit = nullptr,
            .pVulkanFunctions = &functions,
            .instance = instance_.handle(),
            .vulkanApiVersion = VK_API_VERSION_1_3,
            .pTypeExternalMemoryHandleTypes = nullptr,
        };
        VK_CHECK(vmaCreateAllocator(&info, &allocator_));
    }
```

`VMA_ALLOCATOR_CREATE_BUFFER_DEVICE_ADDRESS_BIT` has to match the `bufferDeviceAddress` feature
above. With it set, VMA adds the corresponding usage flag to its internal allocations, and a
buffer whose memory was not allocated that way cannot have its address taken. Part 4 depends on
this entirely; enabling it here costs nothing.

`preferredLargeHeapBlockSize = 0` means "use VMA's default", currently 256 MiB — the size of the
blocks it carves resources out of.

`vkGetPhysicalDeviceMemoryProperties` fills a `VkPhysicalDeviceMemoryProperties` struct
describing every pool of memory the chosen GPU can allocate from, and like the other

fail.

A **heap** is a physical pool of memory the GPU can use. `VK_MEMORY_HEAP_DEVICE_LOCAL_BIT` means
it is memory the GPU reads fastest — on a discrete card, the RAM on the board itself. A heap
without that bit is system RAM reached across PCIe.

Two methods here are new, and neither appeared in the sample.

**`set_debug_name`** is the payoff for enabling `VK_EXT_debug_utils` back in 1.2. Vulkan
handles are opaque numbers, so an unnamed object in a validation message reads
`VkImage 0x5d2f1a` — technically complete and useless. Name it and the same message says

says which kind this one is. From chapter 1.8 onward the samples name things routinely.

**`wait_idle`** blocks the CPU until the GPU has finished absolutely everything. It is the
crudest possible synchronisation, and the comment is a warning: it is correct at teardown,
where you must not destroy an object the GPU is still reading, and correct during a resize.
Using it in a frame loop makes the CPU and GPU take turns instead of working at once, which
costs roughly half your performance. Chapter 1.6 builds the tools that make it unnecessary.

```cpp title="code/common/scaffold/src/device.cpp"
// Extensions every sample in the series needs on the device. Vulkan 1.3 folded
// dynamic rendering and synchronization2 into core, so the only one left is the
// swapchain itself.
constexpr std::array kRequiredDeviceExtensions = {
    VK_KHR_SWAPCHAIN_EXTENSION_NAME,
};

bool device_supports_extensions(VkPhysicalDevice gpu) {
    uint32_t count = 0;
    VK_CHECK(vkEnumerateDeviceExtensionProperties(gpu, nullptr, &count, nullptr));
    std::vector<VkExtensionProperties> available(count);
    VK_CHECK(vkEnumerateDeviceExtensionProperties(gpu, nullptr, &count, available.data()));

    return std::ranges::all_of(kRequiredDeviceExtensions, [&](const char* required) {
        return std::ranges::any_of(available, [required](const VkExtensionProperties& e) {
            return std::strcmp(required, e.extensionName) == 0;
        });
    });
}

// Index of a queue family that can do graphics, compute and presentation at once,
// or nullopt if this GPU has none.
std::optional<uint32_t> find_universal_queue_family(VkPhysicalDevice gpu,
                                                    VkSurfaceKHR surface) {
    uint32_t count = 0;
    vkGetPhysicalDeviceQueueFamilyProperties(gpu, &count, nullptr);
    std::vector<VkQueueFamilyProperties> families(count);
    vkGetPhysicalDeviceQueueFamilyProperties(gpu, &count, families.data());

    for (uint32_t i = 0; i < count; ++i) {
        constexpr VkQueueFlags wanted = VK_QUEUE_GRAPHICS_BIT | VK_QUEUE_COMPUTE_BIT;
        if ((families[i].queueFlags & wanted) != wanted) {
            continue;
        }
        VkBool32 can_present = VK_FALSE;
        VK_CHECK(vkGetPhysicalDeviceSurfaceSupportKHR(gpu, i, surface, &can_present));
        if (can_present == VK_TRUE) {
            return i;
        }
    }
    return std::nullopt;
}

// Discrete GPUs first, then integrated, then whatever is left. Crude, and exactly
// good enough: a tutorial that picks the wrong GPU is a tutorial that runs slowly,
// not one that runs wrongly.
int score_device(const VkPhysicalDeviceProperties& props) {
    switch (props.deviceType) {
        case VK_PHYSICAL_DEVICE_TYPE_DISCRETE_GPU: return 3;
        case VK_PHYSICAL_DEVICE_TYPE_INTEGRATED_GPU: return 2;
        case VK_PHYSICAL_DEVICE_TYPE_VIRTUAL_GPU: return 1;
        default: return 0;
    }
}

}  // namespace
```

```cpp title="code/common/scaffold/src/device.cpp"
void Device::select_physical_device(VkInstance instance, VkSurfaceKHR surface) {
    uint32_t count = 0;
    VK_CHECK(vkEnumeratePhysicalDevices(instance, &count, nullptr));
    if (count == 0) {
        throw std::runtime_error(
            "No Vulkan-capable GPU found. Check that your graphics driver is "
            "installed and current.");
    }
    std::vector<VkPhysicalDevice> devices(count);
    VK_CHECK(vkEnumeratePhysicalDevices(instance, &count, devices.data()));

    int best_score = -1;
    std::string rejection_log;

    for (VkPhysicalDevice candidate : devices) {
        VkPhysicalDeviceProperties props{};
        vkGetPhysicalDeviceProperties(candidate, &props);

        if (props.apiVersion < VK_API_VERSION_1_3) {
            rejection_log += std::format("\n  {}: reports Vulkan {}.{}, needs 1.3",
                                         props.deviceName,
                                         VK_API_VERSION_MAJOR(props.apiVersion),
                                         VK_API_VERSION_MINOR(props.apiVersion));
            continue;
        }
        if (!device_supports_extensions(candidate)) {
            rejection_log +=
                std::format("\n  {}: missing VK_KHR_swapchain", props.deviceName);
            continue;
        }
        const std::optional<uint32_t> family =
            find_universal_queue_family(candidate, surface);
        if (!family.has_value()) {
            rejection_log += std::format(
                "\n  {}: no queue family with graphics + compute + present",
                props.deviceName);
            continue;
        }

        const int score = score_device(props);
        if (score > best_score) {
            best_score = score;
            gpu_ = candidate;
            gpu_properties_ = props;
            queue_family_ = *family;
        }
    }

    if (gpu_ == VK_NULL_HANDLE) {
        throw std::runtime_error(
            "No suitable GPU found. Every device was rejected:" + rejection_log);
    }
}
```

```cpp title="code/common/scaffold/src/device.cpp"
void Device::create_device() {
    const float priority = 1.0F;
    const VkDeviceQueueCreateInfo queue_info{
        .sType = VK_STRUCTURE_TYPE_DEVICE_QUEUE_CREATE_INFO,
        .pNext = nullptr,
        .flags = 0,
        .queueFamilyIndex = queue_family_,
        .queueCount = 1,
        .pQueuePriorities = &priority,
    };

    // Features are opt-in. These three are what the series is built on, and asking
    // for them here is what makes vkCmdBeginRendering and vkCmdPipelineBarrier2
    // legal to call at all.
    // These structs have dozens of fields each. Value-initialise to all-false and
    // then switch on only what is wanted: asking for a feature you do not use can
    // cost performance, and on some drivers it can cost device creation entirely.
    VkPhysicalDeviceVulkan13Features features13{};
    features13.sType = VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_VULKAN_1_3_FEATURES;
    features13.synchronization2 = VK_TRUE;
    features13.dynamicRendering = VK_TRUE;
    // `discard` in Slang compiles to OpDemoteToHelperInvocation rather than the older
    // OpKill, and that SPIR-V capability has to be asked for by name. Without it
    // vkCreateShaderModule rejects the module -- which is how chapter 4.2 found out it
    // was needed, since nothing in the series discards a fragment before then.
    features13.shaderDemoteToHelperInvocation = VK_TRUE;
```

Here is the first addition. **`shaderDemoteToHelperInvocation`** was not in your version,
and it is needed because of a detail two parts away.

A fragment shader can decide a pixel should not be drawn after all — `discard` in Slang.
There are two SPIR-V instructions for that. The older `OpKill` terminates the invocation
outright; the newer one *demotes* it to a helper invocation, which keeps it running purely
so that neighbouring pixels can still compute derivatives from it. Slang emits the newer
one, and using it requires this feature. Leave it off and `vkCreateShaderModule` rejects
the module — which is exactly how chapter 4.2 discovered it was missing, since no chapter
before that discards anything.

```cpp title="code/common/scaffold/src/device.cpp"
    // How a struct reached through a 64-bit address is laid out in memory. Without this,
    // a buffer's contents must follow the "relaxed" rules a uniform or storage block
    // follows, the sharpest of which is that no vector may straddle a 16-byte boundary:
    // two float3 in a row put the second one at offset 12, spanning 12 to 24, and
    // vkCreateShaderModule rejects the module outright. With it, the rule becomes the one
    // a C++ compiler already uses -- every member aligned to its own size and nothing
    // else -- so a struct in Slang and the same struct in C++ are the same bytes.
    // Chapter 4.5 hits this on its very first pointer and explains it in full.
    features12.scalarBlockLayout = VK_TRUE;

    features2.pNext = &features12;
```

The third addition, **`scalarBlockLayout`**, is about how bytes sit in memory.

Without it, a buffer a shader reads must follow the relaxed layout rules that uniform and
storage blocks use. The sharpest of those is that no vector may straddle a 16-byte
boundary. Two `float3` in a row break it immediately: the first occupies bytes 0 to 12,
which puts the second at offset 12, spanning 12 to 24 — across the boundary at 16 — and
the module is rejected.

With the feature on, the rule becomes the one a C++ compiler already follows: every member
aligned to its own size and nothing more. A struct written in Slang and the same struct
written in C++ then occupy the same bytes, which is what makes it safe to `memcpy` one
into the other. Chapter 1.10 meets the relaxed rules head-on, and chapter 4.5 relies on
this feature from its first line.

`set_debug_name` returns early when the extension is missing, so every caller can name
objects unconditionally without guarding each call. The `handle == 0` check covers naming
something that was never created.

`vkDeviceWaitIdle` is the function behind `wait_idle`, and it returns a `VkResult` because
it genuinely can fail: if the GPU has crashed — a driver reset, an infinite loop in a
shader — this is where you find out, as `VK_ERROR_DEVICE_LOST`.

### One more file: VMA's implementation

```cpp title="code/common/base/src/vma_impl.cpp"
// The Vulkan Memory Allocator is a header-only library, which means its function
// bodies have to be compiled into exactly one translation unit somewhere in the
// program. This file is that one place, and it deliberately contains nothing else.

#include <volk.h>

// volk fetches the entry points at run time, so VMA must not expect the linker to
// resolve them statically; it uses the pointers handed to vmaCreateAllocator instead.
#define VMA_STATIC_VULKAN_FUNCTIONS 0
#define VMA_DYNAMIC_VULKAN_FUNCTIONS 1

#define VMA_IMPLEMENTATION
#include <vk_mem_alloc.h>
```

Five lines that are easy to get wrong and produce baffling errors when you do.

VMA is **header-only**: the header holds both the declarations and the function bodies.
Every file that includes it gets the declarations, but the bodies must be compiled exactly
once in the whole program, or the linker reports every VMA function as defined multiple
times. Defining `VMA_IMPLEMENTATION` before the include is what asks for the bodies, and
this file is the one place that does it. It contains nothing else so that nobody is ever
tempted to include it, and so the warnings this third-party code produces can be switched
off for this file alone.

The other two defines are the volk pairing from the previous section, stated to VMA
directly: do not expect `vkAllocateMemory` to exist as a linker symbol, fetch it through
the pointers instead.

## Words introduced in this chapter

| | |
|---|---|
| **physical device** | a GPU that exists; you enumerate and query it, never create it |
| **logical device** | your configured connection to one physical device |
| **queue** | a channel work is submitted to and executed from, asynchronously |
| **queue family** | a group of queues sharing the same capabilities |
| **submit** | to post a recorded command buffer to a queue |
| **surface** | Vulkan's handle for a window-system drawing target |
| **feature** | an optional capability that must be switched on explicitly |
| **heap** | a physical pool of memory, device-local or host-visible |
| **dispatch table** | the loader's indirection for routing calls to the right driver |
| **created vs retrieved** | handles you must destroy, versus handles the driver owns and hands you |
| **allocator (VMA)** | the library that sub-allocates a few large blocks into many resources |
| **device-local memory** | memory the GPU reads fastest; on a discrete card, the RAM on the board |
| **object name** | a readable label attached to a handle, so validation messages name it |
