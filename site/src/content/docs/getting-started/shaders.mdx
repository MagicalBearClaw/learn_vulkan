There is almost no new Vulkan in this chapter. The C++ shrank instead: everything 1.8
wrote by hand now lives in `vkcommon`, and the two buffers are two lines.

```cpp title="code/src/1.getting_started/shaders/main.cpp"
vertex_buffer_ = vkc::upload_to_device_local(
    context(), kVertices.data(), sizeof(kVertices),
    VK_BUFFER_USAGE_VERTEX_BUFFER_BIT);
```

The subject this time is the shading language itself.

## The program compiles them

Vulkan does not take shader source. It takes **SPIR-V**: a binary intermediate
representation, already parsed, with names stripped and control flow made explicit.
Somebody has to do the translation, and the interesting question is *when*.

There are two answers and both are legitimate.

**Ahead of time** is what a shipping game does. Compile every shader during the build,
put the SPIR-V in a pack file, and the program never contains a compiler. Syntax errors
fail your build rather than a user's launch, startup is fast, and the binary is smaller.

**At startup** is what this project does. The samples link `libslang` and hand it the
`.slang` file that sits next to the executable. Chapter 1.7 wrote the code out in full;
from here it is one call:

```cpp title="code/src/1.getting_started/shaders/main.cpp"
const VkShaderModule shader =
    vkc::load_shader(device, LVK_CHAPTER_ID, "quad.slang");
```

The reason is that this is a course, and half the exercises end with "change this and
run it again". The file beside the binary *is* the shader. There is no `.spv` anywhere,
no build step between editing and seeing, and no stale artefact that can lie to you. It
is also how a tool with hot reload works, and how an engine that compiles shader
permutations on demand works, so it is not a toy arrangement.

What it costs, honestly: `libslang` is about 30 MB beside the binary, and the whole
program — window, device, buffers and the shader compile together — takes roughly a
third of a second to reach its first frame. Neither matters for a tutorial. Both would
matter for something you ship, and the answer there is to cache the SPIR-V the first
time and skip the compiler afterwards.

Either way, **one compiler, one dialect**. OpenGL's GLSL front end was each vendor's own,
and they disagreed — about whether an implicit conversion was allowed, about how
aggressive an optimisation could be, occasionally about what a loop meant. SPIR-V moves
that stage out of the driver, whichever side of the build you do it on.

:::tip[Look at the SPIR-V]
There is no `.spv` file to inspect, but the Slang your build downloaded includes the
command-line compiler, so you can make one:

```bash
SLANGC=code/out/build/linux-debug/_deps/slang_bindist-src/bin/slangc
$SLANGC code/src/1.getting_started/shaders/quad.slang \
    -target spirv -profile spirv_1_6 -matrix-layout-column-major \
    -emit-spirv-directly -fvk-use-entrypoint-name -o /tmp/quad.spv

spirv-dis /tmp/quad.spv | head -40
spirv-val --target-env vulkan1.3 /tmp/quad.spv
```

`spirv-dis` prints a module in readable assembly, and it is the fastest way to answer
"did the compiler really keep that branch?" or "which location did that end up at?".
`spirv-val` tells you whether the module is legal before a driver ever sees it.
:::

:::caution[The API's defaults are not the command line's defaults]
Two of the options `load_shader` sets exist because the two disagree.

`VulkanUseEntryPointName` keeps the SPIR-V entry points named after the Slang functions.
Without it, a module with a single entry point gets it renamed to `main` and `pName`
stops matching.

`defaultMatrixLayoutMode` is the one that costs people an afternoon. The API defaults to
row-major, `glm` is column-major, and the mismatch transposes every transform silently —
it still draws. `load_shader` sets `SLANG_MATRIX_LAYOUT_COLUMN_MAJOR`, which is what
`slangc`'s command line does by default. That is why the snippet above passes
`-matrix-layout-column-major`: so that what you disassemble is what the program runs.
:::


## Why Slang

Vulkan does not care what language you write in — it sees SPIR-V and nothing else. GLSL
via glslang is the traditional answer and still works. This series uses **Slang**
instead, for reasons that show up immediately and keep paying off:

- **One file per pipeline.** Every stage lives in one module, and the interface between
  them is a shared struct rather than two lists of declarations in two files.
- **A real type system.** Generics, interfaces, modules and overload resolution, so the
  lighting code you write once in Part 2 can be instantiated for a dozen pipelines
  instead of copied into each of them with a `#define` on top.
- **It is the direction the ecosystem moved.** Slang is a Khronos project and ships in
  the Vulkan SDK; `slangc` sits beside `glslangValidator` in the same `bin` directory,
  and the modules it produces identify their generator as "Khronos Slang Compiler".

The syntax comes from HLSL. If you know GLSL you will be reading it fluently within a
chapter: `vec3` is `float3`, `mat4` is `float4x4`, `mix` is `lerp`, `mod` is `fmod`, and
the `layout(...)` qualifiers become `[[vk::...]]` attributes. Appendix *Slang for GLSL
programmers* has the full table for when you are porting something.

## Stages talk through a struct

A Slang file declares entry points, and an attribute says which stage each one is:

```slang title="code/src/1.getting_started/shaders/quad.slang"
[shader("vertex")]
VSOutput vertexMain(VSInput input) { ... }

[shader("fragment")]
float4 fragmentMain(VSOutput input) : SV_Target { ... }
```

Both compile into one SPIR-V module. `main.cpp` names them in
`VkPipelineShaderStageCreateInfo::pName`, which is the mechanism chapter 1.7 introduced.

What travels between stages is a struct, and the slots are attributes on its fields:

```slang title="code/src/1.getting_started/shaders/quad.slang"
struct VSInput {
    [[vk::location(0)]] float2 position;
    [[vk::location(1)]] float3 colour;
};

struct VSOutput {
    float4 position : SV_Position;
    [[vk::location(0)]] float3 colour;
    [[vk::location(1)]] nointerpolation float3 flat_colour;
};
```

Read those two blocks carefully, because the two numbering spaces are **completely
independent**. `VSInput`'s locations pair with `VkVertexInputAttributeDescription` on the
C++ side; `VSOutput`'s pair with whatever the fragment stage declares as its input. That
`location(0)` appears twice in eight lines and means two unrelated things.

The vertex-to-fragment half of that is where Slang differs from GLSL in a way you feel.
`fragmentMain` takes **the same `VSOutput`**, so there is one declaration of the
interface rather than two that must agree. Nothing stops you writing a second struct —
and exercise 5 asks you to, precisely to see what goes wrong when the two disagree.

A `float3` output occupies one location. A `float4` also occupies one. A `float4x4`
occupies four, and a double-precision type occupies two — so the numbers are not always
consecutive, and the compiler will tell you when you have overlapped them.

## System-value semantics

The `: SV_Something` suffixes are **system-value semantics**: they mark a field the
hardware fills in or reads back, where GLSL would use a `gl_` global. Four matter early.

**`SV_Position`** is the one output every vertex shader must write. It is a clip-space
position, and the hardware divides it by `w` to get normalised device coordinates:

```slang title="code/src/1.getting_started/shaders/quad.slang"
output.position = float4(input.position, 0.0, 1.0);
```

`w = 1.0` makes that division a no-op, which is right for flat 2D work. Once there is a
perspective projection, `w` carries the distance to the camera and the division is
precisely what makes far-away things small. That is chapter 1.13.

Read as a *fragment input*, the same field means something different: the fragment's
position in pixels. GLSL keeps these apart as `gl_Position` and `gl_FragCoord`; Slang
gives the field one name and lets the stage decide. This chapter's fragment shader uses
it:

```slang title="code/src/1.getting_started/shaders/quad.slang"
float2 cell = floor(input.position.xy / kCheckerSize);
float checker = fmod(cell.x + cell.y, 2.0);
```

Its origin is the **top-left** of the framebuffer, consistent with Vulkan's downward y.
OpenGL puts it at the bottom-left, and a shader ported without accounting for that comes
out vertically mirrored.

Because it is in screen pixels, the checkerboard is nailed to the screen rather than to
the quad. Resize the window and the quad changes size while the squares do not.
Attaching a pattern to a *surface* needs texture coordinates, which arrive in 1.11.

**`SV_VulkanVertexID`** counts vertices within a draw — it is what 1.7 used to index its
constant array. Its companion is `SV_VulkanInstanceID`.

:::caution[Not `SV_VertexID`]
Slang has both, and they are not the same. `SV_VertexID` is the HLSL semantic, where the
index is relative to the draw, so Slang compiles it to `VertexIndex - BaseVertex` and the
module declares SPIR-V's `DrawParameters` capability. Unless you enabled
`shaderDrawParameters` on the device, validation rejects it at `vkCreateShaderModule`:

```
SPIR-V Capability DrawParameters was declared, but one of the following requirements is
required (VkPhysicalDeviceVulkan11Features::shaderDrawParameters OR
VK_KHR_shader_draw_parameters [when using Vulkan 1.0]).
```

`SV_VulkanVertexID` is Vulkan's `VertexIndex` builtin directly, with nothing subtracted
and nothing to enable. The two agree whenever `firstVertex` is 0, which is why the
mistake can live in a codebase for a long time.
:::

**`SV_Target`** marks a fragment shader's colour attachment output; `SV_Target0` through
`SV_TargetN` address them individually once there is more than one.

**`SV_Depth`** lets a fragment shader override the depth it writes. It is worth knowing
about mostly so you know to avoid it: writing it disables early depth testing on most
hardware.

:::caution[Vulkan's clip space differs in two ways]
y points **down**, and z runs **0 to 1** rather than −1 to 1. Both differ from OpenGL,
and both are silent: a shader ported straight across renders upside down and with a
depth buffer that is subtly wrong.

The project sets `GLM_FORCE_DEPTH_ZERO_TO_ONE` so glm's projection matrices produce the
right z. The y flip is handled explicitly in chapter 1.13.
:::

## Interpolation, and switching it off

A fragment shader input is not the value a vertex wrote. The hardware interpolates the
three vertex values across the triangle, weighted by the fragment's position. That is
what produced 1.7's gradient, and it is free.

It is also a choice. This chapter's vertex shader sends the same colour twice, and the
second copy carries a qualifier:

```slang title="code/src/1.getting_started/shaders/quad.slang"
[[vk::location(0)]] float3 colour;
[[vk::location(1)]] nointerpolation float3 flat_colour;
```

`nointerpolation` — GLSL's `flat` — means every fragment in the triangle gets the value
from one nominated vertex, the **provoking vertex**, which in Vulkan is the first vertex
of the primitive. Each triangle comes out a single flat colour.

There are two other qualifiers you will meet. `noperspective` interpolates in screen
space rather than correcting for perspective, which is occasionally what you want for
screen-space effects. `sample` forces the shader to run per sample rather than per pixel
under multisampling; `centroid` keeps it per pixel but moves the sample point inside the
covered area, which matters at the edges of triangles.

Integers are *always* `nointerpolation`, whether you say so or not — there is no
meaningful way to interpolate between two integers.

## Specialisation constants

Here is the one genuinely Vulkan-shaped idea in the chapter.

A shader often has a value that never changes at run time but that you would like to
choose from C++: a quality level, a light count, a feature toggle. In OpenGL you would
either recompile the shader with a `#define` or pay for a uniform read and a branch.

Vulkan gives you a third option. Declare a constant with an id:

```slang title="code/src/1.getting_started/shaders/quad.slang"
[[vk::constant_id(0)]] const int kShadingMode = 0;      // 0 = smooth, 1 = flat
[[vk::constant_id(1)]] const float kCheckerSize = 48.0;
```

Those look like ordinary constants with defaults, and if the host says nothing that is
exactly what they are. But the host can replace them **when the pipeline is created** —
after the SPIR-V is written, before the driver compiles it to machine code.

On the C++ side it is a flat block of bytes plus a table describing it:

```cpp title="code/src/1.getting_started/shaders/main.cpp"
struct ShaderConstants {
    int32_t shading_mode = 0;
    float checker_size = 48.0F;
};

const std::array<VkSpecializationMapEntry, 2> entries{{
    {
        .constantID = 0,
        .offset = offsetof(ShaderConstants, shading_mode),
        .size = sizeof(ShaderConstants::shading_mode),
    },
    {
        .constantID = 1,
        .offset = offsetof(ShaderConstants, checker_size),
        .size = sizeof(ShaderConstants::checker_size),
    },
}};
```

Each entry says: constant id N is this many bytes at this offset. The ids match
`vk::constant_id` in the shader; the offsets match the struct. The whole thing goes into
`VkPipelineShaderStageCreateInfo::pSpecializationInfo`, which is the field 1.7 left as
`nullptr`.

The payoff is that the branch disappears. `kShadingMode` is a true compile-time constant
by the time the driver optimises, so only one side of `(kShadingMode == 1) ? ... : ...`
survives, and a loop bounded by a specialisation constant can be fully unrolled.

The cost is that changing a value means **building a new pipeline**. That is the trade:
free at run time, expensive to change. For a value that changes every frame you want a
push constant or a uniform buffer instead — which is chapter 1.10, and is the real answer
to "where did `glUniform` go".

:::note[Added to `vkcommon` this chapter]
`vkc::Buffer`, `vkc::upload_to_device_local` and `vkc::immediate_submit` — chapter 1.8's
code, with a destructor attached. `PipelineBuilder` gained
`fragment_specialisation()`, which does nothing but carry the two structures above
through to the shader stage.

`vkc::load_shader` is chapter 1.7's Slang compiler code, unchanged except that the
global session is now created once and cached rather than per shader. It is in
`code/common/scaffold/src/pipeline.cpp` if you want to read it again.
:::

## A shader style note

A few habits worth forming now, all of which pay off in the lighting chapters.

Prefer the built-in functions. `lerp`, `clamp`, `smoothstep`, `dot`, `normalize`,
`length` and `reflect` usually map to single instructions, and hand-written equivalents
usually do not.

Write `float3(0.0)` rather than `float3(0, 0, 0)` — the splat constructor is there and
it reads better.

Watch out for `if` on a value that differs between neighbouring pixels. Fragment shaders
run in groups — 2×2 quads at minimum, typically 32 or 64 invocations in lockstep — and
when invocations in a group disagree about a branch, the hardware runs **both sides** and
discards the unwanted half. A branch that is uniform across the screen is nearly free; a
branch that is different for every pixel costs the sum of both sides.

## Exercises

1. Set `shading_mode` to `1` in `ShaderConstants` and run it. Two flat triangles. Which
   corner's colour won for each triangle? That is the provoking vertex, and it is the
   first index of each triangle in `kIndices`.
2. Change `checker_size` to `12.0` and to `400.0`. Note that you changed a value the
   shader treats as a compile-time constant and did not touch the shader.
3. Make the checkerboard follow the quad instead of the screen: interpolate a `float2`
   from the vertex positions — mapping −0.6…0.6 to 0…1 — and use that instead of
   `input.position.xy`. Resize the window and watch the difference. You have just
   invented texture coordinates.
4. Produce a `.spv` with the `slangc` command above and run `spirv-dis` on it. Find
   `OpSpecConstant`: those are the two constants sitting in the module with their
   default values, waiting to be overridden. While you are there, find the two
   `OpEntryPoint` lines and the `Flat` decoration.

   Then drop `-matrix-layout-column-major` and diff the two disassemblies. The only
   difference is `RowMajor` becoming `ColMajor` — and that one word is the entire bug
   the caution above describes.
5. Break the stage interface on purpose, which takes a little work now that both stages
   share `VSOutput`. Copy it to a second struct, `PSInput`, and make `fragmentMain` take
   that instead. Now delete `flat_colour` from `VSOutput` (and the line that writes it),
   leaving `PSInput` reading it. The validation layers say so precisely:

   ```
   vkCreateGraphicsPipelines(): pCreateInfos[0] (SPIR-V Interface)
   [EntryPoint "fragmentMain", VK_SHADER_STAGE_FRAGMENT_BIT] has a declared Input at
   Location 1 Component 0 but the previous stage
   ([EntryPoint "vertexMain", VK_SHADER_STAGE_VERTEX_BIT]) has no Output declared there.
   ```

   Now put the field back in `VSOutput` but **without** `nointerpolation`, leaving
   `PSInput`'s copy with it. **Nothing complains**, and it renders. The layers check that
   locations and types line up; interpolation qualifiers are outside what they verify.

   Then delete `PSInput` and go back to sharing one struct, which is the reason to share
   it: the mismatch you just spent five minutes constructing is not expressible.
