Every shader so far has been sealed: vertex data in, colour out, nothing else. This chapter
opens it up.

In OpenGL that was `glUniform4f`. Vulkan has no such call, and the reason is the reason for
most of Vulkan's shape — `glUniform` is a hidden allocation, a hidden copy, and a hidden
synchronisation, and the driver has to guess how long the value must stay alive. Vulkan makes
you say.

There are two mechanisms, and choosing between them is easy once you know the rule.

| | Push constants | Uniform buffer |
|---|---|---|
| Size | ~128 bytes total | 16 KiB guaranteed, usually far more |
| Where it lives | inside the command buffer | in GPU memory |
| Changing it | free, per draw | needs a buffer write |
| Setup | a range in the pipeline layout | layout, pool, set, write |

**Small and per-draw → push constants. Large or shared → a uniform buffer.**

## Push constants first

They are the simpler half by a wide margin.

```slang title="code/src/1.getting_started/descriptors/quad.slang"
struct PushConstants {
    float2 offset;
    float scale;
    float phase;
};
[[vk::push_constant]] PushConstants push;
```

Declared once, at file scope, and both entry points read it. In GLSL each stage repeats the
block in its own file and the two copies have to agree.

```cpp title="code/src/1.getting_started/descriptors/main.cpp"
struct PushConstants {
    glm::vec2 offset;  // where this copy of the quad goes, in clip space
    float scale;       // how big
    float phase;       // where in the pulse it starts
};
static_assert(sizeof(PushConstants) == 16);

constexpr std::array<PushConstants, 4> kQuads{{
    {{-0.45F, -0.45F}, 0.35F, 0.0F},
    {{0.45F, -0.45F}, 0.35F, 1.57F},
    {{0.45F, 0.45F}, 0.35F, 3.14F},
    {{-0.45F, 0.45F}, 0.35F, 4.71F},
}};
```

Four quads differing only in where they sit and where in the pulse they start — roughly
quarter-turns of a sine wave, since 1.57 ≈ π/2.

```cpp title="code/src/1.getting_started/descriptors/main.cpp"
        const VkPushConstantRange push_range{
            .stageFlags = VK_SHADER_STAGE_VERTEX_BIT | VK_SHADER_STAGE_FRAGMENT_BIT,
            .offset = 0,
            .size = sizeof(PushConstants),
        };
```

A `VkPushConstantRange` is the declaration in the pipeline layout that says these bytes
exist: which stages may read them, at what offset, and how many. A layout with no range
means `vkCmdPushConstants` has nowhere to put anything.

`stageFlags` must cover every stage that reads the
block; both do here, and naming only one is a validation error rather than a silent read of
nothing.

```cpp title="code/src/1.getting_started/descriptors/main.cpp"
        for (const PushConstants& quad : kQuads) {
            vkCmdPushConstants(frame.cmd, pipeline_layout_,
                               VK_SHADER_STAGE_VERTEX_BIT |
                                   VK_SHADER_STAGE_FRAGMENT_BIT,
                               0, sizeof(PushConstants), &quad);

            vkCmdDrawIndexed(frame.cmd, static_cast<uint32_t>(kIndices.size()), 1, 0, 0,
                             0);
        }
```

That is the whole mechanism. The bytes are **copied into the command buffer** at record time:

```
   command buffer: [ ...bind... ][ 16 bytes ][ draw ][ 16 bytes ][ draw ][ 16 bytes ][ draw ]
                                  quad 0              quad 1              quad 2
```

No buffer to allocate, no descriptor to write, nothing to keep alive until the GPU is finished,
and no per-frame duplication. Each draw sees the values pushed before it.

There is **one push constant block per pipeline layout**, not one per binding. Everything a draw
needs goes in that single struct.

:::caution[128 bytes is the budget]
`maxPushConstantsSize` is guaranteed to be at least 128 bytes and that is exactly what a good
deal of hardware offers. The sample prints yours at startup:

```cpp title="code/src/1.getting_started/descriptors/main.cpp"
        spdlog::info("maxPushConstantsSize on this GPU: {} bytes",
                     context().gpu_properties().limits.maxPushConstantsSize);
```

128 bytes is two 4×4 matrices with nothing left over, which is why the usual arrangement is a
model matrix in push constants and the camera matrices in a uniform buffer. Chapter 1.13 does
precisely that.
:::

## Descriptors: the three-layer idea

Uniform buffers are more work, because Vulkan separates three things OpenGL merged.

```
   DESCRIPTOR SET LAYOUT      the shape: "binding 0 is a uniform buffer, vertex+fragment"
          │                   no memory, no buffer — built into the pipeline
          ▼
   DESCRIPTOR POOL            preallocated storage for N sets of M descriptors
          │
          ▼
   DESCRIPTOR SET             an instance of that shape, allocated from the pool
          │                   starts out empty
          ▼
   WRITE                      now it points at an actual buffer
```

A **descriptor** is a pointer the GPU can follow — this buffer, at this offset, this many bytes.
A **descriptor set** is a group of them bound together, and sets are the unit of binding: the
split between them is a performance decision, and one set for per-frame data, one for
per-material, one for per-object is the standard arrangement.

Four objects, in order.

### 1. The layout

```cpp title="code/src/1.getting_started/descriptors/main.cpp"
    void create_descriptors() {
        const VkDevice device = context().device();

        const VkDescriptorSetLayoutBinding binding{
            .binding = 0,
            .descriptorType = VK_DESCRIPTOR_TYPE_UNIFORM_BUFFER,
            .descriptorCount = 1,
            .stageFlags = VK_SHADER_STAGE_VERTEX_BIT | VK_SHADER_STAGE_FRAGMENT_BIT,
            .pImmutableSamplers = nullptr,
        };

        const VkDescriptorSetLayoutCreateInfo layout_info{
            .sType = VK_STRUCTURE_TYPE_DESCRIPTOR_SET_LAYOUT_CREATE_INFO,
            .pNext = nullptr,
            .flags = 0,
            .bindingCount = 1,
            .pBindings = &binding,
        };
        VK_CHECK(vkCreateDescriptorSetLayout(device, &layout_info, nullptr,
                                             &set_layout_));
```

This is a description only: no memory, no buffer, nothing bound. It is the *type* of the set.

`descriptorCount` above 1 makes the binding an *array* of descriptors, which is how bindless
rendering works — chapter 3.4. `stageFlags` should list only the stages that actually read it;
some hardware can skip work for stages that do not.

### 2. The pool

```cpp title="code/src/1.getting_started/descriptors/main.cpp"
        const VkDescriptorPoolSize pool_size{
            .type = VK_DESCRIPTOR_TYPE_UNIFORM_BUFFER,
            .descriptorCount = vkc::kFramesInFlight,
        };

        const VkDescriptorPoolCreateInfo pool_info{
            .sType = VK_STRUCTURE_TYPE_DESCRIPTOR_POOL_CREATE_INFO,
            .pNext = nullptr,
            .flags = 0,
            .maxSets = vkc::kFramesInFlight,
            .poolSizeCount = 1,
            .pPoolSizes = &pool_size,
        };
        VK_CHECK(vkCreateDescriptorPool(device, &pool_info, nullptr, &descriptor_pool_));
```

Descriptor sets are not created individually; they are allocated out of a pool told up front how
many of each type it must serve.

**A pool does not grow.** There are two independent limits: `maxSets` counts *sets*, and each
`VkDescriptorPoolSize` counts *descriptors of one type* across all of them. Exhaust either and
allocation fails with `VK_ERROR_OUT_OF_POOL_MEMORY`.

### 3. The sets

```cpp title="code/src/1.getting_started/descriptors/main.cpp"
        const std::array<VkDescriptorSetLayout, vkc::kFramesInFlight> layouts{
            set_layout_, set_layout_};

        const VkDescriptorSetAllocateInfo alloc_info{
            .sType = VK_STRUCTURE_TYPE_DESCRIPTOR_SET_ALLOCATE_INFO,
            .pNext = nullptr,
            .descriptorPool = descriptor_pool_,
            .descriptorSetCount = vkc::kFramesInFlight,
            .pSetLayouts = layouts.data(),
        };
        VK_CHECK(vkAllocateDescriptorSets(device, &alloc_info, descriptor_sets_.data()));
```

One layout repeated, because both sets have the same shape — the API wants one layout per set it
is allocating, even when they are identical. An allocated set is **empty**: it has the right
shape and points at nothing.

### 4. The write

```cpp title="code/src/1.getting_started/descriptors/main.cpp"
        for (size_t i = 0; i < vkc::kFramesInFlight; ++i) {
            const VkDescriptorBufferInfo buffer_info{
                .buffer = uniform_buffers_[i].handle(),
                .offset = 0,
                .range = sizeof(Globals),
            };

            const VkWriteDescriptorSet write{
                .sType = VK_STRUCTURE_TYPE_WRITE_DESCRIPTOR_SET,
                .pNext = nullptr,
                .dstSet = descriptor_sets_[i],
                .dstBinding = 0,
                .dstArrayElement = 0,
                .descriptorCount = 1,
                .descriptorType = VK_DESCRIPTOR_TYPE_UNIFORM_BUFFER,
                .pImageInfo = nullptr,
                .pBufferInfo = &buffer_info,
                .pTexelBufferView = nullptr,
            };

            vkUpdateDescriptorSets(device, 1, &write, 0, nullptr);
        }
    }
```

A `VkDescriptorBufferInfo` is the descriptor itself in its raw form — the buffer, the byte
offset into it, and the number of bytes visible. That triple is what the GPU ends up
following.

Writing into a set is what makes it refer to anything. The three
`pImageInfo`/`pBufferInfo`/`pTexelBufferView` pointers are a union in all but name —
`descriptorType` decides which one is read, and the other two must be null.

This happens **once, at startup**. The set points at the same buffer for the life of the
program; only the buffer's *contents* change per frame. Rewriting descriptor sets every frame is
a common mistake that costs real time — and it is not needed, because the descriptor is a
pointer and the pointer is not what changes.

```cpp title="code/src/1.getting_started/descriptors/main.cpp"
        vkCmdBindDescriptorSets(frame.cmd, VK_PIPELINE_BIND_POINT_GRAPHICS,
                                pipeline_layout_, 0, 1, &descriptor_sets_[slot], 0,
                                nullptr);
```

Bound once for the whole frame, because nothing in it changes between draws. A descriptor set
binding is relatively expensive; a push constant is not, which is exactly why the per-draw data
went the other way.

The `0` after the layout is the **set index**, and it is the second number in the shader's
`[[vk::binding(0, 0)]]` — Slang writes the attribute as `[[vk::binding(binding, set)]]`, binding
first.

```slang title="code/src/1.getting_started/descriptors/quad.slang"
struct Globals {
    float4 ambient;
    float time;
};
[[vk::binding(0, 0)]] ConstantBuffer<Globals> globals;
```

`ConstantBuffer<T>` is Slang's name for a uniform buffer. The struct's *name* is not matched
against anything on the host; only the numbers are.

## One buffer per frame in flight

This is the detail that turns a working program into a subtly broken one.

The CPU runs up to `kFramesInFlight` frames ahead of the GPU — that was chapter 1.6's whole
point. So when the CPU writes frame 7's data, the GPU may still be reading frame 6's:

```
   one buffer:    CPU writes frame 7 ──▶ [ Globals ] ◀── GPU still reading it for frame 6
                                          corrupted mid-frame

   two buffers:   CPU writes frame 7 ──▶ [ slot 1 ]
                                         [ slot 0 ] ◀── GPU reads frame 6 undisturbed
```

```cpp title="code/src/1.getting_started/descriptors/main.cpp"
        const size_t slot = frame.frame_number % vkc::kFramesInFlight;

        update_globals(slot, frame.frame_number);
```

```cpp title="code/src/1.getting_started/descriptors/main.cpp"
    std::array<vkc::Buffer, vkc::kFramesInFlight> uniform_buffers_;
    std::array<VkDescriptorSet, vkc::kFramesInFlight> descriptor_sets_{};

    VkDescriptorSetLayout set_layout_ = VK_NULL_HANDLE;
    VkDescriptorPool descriptor_pool_ = VK_NULL_HANDLE;
```

The symptom of getting this wrong is nasty: everything looks right most of the time, and
occasionally a frame flickers with the next frame's values. It gets worse under load, and it may
not happen at all on your machine.

The *layout* and the *pool* are not duplicated, because neither is written to per frame. Only
the things the CPU touches while the GPU might be reading them need a copy each.

## Uniform buffer memory

```cpp title="code/src/1.getting_started/descriptors/main.cpp"
    void create_uniform_buffers() {
        for (vkc::Buffer& buffer : uniform_buffers_) {
            buffer = vkc::Buffer(context().allocator(), sizeof(Globals),
                                 VK_BUFFER_USAGE_UNIFORM_BUFFER_BIT,
                                 VMA_ALLOCATION_CREATE_HOST_ACCESS_SEQUENTIAL_WRITE_BIT |
                                     VMA_ALLOCATION_CREATE_MAPPED_BIT);
        }
    }
```

The vertex buffer in 1.8 was device-local, uploaded once through a staging buffer. A uniform
buffer that changes every frame wants the opposite: host-visible and permanently mapped, so
updating it is a `memcpy`. A staging copy per frame would cost more than the slower GPU reads
do, for 32 bytes read a handful of times.

```cpp title="code/src/1.getting_started/descriptors/main.cpp"
    void update_globals(size_t slot, uint64_t frame_number) {
        const Globals globals{
            .ambient = glm::vec4(0.12F, 0.10F, 0.18F, 1.0F),
            .time = static_cast<float>(frame_number) / 30.0F,
            .padding = {},
        };

        std::memcpy(uniform_buffers_[slot].mapped(), &globals, sizeof(globals));
    }
```

Frame-counter driven rather than clock driven, so frame N always looks the same and
`tools/capture.py` can diff screenshots.

No flush is needed because VMA gave us coherent memory. On memory that is not coherent,
`vmaFlushAllocation` goes after the `memcpy`.

```cpp title="code/src/1.getting_started/descriptors/main.cpp"
            buffer.destroy();
        }
```

Sets allocated from the pool are freed with it, so there is no `vkFreeDescriptorSets` here. The
layout is a separate object and has to go separately.

## The alignment trap

Now the part that catches everyone, once, and costs an afternoon.

A uniform buffer is laid out by **std140** rules, and they are not C++'s rules:

| Type | Alignment |
|---|---|
| `float`, `int`, `bool` | 4 |
| `float2` | 8 |
| `float3` | **16** |
| `float4` | 16 |
| `float4x4` | 16 |
| struct or array | 16, rounded up |

The two that bite are `float3` aligning to 16 rather than 12, and the whole block's size rounding
up to a multiple of 16.

Slang applies these rules to every `ConstantBuffer<T>`, and the SPIR-V says so out loud — the
generated type is literally named `Globals_std140`. **It will not warn you when the C++ struct
disagrees.**

```cpp title="code/src/1.getting_started/descriptors/main.cpp"
struct Globals {
    glm::vec4 ambient;  // offset 0, 16 bytes
    float time;         // offset 16
    float padding[3];   // to 32, the next multiple of 16
};
static_assert(sizeof(Globals) == 32);
```

Here is what happens if you put `time` first and drop the padding, which looks perfectly
symmetric on both sides:

```
   C++                          std140
   time    at offset 0          time    at offset 0
   ambient at offset 4          ambient at offset 16      ← aligns to 16
   size 20                      size 32

   the shader reads ambient from bytes 16..32 — which in your struct is
   twelve bytes past the end of it
```

Nothing reports an error. The shader reads whatever bytes are at the offset it expected.

Three habits make this a non-issue:

1. **Use `float4`, not `float3`**, in uniform blocks. The fourth component is free — the space is
   there either way — and you can put something useful in it.
2. **`static_assert` the size** of every uniform struct. It turns a silent corruption into a
   compile error.
3. **Order members largest first**: `float4x4`, then `float4`, then `float2`, then scalars.

Note that the Slang side declares only `ambient` and `time` — the padding is implicit there,
because std140 adds it whether you write it or not. The C++ side has to say it out loud.

## The shaders

```slang title="code/src/1.getting_started/descriptors/quad.slang"
[shader("vertex")]
VSOutput vertexMain(VSInput input) {
    float pulse = 0.85 + 0.15 * sin(globals.time + push.phase);

    VSOutput output;
    output.position = float4(input.position * push.scale * pulse + push.offset, 0.0, 1.0);
    output.colour = input.colour;
    return output;
}
```

```slang title="code/src/1.getting_started/descriptors/quad.slang"
[shader("fragment")]
float4 fragmentMain(VSOutput input) : SV_Target {
    float brightness = 0.6 + 0.4 * sin(globals.time + push.phase);

    return float4(input.colour * brightness + globals.ambient.rgb, 1.0);
}
```

Both data paths are live in both stages: `time` is shared by all four quads and comes from the
uniform buffer, `phase` differs per quad and comes from a push constant. The ambient term is
identical across the four; the brightness is not.

```cpp title="code/src/1.getting_started/descriptors/main.cpp"
        const VkPipelineLayoutCreateInfo layout_info{
            .sType = VK_STRUCTURE_TYPE_PIPELINE_LAYOUT_CREATE_INFO,
            .pNext = nullptr,
            .flags = 0,
            .setLayoutCount = 1,
            .pSetLayouts = &set_layout_,
            .pushConstantRangeCount = 1,
            .pPushConstantRanges = &push_range,
        };
        VK_CHECK(vkCreatePipelineLayout(device, &layout_info, nullptr,
                                        &pipeline_layout_));
```

The pipeline layout, finally doing something. Every chapter until now created an empty one; it is
the declaration of what the shaders can see, and now they can see two things.

## Words introduced in this chapter

| | |
|---|---|
| **push constant** | a few bytes copied straight into the command buffer, per draw |
| **uniform buffer** | GPU memory a shader reads through a descriptor |
| **descriptor** | a pointer the GPU follows: this buffer, this offset, this size |
| **descriptor set** | a group of descriptors bound together; the unit of binding |
| **descriptor set layout** | the *shape* of a set, with no memory attached |
| **descriptor pool** | preallocated storage sets are carved from; it does not grow |
| **std140** | the layout rules a uniform block obeys, which are not C++'s |

## Exercises

1. Swap the two members round — `float time` first, `glm::vec4 ambient` second — in the C++
   `Globals` and in the shader's `Globals`, and drop the padding. There are only two declarations
   to change and they agree with each other, so this *looks* correct. It is not, and the quads
   come out bright orange and magenta. Nothing in the validation layers says a word.
2. Now put `ambient` back first but change it to `float3`/`glm::vec3` on both sides, with no
   padding. Work out, before running it, what the shader reads for `time`.
3. Use one uniform buffer instead of two, by forcing `slot` to `0`. It will very likely look
   fine — the bug needs the GPU to actually be a frame behind. Try `--frames 2000` with the
   window dragged around.
4. Move `ambient` into the push constant block. It fits easily, and the sample gets simpler. Now
   consider what happens when it is a 64-light array instead.
5. Add a second binding to the set and watch what the pool says when you forget to increase
   `descriptorCount`. That `VK_ERROR_OUT_OF_POOL_MEMORY` is worth meeting deliberately once.
6. Drop `VK_SHADER_STAGE_FRAGMENT_BIT` from `push_range.stageFlags` but leave the
   `vkCmdPushConstants` call alone. The layers object, and the message names both the stage and
   the range — a good example of the pipeline layout being a contract rather than a formality.
